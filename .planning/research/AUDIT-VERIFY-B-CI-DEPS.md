## 3. Langium 4.4 Regression

**Current pin:** `bbj-vscode/package.json:701` — `"langium": "~4.3.1"` (tilde range, not caret: allows `4.3.x` patch releases only, not `4.4.0`). `bbj-vscode/package.json:715` — `"langium-cli": "~4.3.0"` (same tilde convention, must move in lockstep with the runtime).

**Would Dependabot re-propose it?** `.github/dependabot.yml` has **no** `ignore:` entry for `langium` or `langium-cli` (confirmed via grep — the only `ignore:` entries in the file are for `chevrotain` and `typescript` majors). PRs #682 (`langium` 4.3.1→4.4.0) and #684 (`langium-cli` 4.3.0→4.4.0) were both **closed without merging** on 2026-09-26, with a human comment explaining the regressions, and Dependabot's own bot reply confirms the standard behavior: *"OK, I won't notify you again about this release, but will get in touch when a new version is available."* This means:
- Dependabot will **not** re-open a PR for exactly `4.4.0` again on its own.
- Dependabot **will** open a new PR the next time `langium`/`langium-cli` publish a newer version (e.g. `4.4.1` or `4.5.0`), since no `ignore` rule was added to `dependabot.yml`.
- If the regression lives in the 4.4.0-era CST rework itself (PR #2191 in upstream `eclipse-langium/langium`, per the closing comment) rather than something fixed in a later patch, a `4.4.1` proposal would likely reproduce the same two regressions and get closed again the same way — this is a recurring maintenance cost until either upstream fixes it or the project adds an explicit `ignore` rule (e.g. `dependency-name: langium(-cli)?` with `update-types: ["version-update:semver-minor"]`) to stop re-litigating it every cycle.

**Regressions found (from PR #682's closing comment, human-verified locally on current `main` with `langium`/`langium-cli` 4.4.0 and Chevrotain aligned to `~13.2.0`):**
1. **Error-recovery performance:** parsing an unfinished call such as `x$ = CVS(`, `CVS(a$`, or `CVS(a$,` takes ~2.3s per document on 4.4.0 vs 1-2ms on 4.3.1 (and reports 2 parser errors instead of 1). This is what times out `composer-codelens.test.ts` in the local verification.
2. **Completion:** `DEF fnIsText(_f$,_t$)=_f$+|` (cursor at `|`) no longer offers the DEF FN parameters `_f$`/`_t$` as completions (`completion-test.test.ts`).

**Minimal upstream repro needed (for filing against `eclipse-langium/langium`, not this repo):**
- A small standalone Langium grammar project (or a fork of `eclipse-langium/langium`'s own test harness) with:
  - **Performance repro:** a grammar rule for a function-call expression with a required closing paren, parsed against an input that opens the call and terminates the document/line without closing it (mirroring `CVS(`/`CVS(a$`/`CVS(a$,`). Measure wall-clock parse time on 4.3.1 vs 4.4.0 for the same input; the ~1000x regression (1-2ms → 2.3s) should reproduce with error recovery enabled (`chevrotainParserConfig.recoveryEnabled: true`, matching `bbj-vscode/langium-config.json:19-22`) since that's what BBj's own config uses.
  - **Completion repro:** a grammar rule for a function definition with named parameters, parsed with the cursor positioned inside the function body/return-expression before the closing terminator (mirroring `DEF FN ... = expr|`), then a completion request at that offset. Compare the completion item list between 4.3.1 and 4.4.0 — the parameter names should appear on 4.3.1 and be missing on 4.4.0.
- Both repros should isolate whether the cause is the CST memory/rework (#2191) or the Chevrotain v13 bump (#2196), since upstream's own changelog names both as the two candidate causes in the 4.4.0 release. **Do not install or run langium 4.4 in this repository** — any repro should be built in a scratch project or against upstream's own repo, not `bbj-vscode`.

## 4. Grouping Suggestion for Phases

Given the risk flags above (anything touching `preview.yml`/`manual-release.yml`/`package.json`'s `vscode:prepublish` affects the live publish pipeline that runs on every push to `main`), a safe phase grouping is:

**Phase A — Pure dependency/metadata fixes (no CI behavior change, no risk to publish pipeline):**
#501 (`vsce` → devDependencies), #520 (pin `tsx`), #521 (bump Guava), #551 (add `github-actions` + `/documentation` Dependabot entries). All mechanical, independently testable, zero interaction with each other.

**Phase B — Dead-code / packaging cleanup in `bbj-vscode/package.json` (low risk, but touches the publish artifact — needs a VSIX install smoke test):**
