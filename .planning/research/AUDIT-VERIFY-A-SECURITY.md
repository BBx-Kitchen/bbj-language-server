## Per-issue detail

### #509 — interop host/port falsy-check only
Claims: `setConnectionConfig(host, port)` does `host || '127.0.0.1'` / `port || 5008` with no type/range check, so a malicious workspace-scoped setting can redirect the Java-lookup socket off loopback. Code today (`java-interop.ts:489-492`) is byte-for-byte the same shape reported by the audit; `createSocket()` still calls `socket.connect(this.interopPort, this.interopHost)` unchanged (`:513`). Fix statement: `setConnectionConfig()` rejects (or clamps to the default) a `port` that is not an integer in `[1, 65535]`, and a `host` that is not a non-empty string.

### #510 — duplicate falsy-only guard at both call sites
Same defect confirmed at both current call sites: `bbj-ws-manager.ts:72-74` (`params.initializationOptions.interopHost || 'localhost'`) and `main.ts:263-264` (`config.interop?.host || 'localhost'`), both feeding the still-unvalidated `setConnectionConfig`. Fix statement: centralizing the fix from #509 inside `setConnectionConfig` closes this one automatically — no separate call-site change needed, but a regression test should exercise both paths.

### #511 — configPath read with no containment check
Claims: a workspace-scoped `bbj.configPath` can point outside the workspace and have its full contents read on every `initializeWorkspace()`. The repo has since grown a dedicated `config-path-resolver.ts` (not present at audit time) that validates the setting is *absolute* after tilde-expansion and canonicalizes/symlink-resolves it (`resolveConfigPath`, `:167-206`) — but its own doc comment states the path is deliberately "never anchored to a workspace folder," i.e. containment was consciously rejected as a design goal (it must support `bbjHome`-relative defaults and system-wide config files, similar in spirit to `bbj.home`). The specific risk named in the issue (a committed `.vscode/settings.json` redirecting a **workspace-scope** setting to an arbitrary path) is not mitigated. Fix statement: since a blanket containment check would break the legitimate system-wide-config use case, gate resolution of a *workspace-scope* `configPath` value behind VS Code's Workspace Trust API (untrusted workspace → ignore/ prompt on `configPath`), or document this as an accepted risk if trust is out of scope for this milestone.

### #523 — java-interop peer fields unvalidated onto AST node
`resolveClass()` (`java-interop.ts:1121-1260`) still copies `fields`, `methods`, `constructors`, `isDeprecated`, parameter names/types straight onto the `JavaClass` node with only `??= []` defaulting for missing arrays (added for a different issue, P61-D2-003) — no length bound, no schema check. The hand-built method-signature string (`:1227-1233`) still interpolates `javaTypeAdjust(p.type)`/`realName`/`method.returnType` with zero escaping. Fix statement: `resolveClass()` truncates/rejects a field whose string length exceeds a fixed bound and escapes Markdown control characters before it reaches `docu`/`documentation`.

### #524 — hover/completion render javadoc unescaped
`bbj-hover.ts`'s `tryParseJavaDoc` (`:168-178`) returns either `doc.toMarkdown()` (a JSDoc library's own output) or the raw comment text verbatim; nothing strips `[`, `]`, `(`, `)`, backtick, or `!`. `bbj-completion-provider.ts`'s `createReferenceCompletionItem` (`:800-821`) builds `{ kind: 'markdown', value: parts.join(...) }` directly from `node.docu.javadoc`/`node.docu.signature`, same as reported. Fix statement: a shared `escapeMarkdown()` helper applied to `javadoc`/`signature` text before either site constructs `MarkupContent`.

### #525 — quick-fix/auto-import insert unvalidated fqn
`createUseAction` (`bbj-code-action-provider.ts:82-95`) builds `TextEdit.insert(..., \`use ${fqn}\n\`)` directly from a `fqn` sourced from `resolveClassCandidatesBySimpleName`, itself fed by peer-supplied class names — no format check. `completeAutoImportClasses` (`bbj-completion-provider.ts:157-172`) does the same via `additionalTextEdits`. Fix statement: both sites reject (or the shared candidate-producing helper filters out) any `fqn` that doesn't match `^[A-Za-z_$][A-Za-z0-9_$]*(\.[A-Za-z_$][A-Za-z0-9_$]*)*$` before it reaches a `TextEdit`.

### #526 — USE-statement path traversal outside PREFIX root
`addImportedBBjDocuments` (`bbj-document-builder.ts:1114-1120`) still does `URI.file(resolve(prefixPath, importPath))` then `fsProvider.readFile(prefixedPath)` (`:1119`) with no check that the resolved path stays under `prefixPath`. The identical unguarded pattern exists in the scope resolver, `bbj-scope.ts:334-338` (`prefixes.map(prefixPath => URI.file(resolve(prefixPath, bbjFilePath)))`), used for the class index lookup path (lower severity there, since it only affects which files are searched for symbols, but the same traversal semantics apply). Fix statement: `addImportedBBjDocuments` computes `path.relative(prefixPath, resolved)` and rejects (skips this prefix) whenever the result starts with `..` or is absolute, before calling `readFile`.

### #529 — EM token/password via exec() argv — FIXED
The whole exec surface was rewritten (comment block cites `GHSA-p5f3-9456-9pcx`, CWE-78) into `process-args.ts` (pure `{file, args, env}` builders) + `process-runner.ts` (`execFile`, never a shell). `buildEmValidateArgv`/`buildEmLoginArgv` put username/password/token exclusively on the `env` map under `EM_ENV_VARS`, never in `args` (`process-args.ts:250-283`). `formatArgvForLog` (`process-runner.ts:96-100`) masks by exact array-element match against the `secrets` list, not substring — a double-quote inside a token/password can no longer defeat it, since there is no longer a substring-replace at all. No remaining work.

### #546 — web.bbj default admin/admin123 fallback — STILL-OPEN
`web.bbj:34-35` is unchanged: `if (username! = null() or username! = "") username! = "admin"` / `if (password! = null() or password! = "") password! = "admin123"`, immediately followed by `BBjAdminFactory.getBBjAdmin(username!, password!, err=login_failed)` at `:36`. Fix statement: delete both fallback assignments; when both `username!`/`password!` are empty and no token was supplied, jump straight to `login_failed:` instead of attempting an admin/admin123 login.

### #548 — six post-login EM calls with no err= handler — STILL-OPEN
Confirmed by exhaustive grep of `web.bbj`: the only `err=` occurrences remaining are the 5 `ARGV`/`CLIENTENV`/`ENV` reads and the 2 `getBBjAdmin(...)` calls. `getRemoteConfiguration()`, `createApplication()`, `getConfigFileName()`, `commit()`, `getDwcUrl`/`getBuiUrl`, and `browse()` still carry none. Fix statement: each of the six gains its own `err=<label>` with a distinct `MSGBOX` message naming that specific failure, rather than the current silent no-op.

### #553 — EM token expiry check fails open — STILL-OPEN
`extension.ts:411-439`'s `isTokenExpired()` is unchanged in logic (only line numbers drifted, 339→411): non-3-part token, exp-less payload, and decode-throw all still `return false` (treated as "not expired"). Fix statement: change the three branches at `:416`, `:429`, `:437` to `return true`, matching the fix already applied on the IntelliJ side.

### #566 — shell-string exec() vs IntelliJ argument-array — FIXED
Same rewrite as #529 covers this. `Commands.cjs` and `extension.ts` no longer build shell command strings; every launch site (`bbj.run`/`runBUI`/`runDWC`/`compile`, EM validate/login) goes through `process-args.ts` builders + `process-runner.ts`'s `execFile`. Pre-flight validation now exists and is *stronger* than IntelliJ's: `bbj-home-layout.ts`'s `resolveBbjBinary`/`confineBbjExecutable` checks `bbj.home` is absolute, exists, contains executable `bin/bbjcpl` and `bin/bbj`, and a `cfg` directory, before any executable path is handed to `execFile` (`process-runner.ts:34-42`, called from both `runProcess` and `runProcessCallback`). No remaining work.

### #579 — isExternalDocument() bare string-prefix comparison — STILL-OPEN
`bbj-ws-manager.ts:273-283` unchanged, including the original `// TODO check that document is part of the workspace folders` comment on line 276. Still a raw `documentUri.fsPath.startsWith(URI.file(prefix).fsPath)`. Fix statement: compare `documentUri.fsPath.startsWith(prefixFsPath + path.sep) || documentUri.fsPath === prefixFsPath` instead of a bare `startsWith`.

### #585 — isTokenizedFile/statSize no symlink/file-type check — STILL-OPEN
`decompile-io.ts:16-41` unchanged: `fs.promises.open`/`fs.promises.stat` called directly with no `lstat` pre-check. Still true that no current caller passes an attacker-influenced path (this remains a defense-in-depth gap, not a live exploit). Fix statement: `fs.promises.lstat(file)` first; reject (return `false`/`undefined`) if the entry is a symlink, directory, or other non-regular file.

### #586 — cached Node.js binary integrity — FIXED
`BbjNodeDownloader.getCachedNodePath()` now delegates to `NodeInstallPipeline.cachedNodePath()`, which re-verifies the installed executable's digest recorded at download time (`NodeInstallPipeline.java:109,158-187,303`, via `NodeInstallIntegrity`) before returning the path — an absent or mismatched digest record is treated as "not cached," forcing re-download/re-verify. No remaining work.

### #604 — composer webviews: no runtime shape validation — STILL-OPEN
`webview-panel-lifecycle.ts`'s `registerPanelMessageHandler<T>` (`:16-23`) types the handler purely via a TS generic; `panel.webview.onDidReceiveMessage(handler)` passes whatever arrives straight through, with no `typeof`/shape check anywhere before `build(msg.payload)` in any of the four composer webview files. As before, none of the four `getHtml()` templates currently interpolates attacker-reachable content, so this remains a defense-in-depth gap rather than a live injection. Fix statement: add a `isValidXPayload(msg): msg is {type: string; payload: Selection}` predicate call before dispatch in each of the four handlers (or once, centrally, in `registerPanelMessageHandler`).

### #605 — formatter resolves `java` via bare PATH lookup — STILL-OPEN
`document-formatter.ts:144` still does `cp.spawn('java', formatFlags)` — an unqualified executable name resolved via the extension host's PATH, with no `bbj.javaHome`-equivalent setting anywhere in the codebase (checked: no `javaHome` string appears in `package.json` or `document-formatter.ts`). Fix statement: add an optional `bbj.javaHome` VS Code setting; when set, `document-formatter.ts` spawns `${javaHome}/bin/java${exeSuffix}` instead of the bare `'java'` PATH lookup, defaulting to today's behavior when unset.

### #626 — addWindow/addChildWindow/msgbox assignTo validation — PARTLY-FIXED
`addwindow-composer.ts`'s `addwindowPreview` and `addchildwindow-composer.ts`'s `addchildwindowPreview` now validate every free-text field (`receiver`, `sysgui`/`window`, `title`, `x`/`y`/`width`/`height`, `id`, `context`) via `validateBbjExpression`/`validateStringField`/`validateNumericField`, and fold every result into the returned `valid` flag (`addwindow-composer.ts:288-340`, `addchildwindow-composer.ts:196-258`) — this closes the majority of the original finding. The one field still exactly as reported: `msgbox-composer.ts`'s own `assignTo` (`:145`) is used unchecked in `composeStatement` (`:162`) and is not part of `msgboxPreview`'s `valid` computation (`:420`, which is `msgV.ok && titleV.ok && customOk` — no `assignTo` term). Fix statement: `msgboxPreview` runs `input.assignTo` through `validateStringField`-style validation (a BBj variable/identifier pattern, since it's an assignment target, not a general string) and ANDs the result into `valid`.

### #676 / #698 — "java.io/java.net has no container" log + crash
The crash itself — `Error: The service registry contains no services for the extension ''`, reported by the user opening an extensionless PREFIX-resolved USE target — is fixed by the merged PR #698, via `bbj-service-registry.ts`'s `BBjServiceRegistry` registering each USE-resolved file's own URI so Langium always has a service group for it, regardless of extension. Verified present in the current tree.

The **separate** log line the user also saw, `Java class java.io has no container, packageName: java`, originates at `java-interop.ts:1155-1158` inside `resolveClass()`:
```
if (javaClass.$container === undefined) {
    console.error(`Java class ${className} has no container, packageName: ${javaClass.packageName}`);
    javaClass.$container = this.classpath; // fallback to classpath
}
```
This fires whenever `storeJavaClass()` (`:1307-1364`) does *not* assign `$container` — which happens when the computed insertion key (the last segment of `packageName.split('.').concat(simpleName)`) already exists in `childrenOfByName` as something *other* than a fresh class slot (e.g. an already-registered `JavaPackage` node at that same path). For `className = "java.io"`, `extractPackageName` (`:1509-1519`) returns `"java"` (no dot immediately followed by an uppercase letter), so `storeJavaClass` treats `"io"` as a *class* named `io` under package `java` — but if a `JavaPackage` node named `io` was already registered under `java` from earlier real `java.io.*` class resolutions, the `children.has('io')` check short-circuits and `$container` is left unset. This is a name/kind collision in the `childrenOfByName` map (a package vs. a same-named "class"), not a crash: the very next line supplies a fallback container (`this.classpath`), so no exception propagates from this path — it is independent of, and not fixed by, #698. **It can still occur** whenever the interop backend or a scope-resolution path passes a bare package-shaped string (`"java.io"`, `"java.net"`) into `resolveClass()` as if it were a class name. Given time constraints this research did not trace the exact caller that requests `"java.io"`/`"java.net"` as a "class" (most likely a `use java.io`/`use java.net` bare-package import, or `autoImportCandidatePackages` probing, in a project that has some form of package-level reference); a full fix needs that call site identified so the request is either skipped or answered without going through `resolveClass`'s class-shaped path. Fix statement: downgrade the log to `logger.debug`/`logger.warn` (it is now proven non-fatal) and/or trace+special-case whichever caller passes a bare package name into `resolveClass`.

## Grouping suggestion for phase planning

- **Java-interop network/config trust boundary** (#509, #510, #511): all three touch `setConnectionConfig`/`resolveConfigPath` and the two call sites that feed it — one phase, one shared fix in `java-interop.ts` plus a Workspace-Trust decision for `configPath`.
- **Java-interop peer-response rendering** (#523, #524): both are "unescaped/unvalidated peer data reaches IDE UI" — one phase touching `java-interop.ts` (bound/validate at the source) and `bbj-hover.ts`/`bbj-completion-provider.ts` (escape at render time). A shared `escapeMarkdown`/`boundString` helper serves both.
- **Unvalidated fqn / path insertion into user content** (#525, #526): both are "untrusted string reaches a `TextEdit`/`readFile` with no format/containment check" — #525 in `bbj-code-action-provider.ts`/`bbj-completion-provider.ts`, #526 in `bbj-document-builder.ts`/`bbj-scope.ts`. Different files but same "validate before write/read" shape; can share a phase or a reviewer pass.
- **web.bbj EM auth hardening** (#546, #548): same file, same login flow — one phase, sequential edits (kill the fallback, then add the six `err=` branches) since #548's err= additions are easiest to review right after #546's control-flow change.
- **VS Code EM token trust** (#553): stands alone (pure function, `extension.ts`), trivial one-line-per-branch fix — good "quick win" filler in whichever phase touches `extension.ts` for #529/#566 follow-up work (already fixed) or #546/#548.
- **Composer webview field validation** (#604, #626): both are "webview/composer input reaches a document write with insufficient validation." #626 is a small mechanical finish (port the already-proven `validateStringField` pattern to `assignTo`); #604 is the more speculative defense-in-depth item. Can share a phase touching `msgbox-composer.ts` and `webview-panel-lifecycle.ts`.
- **Standalone / low-priority hardening**: #579 (`bbj-ws-manager.ts`, one-line `startsWith` fix), #585 (`decompile-io.ts`, `lstat` add), #605 (`document-formatter.ts`, new setting). None share a file with each other; each is small enough to fold into whatever phase has spare capacity, or batch as one "small hardening" phase since they're all S-sized and low severity.
- **#676's log-line remainder**: fold into whichever phase next touches `java-interop.ts` (pairs naturally with the #509/#510/#511 or #523/#524 phases) — cheap (downgrade log level) but the root-cause trace is a distinct, non-trivial side investigation if the full fix is wanted.
