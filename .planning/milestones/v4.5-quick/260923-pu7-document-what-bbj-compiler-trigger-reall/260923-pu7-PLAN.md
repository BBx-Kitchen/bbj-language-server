## Verified facts (planner checked these against the code on 2026-09-23; write docs from these, not from the task description)

Real delay:
- The delay is **500 ms**, fixed: `private static readonly SAVE_DEBOUNCE_MS = 500;`
  (bbj-document-builder.ts:107), used as the `setTimeout` delay in `debouncedCompile`
  (bbj-document-builder.ts:481 and :596). It is a per-file trailing-edge timer: every new event
  resets it (:478-479). There is **no setting** for it; nothing reads a delay from configuration.
- The old package.json text "(2s)" (package.json:608) is wrong. It traces back to the original
  phase-53 design note ("errors appear as you type after a 2-second pause"), which the
  implementation never adopted (the 500 ms constant has been there since the first wiring commit
  26bcdfcf).

What re-arms the 500 ms timer (for every mode except `off`):
- Every open and every content change of an open document, straight from the text-document events
  (constructor listeners, bbj-document-builder.ts:143-147 -> `armLiveParseFromEvent` :321-337 ->
  `armLiveParseForDocument` :381-388).
- Every Langium rebuild of an open document (`buildDocuments` :232 -> `runBbjcplForDocuments`
  :278-285). In VS Code a save produces such a rebuild through the `**/*.bbj` file watcher
  (extension.ts:1075 and :1094 -> Langium didChangeWatchedFiles -> update). For IntelliJ the
  save-driven rebuild depends on LSP4IJ file-watch registration and was NOT verified, so do not
  claim "after saving" in the IntelliJ docs.

What a cycle does when the timer fires (`debouncedCompile`, :476-599):
- First the live parse: the current, possibly unsaved text is sent to BBjServices' parser
  (`bbjParserService.requestLiveParse`, :498-500; needs BBj 26.03+ with BBjServices running).
  With a verdict for the current text, bbjcpl does NOT run this cycle (:505-537).
- Only if the live parse is unavailable or failed does it fall back to bbjcpl (:570-571), which
  compiles the **file on disk** (`key = document.uri.fsPath`, :477; bbj-cpl-service.ts:161 spawns
  `bbjcpl -N <path>`). So with an older BBj (or BBjServices down) bbjcpl runs after every typing
  pause too, and its results reflect the last saved version of the file.
- Both halves require the bbjcpl binary under `<bbj.home>/bin` (checked once per session,
  :642-665); if it is missing, neither the live parse nor bbjcpl runs (:384-385, :280). Record
  only; the docs do not need to cover this.

Per value:
- `debounced` (default; bbj-document-validator.ts:53): as above.
- `on-save`: **identical to `debounced`**. The only trigger check anywhere in the language server
  is `=== 'off'` / `!== 'off'` (bbj-document-builder.ts:259, :323, :357;
  bbj-document-validator.ts:251). `on-save` is only accepted as a valid value (main.ts:227,
  bbj-ws-manager.ts:109). This has been the case since phase 53 (53-02-SUMMARY: "distinction is
  preserved in the enum for future use but both trigger the same debouncedCompile() path").
  **Discrepancy with the task description:** it said on-save "still runs the live parse while
  typing and only defers bbjcpl to save". That is wrong: bbjcpl (the fallback) is NOT deferred to
  save; it runs after typing pauses exactly as in `debounced`. The old package.json text
  ("runs on file save only") is wrong too.
- `off`: disables both the live parse and bbjcpl. The event path returns early (:323; deferred
  path re-checks at :357); the rebuild path clears all verdict state, strips compiler-sourced
  (`BBjCPL` and live-parser) diagnostics from rebuilt documents and schedules nothing (:259-276);
  validation skips verdict composition (bbj-document-validator.ts:251). Compiler diagnostics
  already on screen go away at the next rebuild of that file (next edit or save). The language
  server's own diagnostics (syntax, references, and so on) are unaffected and keep running as you
  type. The explicit "Compile BBj Program" command (package.json:139-140) does not read the
  trigger (compile-command.ts has no `getCompilerTrigger` reference) and still works.
- In VS Code, changing the setting takes effect immediately without a restart: the client pushes
  the `bbj` section (extension.ts:1095) and main.ts:224-230 applies it on
  `onDidChangeConfiguration`; the initial value arrives via `initializationOptions.compilerTrigger`
  (extension.ts:1107 -> bbj-ws-manager.ts:107-114).

IntelliJ:
- IntelliJ does **not** expose this setting at all. `BbjSettings.State` has no trigger field
  (BbjSettings.java:25-36); the settings page's "BBj Compiler" group holds only "Compile output
  directory" (BbjSettingsComponent.java:295-296); `initializationOptions` sends home, classpath,
  javaInteropHost, javaInteropPort, configPath and compilerOutputDirectory only
  (BbjLanguageServerFactory.java:43-61); `createSettings()` sends home, classpath and logLevel only
  (BbjLanguageClient.java:32-39), and LSP4IJ's `workspace/configuration` pull for section "bbj"
  resolves to null (CompilerInitOptions.java:6-14). The server therefore falls back to
  `setCompilerTrigger('debounced')` (bbj-ws-manager.ts:113) on every IntelliJ start.
- **Discrepancy:** the current IntelliJ features.md says "This follows the existing
  `bbj.compiler.trigger` setting: setting it to `off` turns live compiler diagnostics off...".
  An IntelliJ user cannot do that. The `off` workaround is VS Code-only today.

Tests: no test asserts the setting's description or enum text (only a comment mention in
test/functional/installed-extension-e2e.test.ts:389). No test guards the two comments touched in
Task 1. Nothing else in package.json uses `enumDescriptions` yet; it is a standard VS Code
configuration key.
