<objective>
Make the endpoint safe to leave running. One daemon worker thread per connection serializes that
connection's parses (D-13), a newer request for the same document supersedes an older one with
lsp4j's standard cancellation code (D-11), every failure mode travels as a JSON-RPC error with a
fixed application code rather than as a fake syntax error (D-12), a per-parse timeout and a
document size cap bound the work and are both overridable by system property (D-14), and a closed
connection takes its worker down with it.

Two facts settle the design rather than leaving it to taste. First, the program factory and its
type resolver are backed by plain, unsynchronised hash maps, so two concurrent parses on one
connection are a real corruption risk, not a theoretical one — the single worker thread is
required, not cautious. Second, nothing in BBj's parse path checks the interrupt flag, so a
timeout can only make the *caller* stop waiting; the parse keeps running. This plan therefore
makes the size cap the load-bearing guard and, on a timeout, keeps the connection's one worker and
fails further requests fast until the abandoned parse ends — a second worker thread would need a
second factory, and a second factory reintroduces the stale-AST-cache hazard plan 02 exists to
avoid.

Purpose: bound the endpoint's resource use and make its failure surface structural.
Output: a worker with a latest-wins queue, five application error codes, two system properties, a
unit test for the guards, and a connection-close teardown hook.
</objective>

    Latest-wins (D-11). Keep a `ConcurrentHashMap` from canonical name to the pending request
    (the params, the caller's `CompletableFuture`, and a started flag). `submit` builds its
    pending record, puts it into the map for `params.canonicalName`, and inspects whatever record
    it displaced:
    - a displaced record that had not started is completed exceptionally, immediately, with a
      `ResponseErrorException` carrying `ResponseErrorCode.RequestCancelled` and a short message
      saying a newer request for the same document superseded it; its queued task, when it later
      reaches the worker thread, sees it is no longer the map's current record and returns without
      parsing at all;
    - a displaced record that had started is left to finish — its parse cannot be stopped — and
      when it finishes it discovers it is no longer current and completes its own caller
      exceptionally with the same RequestCancelled error instead of returning the result it just
      computed. The computed result is dropped.
    The superseded caller therefore never receives an errors list under any interleaving. This
    holds regardless of the version tokens involved: two requests carrying the same `version`
    string and the same `text` are still two requests, each with its own fresh source UUID, and the
    earlier is still superseded. Do not add an equality short-circuit on the token or the text.

    Timeout policy (D-14, and the fact that a timeout cannot stop the parse). The worker owns an
    "overrunning" marker, set when a submitted parse exceeds the timeout and cleared by that same
    parse task when it eventually returns. While the marker is set, `submit` completes the new
    caller's future immediately and exceptionally with the timeout code rather than queueing behind
    a parse of unknown remaining duration. Do not shut the executor down and do not build a second
    worker thread or a second factory on timeout: the abandoned thread still owns the connection's
    only factory, which is not thread-safe, and a replacement factory would start with an empty

    reasoning in prose Javadoc on the marker.
