<objective>
Make every non-verdict outcome behave exactly as the user decided, and prove the older-server path
is the 0.16.x path to the byte.

Plan 01 wired the verdict path and left every other outcome on the save-time compile. This plan
makes them precise: a failed cycle falls back to `bbjcpl` and puts Langium's errors back (D-02,
D-03); a cancelled or stale answer does nothing; an unavailable endpoint, a new connection and the
trigger set to `off` forget every verdict; the USE revalidation keeps the remembered list honest.
Then an exact-equality regression test against the old-server double pins "unchanged" as a
computed equality rather than a description.

Purpose: success criterion 3 — the suppression is conditional on live diagnostics being on, never a
permanent removal of checks — is the one change in this milestone that can make diagnostics worse
for users on an older BBj.
Output: the outcome handling and lifecycle clears in `bbj-document-builder.ts`, a generation-reset
clear in `bbj-parser-service.ts`, and tests in the two existing builder suites.

<decisions_resolved_here>
- **Cancelled** (research open question 1): no fallback, no verdict update, no reconciliation —
  Phase 102's treatment. The cycle still ends with its single publish, as today.
- **Stale verdict:** D-03 says only a verdict for the current text may downgrade or replace. The
  builder compares the document's text version before and after the request; a changed version is
  treated like a cancellation, because the edit that changed it has already scheduled a newer cycle.
- **Connection reset** (Claude's discretion): cleared through the existing generation counter, as
  the research recommended, in addition to per-document clears on every fallback.
</decisions_resolved_here>
</objective>
