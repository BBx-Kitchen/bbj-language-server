<objective>
Prove the reconciliation end to end on its one essential path, then build out the pure functions
that decide everything else.

The tracer: an open document with a Langium parse error, a live endpoint that accepts the text, and
the existing 500 ms debounce. After the callback fires, the parse error is a Warning with its own
message and source, nothing is red, and the save-time `bbjcpl` run never happened. That single path
touches every layer this phase changes — the parser service's outcome, the builder's debounce, a new
pure reconciliation module, and the validator's hierarchy — so an architectural dead end shows up
after one commit.

Then two expansion tasks make the pure layer complete: replace-by-overlap and every edge of
`reconcileWithVerdict`, and the hierarchy rules plus the carry-over function that plans 02 and 03
wire into the builder and the validator.

Purpose: PSRV-06 (one diagnostic per line, no duplicate from `bbjcpl`) and PSRV-07 (no language
server syntax *error* on an accepted document) are decided by one small pure module; everything
else in the phase is wiring and lifecycle.

`requestLiveParse()`, a live-parse-first debounce callback, an exported hierarchy with the D-06

<decisions_resolved_here>
Claude's-discretion items and research open questions, decided so no executor improvises:

1. **Where the reconciliation lives:** a new pure module `bbj-diagnostic-reconciliation.ts` (in the
   style of `mergeDiagnostics`, which stays where it is and stays the latch-off merge). It also owns
   the per-document verdict state and the remembered pre-hierarchy Langium list, as plain
   module-scoped state with exported accessors — the pattern `bbj-document-validator.ts` already uses
   for `compilerTrigger` and `maxErrorsDisplayed`.
2. **`requestLiveParse()`'s return shape:** a discriminated union
   `LiveParseOutcome = { kind: 'verdict'; diagnostics } | { kind: 'failed' } | { kind: 'unavailable' } | { kind: 'cancelled' }`.
   A boolean `verdict` flag (the research's first suggestion) cannot tell a cancellation from a
   failure, and the two must behave differently.
3. **`RequestCancelled` is a no-op for its cycle** — no fallback, no verdict update — matching
   Phase 102's treatment. This plan only classifies it; plan 02 wires the no-op.
4. **The debounce rebuilds from the remembered pre-hierarchy list**, not from `document.diagnostics`:
   the hierarchy already removed linking diagnostics (Rule 1) and warnings (Rule 2) before the
   verdict arrived, and D-05/D-06 need them back once Langium's syntax errors stand down.
5. **Rule 3:** downgraded warnings do not count against the error cap and get their own cap at the
   same `maxErrors` value. Reversible.
6. **Replaced complaints between verdicts:** BBj's own diagnostic disappears on the next keystroke
   (Phase 102 behaviour: Langium resets `document.diagnostics` on every rebuild). D-08 says only
   complaints the last verdict has *not* seen show as errors in the meantime, so a complaint the last
   verdict *replaced* is carried over like a downgraded one — shown as a Warning with Langium's text
   until the next verdict, rather than vanishing or turning red. One `seen` set covers both.
   Reversible.
7. **Rule 0** is dead in both paths (research finding, confirmed by reading every call site). It is
   documented in a doc comment and pinned, not changed.
</decisions_resolved_here>
