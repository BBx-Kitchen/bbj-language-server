<objective>
Make every writer of a document's diagnostics build its list from one consistent snapshot, so the
early verdicts plan 01 enables never lose, double or misplace a diagnostic.

The tracer: an open document still in the startup build gets BBj's verdict first (plan 01's early,
client-only publish); then Langium validates the same text. The list Langium's validation publishes
contains BBj's diagnostic exactly once, Langium's complaint on BBj's line gone and its other
complaint downgraded — the Phase 103 result, reached in the opposite order. That path runs through
every layer this plan changes: the builder's verdict branch storing the full verdict record, the
pure composition from plan 02, the validator's composition, and Langium's own publish.

The expansion tasks move the remaining writer (the bbjcpl fallback) onto the same snapshot, keep
the USE revalidation honest, and pin the interleaving matrix D-12 asks for.

Purpose: RESP-03 (latest text version wins, nothing lost, doubled or misattributed) and the
correctness half of RESP-01.
Output: composition wired into `bbj-document-validator.ts` and `bbj-document-builder.ts`;
`test/live-parse-interleaving.test.ts`.

<decisions_resolved_here>
1. **No per-document queue (D-07):** writers stay concurrent; each derives its whole list from the
   stored inputs at the moment it writes.
2. **The validator includes BBj's diagnostics when the stored verdict is for the live version** —
   previously it only carried decisions over. That is D-04's "the Phase 103 reconciliation runs
   against it then", and it also removes a flicker Phase 103 had: a relink-driven revalidation of
   unchanged text no longer drops BBj's diagnostic until the next cycle.
3. **The validator refreshes the stored verdict's `seen` set** when it reconciles against a current
   verdict, so the next keystroke's carry-over uses keys from Langium's fresh list rather than from
   an early verdict's stale one.
4. **The bbjcpl fallback stays 0.16.x-shaped:** hierarchy on Langium's list, then `mergeDiagnostics`
   with bbjcpl's result, no reconciliation (Phase 103 D-03). Only its input moves: the latest
   remembered Langium list read after the compile resolves. The validator never includes bbjcpl
   diagnostics, exactly as before.
5. **No remembered list at all** (a document Langium never validated this session): the cycle uses
   the document's current list without compiler diagnostics — "whatever Langium last published" in
   D-04's words, empty for a never-validated document.
</decisions_resolved_here>
