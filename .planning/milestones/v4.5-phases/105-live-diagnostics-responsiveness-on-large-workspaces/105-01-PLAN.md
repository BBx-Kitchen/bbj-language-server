<objective>
Take the live-parse cycle out from behind Langium's workspace lock.

The tracer: Langium's real workspace lock is held by a write action that never finishes, standing
in for the startup build of a large workspace. The user edits an open file whose document was
loaded from disk but never built. A change event arrives. 500 ms later the parser has been asked
about the edited text, and BBj's diagnostic has reached the client — while the lock is still held
and the queued rebuild has not run. That one path touches every layer this plan changes: the
text-document event, the new listener, the live-text binding, the existing debounce timer, the
parser service, and the publish.

The expansion task adds the open event, the "workspace not loaded yet" deferral, the gates, the
merge with the rebuild-driven trigger, the bbjcpl fallback in an early cycle, and the quiescence
predicate.

Purpose: RESP-01 and RESP-02. Issue #692's first serialization point is removed here; plan 03
removes the second (the shared socket), plan 04 makes the early publish reconcile correctly against
Langium's own diagnostics across text versions.
Output: the event-armed cycle and the state-aware publish in `bbj-document-builder.ts`, and
`test/live-parse-scheduling.test.ts`.

<decisions_resolved_here>
Claude's-discretion items decided so no executor improvises:

1. **Arm point:** a direct listener on `services.workspace.TextDocuments` (`onDidChangeContent` and
   `onDidOpen`), registered in `BBjDocumentBuilder`'s constructor — not a `DocumentUpdateHandler`
   override (that would have to split its own lock-taking call) and not a builder `update()`
   override (that runs inside the lock). Additive, so the rebuild-driven trigger (D-03) cannot
   regress. Registered only when the provider exposes both events; the core services type has only
   `get`, and several test harnesses construct the builder with such a stub.
2. **Live text (research Pitfall 1):** bind the event's live `TextDocument` onto the
   `LangiumDocument` without re-parsing, with the exact property shape Langium's
   `DefaultLangiumDocumentFactory.update()` uses. This keeps `debouncedCompile(document)` and
   `requestLiveParse(document)` unchanged in signature, keeps the forty-odd existing tests that
   drive `debouncedCompile` directly valid, and puts a never-built document in the same state every
   open document is in after its first build (live text, AST lagging). Re-parsing outside the lock
   was rejected: it mutates the parse result a lock-held build may be reading.
3. **A file the workspace has not loaded yet:** the event is remembered per uri (at most one
   pending entry per uri) and re-armed when `WorkspaceManager.ready` resolves. `ready` resolves
   after the startup file scan, before the build — it is not the lock, so this does not bring the
   wait back (issue #692's own note is about the lock, not `ready`).
4. **Publish path (found while planning, not in the research):** Langium's `waitUntil(state, uri)`
   resolves on any document-phase notification for that uri. Code actions wait for the Validated
   state. An early cycle calling `notifyDocumentPhase(document, Validated)` for a document still in
   the startup build would release those requests against an unlinked document, and writing
   `document.diagnostics` between a build's reset and its validation would make Langium append its
   fresh list onto the cycle's list (`DefaultDocumentBuilder.validate()` pushes when a list
   exists). So: at or above Validated, publish exactly as today; below it, send the list to the
   client through the LSP connection only. Plan 04 relies on this — it is why no `validate()`
   override is needed there.
5. **Quiescence (#486):** no new field. The event path reuses `cplDebounceTimers`, so
   `hasPendingCompile()` already covers a pending event-armed cycle; a test proves it (research
   Pitfall 4).
6. **Parse context this early:** the PREFIX list is read at request time and may still be empty
   while the workspace preamble runs. Accepted: the endpoint does not resolve referenced programs
   under type checking off (Phase 101 override), so the verdict does not depend on it.
</decisions_resolved_here>
