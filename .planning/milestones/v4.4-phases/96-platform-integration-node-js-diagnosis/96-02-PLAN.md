<objective>
Stop re-extracting the TextMate bundle on every launch. `BbjTextMateBundleProvider.getBundles()`
currently calls `Files.createTempDirectory(PathManager.getTempPath(), "textmate-bbj")` and copies all
five bundle files every single time it runs — and RESEARCH established it can run more than once per
session, because the platform's `reloadEnabledBundles()` re-invokes it. Every one of those
directories is then abandoned on the user's disk.

Purpose: ROADMAP criterion 1 — a second IDE launch reuses the cached directory instead of allocating
a fresh one and re-copying, and directories abandoned by earlier launches are cleaned up rather than
accumulating. PLAT-01 was left entirely to Claude's discretion in CONTEXT.md, with three sub-questions
routed to research: the invalidation key, concurrent-launch safety, and whether to sweep. Research
answered the first two and explicitly flagged residual ambiguity on the third, which Task 2 surfaces
as a decision rather than deleting past by default.

Output: a new platform-free `TextMateBundleCache` seam with its own plain-JUnit test class (this file
has no test and no source guard today — 96-VALIDATION.md records it as a Wave 0 gap), a rewritten
provider that is a thin wrapper over it, and a scoped sweep behind an explicit human decision.
</objective>

`BbjTextMateBundleProvider` today (whole file is 49 lines): implements
`org.jetbrains.plugins.textmate.api.TextMateBundleProvider`, whose one method is
`@NotNull List<PluginBundle> getBundles()`. `PluginBundle` is constructed as
`new PluginBundle("BBj", bundleDir)` where `bundleDir` is a `java.nio.file.Path`.

`BUNDLE_RESOURCE_PATH = "textmate/bbj-bundle/"` and `BUNDLE_FILES` is a `List.of` of exactly five
relative paths, two of which carry a `syntaxes/` path segment:
`package.json`, `bbj-language-configuration.json`, `bbx-language-configuration.json`,
`syntaxes/bbj.tmLanguage.json`, `syntaxes/bbx.tmLanguage.json`.
Resources are opened with `getClass().getClassLoader().getResource(BUNDLE_RESOURCE_PATH + file)` and
`Objects.requireNonNull(...)` with the message `"Missing TextMate bundle resource: " + ...`.

Only `package.json` is committed under `bbj-intellij/src/main/resources/textmate/bbj-bundle/`. The
other four are staged at build time by `build.gradle.kts`'s `copyTextMateBundle` task, which copies
them from `bbj-vscode/` into `build/resources/main/textmate/bbj-bundle`, and `processResources`
dependsOn it. All five therefore reach the classloader identically at runtime, and all five can only
change when the plugin artifact changes — which is what makes plugin version the correct
invalidation key.

The stable-directory pattern to mirror exactly, `BbjNodeDownloader.java:149-153`:
```

    Path dataDir = Paths.get(PathManager.getPluginsPath(), "bbj-intellij-data", "nodejs");
    Files.createDirectories(dataDir);
    return dataDir;
}
```
Swap only the leaf subdirectory name to `"textmate"`.

The running plugin's version, obtained the same way `BbjLanguageServer.resolveServerPath()` already
obtains the descriptor (`BbjLanguageServer.java:99-101`), calling `getVersion()` instead of
`getPluginPath()`:
`PluginManager.getInstance().findEnabledPlugin(PluginId.getId("com.basis.bbj"))`.
Handle a null descriptor — in a development/test classloader it can be absent.

`NodeInstallPipeline.deleteRecursively(Path root) throws IOException` is ALREADY `public static`
(96-RESEARCH.md Open Question 2 asked whether it needed widening — it does not). It passes no
file-visit option to `Files.walkFileTree`, so a symlink inside the tree is deleted as a link and its

method, never re-implement it.

`NodeInstallIntegrity`'s defensive-read idiom, the model for the marker read: a read that catches
`IOException | RuntimeException` and returns false, meaning "not cached" — never "fail" and never
"trust anyway".
