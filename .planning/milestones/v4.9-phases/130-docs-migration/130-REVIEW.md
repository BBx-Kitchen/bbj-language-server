## Warnings

### WR-01: IntelliJ docs claim Reformat Code is in the editor context menu

**File:** `documentation/docs/intellij/formatting.md:16`
**Issue:** "Choose **Code > Reformat Code**, or use **Reformat Code** in the editor context menu."
The plugin registers no such entry (`plugin.xml` adds only the composers, Run/Compile and
`bbj.denumber` to `EditorPopupMenu`), and IntelliJ's stock editor popup does not carry Reformat Code
(it is in the Code menu, with Ctrl+Alt+L, and in the Project view popup). A reader following the
guide will not find the item. The QA rows correctly use only `Code > Reformat Code`, so the guide and
the checklist disagree.
**Fix:** Drop the context-menu clause and name the real entry points:
```markdown
Choose **Code > Reformat Code** (`Ctrl+Alt+L` on Windows and Linux, `Cmd+Option+L` on macOS).
```
Verify the shortcut against the default keymap before adding it, or omit it.

### WR-02: Message tables say "try again" but omit that repeats are silent

**File:** `documentation/docs/vscode/formatting.md:79-84`, `documentation/docs/intellij/formatting.md:102-107`
**Issue:** Only the "requires BBj 26.03" row says "Shown once per connection". In
`bbj-format-service.ts` (`report`, `environmentNotice`, `contentNotice`, `notice`) the timeout,
engine-failed and service-unavailable messages are also shown once per connection, the too-large and
protected messages once per document version, and the invalid-settings message once per settings
revision; repeats are only logged. The tables tell the user "Try again" for the timeout and
engine-failure rows, but a second timeout in the same session produces no message at all, so the
guide sets an expectation the product does not meet. The always-shown cases (the line-numbers offer,
the selection message, every Denumber message) are the only ones that repeat.
**Fix:** Add a short note under "Formatting messages" in both guides, for example:
```markdown
Formatting messages are shown once and not repeated: the timeout, formatter-failed and
service-unavailable messages once per connection (restart the language server to see them again), the
too-large and protected messages once per file version, and the invalid-settings message until you
change a setting. A later format that fails the same way changes nothing and shows no message; the
`BBj` output channel (`BBj Language Server` console in IntelliJ) still logs it. The line-numbers offer
and all Denumber messages are shown every time.
```

### WR-03: QA rows with unnamed files and an unmentioned open prompt

**File:** `QA/FULL-TEST-CHECKLIST.md:57` (VS Code row 31 step 3), `QA/FULL-TEST-CHECKLIST.md:62` (VS Code row 36 step 1), `QA/SMOKE-TEST-CHECKLIST.md:39` (smoke row 12), `QA/FULL-TEST-CHECKLIST.md:111` (IntelliJ row 40 step 1)
**Issue:** Two executability gaps.
1. Row 31 step 3 ("Create a file holding ... and save it twice"), row 36 step 1 and IntelliJ row 40
   step 1 ("Open a file holding ...") give no file name. Format and Denumber only act on documents
   whose language id is `bbj` (`bbj-formatting-handler.ts`, `bbj-denum-service.ts`), so a file saved
   without a `.bbj` extension yields no offer and the row fails for the wrong reason. The sibling rows
   (32, 33, 37) do name a `.bbj` file.
2. In VS Code, saving a new three-line numbered `.bbj` file (row 31 step 3, smoke row 12) or opening
   one (row 36) makes it the active editor, and `maybePromptLineNumbered` shows the prompt
   `"<name>" is a line-numbered BBj program. Denumber it for editing, or open it read-only?` (the
   `bbj.denumber.promptOnOpen` default is true). None of those rows mention it, and its `Denumber`
   button sits next to the `Denumber` button of the offer the row asks the tester to click, so the
   expected results ("each save shows the line-numbered offer", "the warning offers `Denumber` and
   `Denumber and Format`") are accompanied by a second, undocumented notification.
**Fix:** Name the files (for example `numbered.bbj`) in rows 31, 36 and IntelliJ row 40, and either
add "set `bbj.denumber.promptOnOpen` to false first" to those VS Code steps or add one sentence to the
expected result: "A line-numbered-program prompt (`Denumber` / `Open Read-only`) may also appear;
ignore it."

## Info

### IN-01: Two QA rows leave a repository example file reformatted

**File:** `QA/FULL-TEST-CHECKLIST.md:60` (VS Code row 34), `QA/FULL-TEST-CHECKLIST.md:110` (IntelliJ row 39)
**Issue:** Both rows remove an indent in `examples/bbj-classes.bbj`, end with a successful format that
re-indents the whole file (the file is 4-space indented; the default is 2), and never restore it.
Rows 31 and 36 do say "restore ... (Undo or git)". A tester can commit the reformatted example by
accident, and later rows that reopen the file no longer start from the original.
**Fix:** Append "Restore `examples/bbj-classes.bbj` (Undo or git)" to the last step of both rows.

### IN-02: changeNotes carry no version and replace the whole history

**File:** `bbj-intellij/build.gradle.kts:65-74`
**Issue:** The previous notes were headed `0.1.0 - Initial Release`; the replacement heading is
`Formatting and Denumber for BBj files`, with no version. The HTML is well formed, but the Marketplace
shows `changeNotes` as the notes of the current build, so the text is correct only until the next
release changes the plugin and nobody edits this block. The `version` defaults to `0.1.0` and is
supplied by the build, so a heading that follows `project.version` would stay accurate.
**Fix:** Either interpolate the version (`<h3>${project.version} - Formatting and Denumber</h3>`,
keeping the `$` out of the rest of the raw string) or keep a short version-headed list and prepend the
new entry instead of replacing the old one.

### IN-03: Deprecated-key row omits that only boolean values are moved

**File:** `documentation/docs/vscode/configuration.md:292`
**Issue:** "A value set here is moved to the new name once per scope ..." In `settings-migration.ts`
(`migrateScope`) only a `boolean` old value is moved; a string or number under
`bbj.formatter.splitSingleLineIF` is left in place. Because the new key always has a declared default,
the language server's legacy fallback never fires for it either, so such a value is silently ignored.
The schema types the old key as `boolean | null`, so this is an edge case, but the sentence is
broader than the behaviour.
**Fix:** Write "A boolean value set here is moved ...".

### IN-04: IntelliJ Actions on Save statements are not backed by the code

**File:** `documentation/docs/intellij/formatting.md:30,33`
**Issue:** "Both the whole-file and the changed-lines choice work with BBj files" and "IntelliJ saves
the text you typed, formats it, and saves a second time, so nothing is lost" describe platform
behaviour that nothing in this repository exercises, and QA IntelliJ row 36 only tests the default
choice. If either is wrong the guide misleads. IntelliJ's changed-lines mode formats only VCS-changed
ranges and silently does nothing in a file outside version control.
**Fix:** Either add a QA step for the changed-lines choice and for a file outside VCS, or soften both
sentences to what row 36 verifies ("turn on Reformat code; BBj files are formatted when you save").
