<objective>
Fix the in-place "Decompile & Replace" that failed in the phase 127 hand check (127-06 step 15,
backlog 999.1) in the existing VS Code client path, per D-01. Root cause (research Answer 1,
reproduced on BBj 26.03): `bbjlst -l <file>` writes its listing to the input name with the
extension removed (`prog.bbj` -> `prog`), and only appends `.lst` for an extensionless input, so
the extension waited 20 s for a `<input>.lst` that never came and left (or overwrote) a stray
sibling file. The fix runs `bbjlst -l [-xlst for .lst] -d<private temp dir> <file>`: with `-d`
the listing has exactly the input's file name inside that directory, for every extension
(verified again during planning, including `-xlst -d` on a `.lst` input and paths with spaces).

Also closes the decompile half of D-14: IN-01 (the constant "in place" flag, the second tokenized
check and the file-name alias disappear with the old flow), IN-02 (the temp dir is removed on every
failure path) and the decompile part of IN-04 (structural source guards and the free-text
"denumber" grep replaced by behavioural or narrowly targeted checks).

Purpose: a user who opens a tokenized program and picks Decompile & Replace gets editable source in
place within seconds, and no file next to it is created or clobbered.
Output: reworked `buildDecompileArgv`, decompile flow in `Commands.cjs`, new listing helpers in
`decompile-io.ts`, a fake bbjlst in the tests that models the real `-d` naming, and a real-bbjlst
smoke test.

Out of scope here (later plans): symlink resolution and honest I/O-error messages (plan 02), the
open prompt (plan 02), IntelliJ (plan 07). Decompile is not moved into bbj-ls (deferred).
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-130.1-01 | Tampering / EoP | buildDecompileArgv -> runProcess | high | mitigate | argv array, one element per value, file name last, `-d` value built only from an `fs.mkdtemp` path; launch only through `runProcess` (execFile, no shell, `confineBbjExecutable`); argv-injection tests cover metacharacters and spaces in both the file and the directory |
| T-130.1-02 | Tampering | bbjlst implicit output naming | high | mitigate | output only ever goes to a fresh private directory, never next to user files; real-bbjlst test asserts a pre-existing sibling is byte-identical and no extra file appears |
| T-130.1-03 | Tampering / DoS | replace of the user's program | medium | mitigate | staged copy in the target's own directory created with `COPYFILE_EXCL`, permission bits copied, atomic `rename`; staged file removed on failure; target never written in place |
| T-130.1-04 | Spoofing | success detection | medium | mitigate | bbjlst exits 0 on failure, so success requires the exact listing path to exist, be non-empty, settle in size and not start with the tokenized magic; listing read via lstat-based `statSize` (a planted symlink counts as absent) |
