## Summary

**Backlog 999.1 root cause (D-01) is not an in-place vs `.lst` ambiguity; it is bbjlst's output naming.** Run against the installed BBj 26.03 (`/opt/bbx/bin/bbjlst`), `bbjlst -l <file>` writes its listing to the input name with the *extension removed* (`prog.bbj` -> `prog`, `prog.pub` -> `prog`), appends `.lst` only for an extensionless input (`noext` -> `noext.lst`), and rewrites in place only for `-xlst` on a `.lst` input. The extension's `waitForDecompileOutput` only recognises `<input>.lst` or an in-place rewrite, so for every tokenized program that has an extension (`.bbj`, `.src`, `.pub`, `.bbjt`) it polls for 20 s and fails with "Timed out waiting for bbjlst…", while a stray extensionless sibling file has already been written next to the original (and silently overwrote a pre-existing sibling of that name in my test). The read-only path has the same defect. The unit tests hid it because `fakeBbjlstWrites` always writes `<lastArg>.lst`. The fix is to stop depending on bbjlst's implicit naming: run `bbjlst -l -d<private-temp-dir> <input>`; with `-d` and no `-x` the output has exactly the input's base name in that directory, for any extension.

The rest of the phase is mostly wiring around that: one realpath-based probe shared by the open prompt, the decompile commands and Denumber (D-02..D-04); a text-prefix gate in the LS for tokenized and line-numbered documents that must cover three diagnostic publishers, not only `validateDocument` (D-07..D-09); an `onDidChangeConfiguration` re-run of the existing idempotent migration (D-10/D-11); a `version` field on `bbj/denumDiagnostics` whose value must be the *post-edit* version as the server mirror sees it (D-16); and an IntelliJ banner provider that must bypass `BbjNotificationProviderBase`'s file-type guard if extensionless/`.pub` programs are to get it (D-06). Several statements in CONTEXT.md need correcting (see Answers 3, 5, 6): `bbj-document-builder.ts:1139` skips tokenized files only when loading PREFIX `USE` targets (not in the workspace scan), and IntelliJ does not place problems at all (it only logs the list), so D-16 on IntelliJ is "accept and ignore the field".

**Primary recommendation:** Replace the implicit-naming bbjlst flow with `bbjlst -l -d<private tmp dir> <realpath>` + "output exists and is no longer tokenized" + atomic same-directory replace, behind one `probeTokenizedFile` (realpath, lstat, O_NOFOLLOW, fstat, discriminated result) used by prompt, commands and Denumber; build the LS gate on a single shared tokenized-prefix constant and gate `validateDocument`, `shouldCompileWithBbjcpl` and the debounce callback together.

### Answer 1: Root cause of 999.1 (D-01) [VERIFIED: bbjlst 26.03 run in /opt/bbx this session]

Trace (current code): `open-file-prompts.ts:57-74` -> `Commands.decompileReplace(uri)` (`Commands.cjs:432-436`) -> `decompileInPlace` (`Commands.cjs:200-248`): `buildDecompileArgv` (`process-args.ts:221-229`: `['-l']`, plus `'-xlst'` for `.lst`, then the file) -> `deleteLeftoverLst` -> `execWithProgress(argv)` -> `waitForDecompileOutput(resolvedFileName, { canRewriteInPlace: wasTokenized })` (`decompile-io.ts:128-150`) -> `rename(<input>.lst, <input>)` (`Commands.cjs:235`).

`waitForDecompileOutput` returns only for (a) `<input>.lst` exists and its size settles, or (b) no `.lst` and the input is no longer tokenized. Experiment (BBj 26.03 is what `/opt/bbx/readme.htm`/`relnotes.htm` report, the version of the failed hand check). A tokenized sample was made with `bbjcpl -d<dir> src.bbj`; header bytes `<<bbj>>`.

| Input name | argv used by the extension | What bbjlst produced | extension logic |
|---|---|---|---|
| `prog.bbj` | `-l prog.bbj` | new file `prog` (no extension), input untouched, no `.lst` | times out after 20 s |
| `prog.pub` | `-l prog.pub` | `prog` | times out |
| `prog.bbj.lst` / `prog.lst` | `-l -xlst prog.lst` | input rewritten in place (it is the output name) | works |
| `noext` | `-l noext` | `noext.lst` | works (rename) |
| `prog.bbj` with `-xlst` | | `prog.lst` | not what the code looks for (`prog.bbj.lst`) |
| `prog.bbj` with `-l -d<existing dir>` (no `-x`) | | `<dir>/prog.bbj`, same base name, listing text, input untouched | deterministic |
| `.lst` input with `-l -d<dir>` | | `<dir>/prog.lst` | deterministic |

Documented rule: "If a source file name has no extension, the corresponding output filename will have an extension of '.lst'", "If a source file name has an extension, the corresponding output filename will have no extension", `-x<ext>` appends the extension, and with `-d<directory>` "the listing files have exactly the same names as the source files but are in a different directory" [CITED: https://documentation.basis.cloud/BASISHelp/WebHelp/util/bbjlst_bbj_lister.htm]. The extension's `<input>.lst` assumption therefore only ever matched extensionless inputs.

Further facts from the same session, all relevant to the fix:
- **Sibling clobber (the "not safe" in 999.1):** with a pre-existing `prog` next to `prog.bbj`, `bbjlst -l prog.bbj` overwrote `prog` with the listing.
- **Exit code is 0 on failure.** `bbjlst -l -d… nope.bbj` printed `…/nope.bbj: error: Unable to open file` and exited 0; a missing `-d` directory prints "Directory … does not exist.  Exiting..." and exits 0. Success must be judged by the output file, never by `runProcess` resolving.
- A *plain-text* input listed with `-l -d` just produces a copy (no error), so the "is it tokenized" check must happen before running bbjlst (the existing guard does).
- `-l` strips the line numbers but leaves numeric references: a numbered tokenized program decompiles to `goto 0010` with no `0010` label; the result is then a line-number-free file that still needs Denumber to be fully clean (this is the "with or without line numbers" in the backlog entry). Not a defect in this phase; mention in the hand check.
- bbjlst on a symlink input writes next to the *link* (`link`), not the target; hence resolve with `realpath` first (D-02).
- The read-only path (`decompileReadonly`, `Commands.cjs:441-489`) copies to `<tmp>/<base><ext>` and waits for `<tmpInput>.lst`; it fails identically for any input with an extension.

**Why the tests are green:** `commands-cjs-execution.test.ts:401-408` fakes bbjlst by writing `${target}.lst` for whatever file was passed, so the unit tests model a bbjlst that does not exist for extensioned inputs.

**Recommended fix shape (hand to the planner):**
1. `buildDecompileArgv({home, platform, fileName, outputDir})` -> `['-l', '-d' + outputDir, fileName]` (one argv element per value, no shell; keep `-xlst` only if kept for parity, it is not needed with `-d`). Update `command-argv-injection.test.ts:224-240` and `commands-cjs-execution.test.ts:410-446`.
2. Both commands: probe (Answer 2) -> `mkdtemp` private dir (`fs.mkdtempSync(path.join(os.tmpdir(), 'bbj-decompiled-'))`, 0700 on POSIX) -> run bbjlst with `-d<tmp>` on the resolved real path -> expect exactly `<tmp>/<basename(real)>`; wait for it to exist with a stable size (keep the size-settle idea, the existing comment says some versions flush late) -> verify it is non-empty and no longer starts with the magic.
3. Replace: write the verified output to a sibling temp file in the same directory as the real target and `rename` over it (same file system, atomic), then `chmod` to the original mode; never copy across file systems (the temp dir may be on another device; `rename` would give EXDEV). Read-only: `rename`/copy to `<tmp>/<base>.bbj`, open it, flip read-only (existing behaviour).
4. `finally { rm -rf tmpDir }` in both commands (covers IN-02 for every failure path, including the early ones). Remove `deleteLeftoverLst`, the `.lst` size wait and `canRewriteInPlace` if the new flow no longer needs them; D-14's IN-01 items (`canRewriteInPlace: true`, second `isTokenizedFile`, `fileName` alias) are then satisfied by deletion, and the structural source guards at `decompile-io.test.ts:317-343` must be replaced by behavioural tests.
5. Open the *original URI* the user clicked at the end, not `Uri.file(realpath)` (a symlinked file would otherwise open a second tab for the target).

### Answer 2: WR-01 shared rule [VERIFIED: source read this session]

| | `readLeadingBytes` (`open-file-prompts.ts:21-33`) | `isTokenizedFile` (`decompile-io.ts:26-53`) |
|---|---|---|
| Symlink | follows it (`fs.promises.open(fsPath, 'r')`), tokenized target detected | `lstat` -> `!isFile()` -> `false` (never reaches `open`) |
| FIFO/device/dir | `open` follows and can block on a FIFO (the #585 hole is still open in the prompt) | refused by `lstat`, `O_NOFOLLOW|O_NONBLOCK`, `fstat` re-check |
| I/O error | `catch { return undefined; }` then prompt state deleted, silent | `catch { return false; }` -> "is not a tokenized BBj program" message (`Commands.cjs:193-194`) |

Recommended single rule, in `decompile-io.ts` (still no `vscode` import), returning a discriminated result instead of a boolean:

```ts
export type TokenizedProbe =
    | { kind: 'tokenized'; resolvedPath: string }
    | { kind: 'not-tokenized'; resolvedPath: string }
    | { kind: 'not-a-file' }                       // dir, FIFO, socket, device after realpath
    | { kind: 'missing' }                          // ENOENT/ENOTDIR, including a dangling symlink
    | { kind: 'unreadable'; code: string; message: string };  // EACCES, EBUSY, EIO, ELOOP, EMFILE…
```
Steps: `realpath(file)` (ENOENT -> missing; other errors -> unreadable) -> `lstat(real)` must be a regular file (otherwise `not-a-file`) -> `open(real, O_RDONLY | O_NOFOLLOW | O_NONBLOCK)` (the flags only where `fs.constants` defines them, as today; Windows has neither) -> `handle.stat().isFile()` -> read `TOKENIZED_BBJ_MAGIC.length` bytes and compare with `isTokenizedBBjHeader` -> always close the handle. Keep the hardening comments (the #585 rationale) with the code. realpath makes the O_NOFOLLOW/lstat on the resolved path a pure TOCTOU guard, which is exactly what D-02 asks to keep.

Callers: the open prompt offers only for `tokenized` and uses the returned `resolvedPath`; `unreadable` there logs a fixed line to the BBj channel and does not prompt (a read race must not be a silent forever-skip: keep the existing `promptedTokenizedFiles.delete(key)` for retry). The two decompile commands map the other kinds to messages: `not-tokenized` keeps `notTokenizedMessage`; `unreadable` -> `Could not read "<name>": <code> <message>` (D-03); `missing`/`not-a-file` -> their own plain sentences. `isTokenizedFile` can stay as a thin boolean wrapper if anything still needs it; `readLeadingBytes` is deleted. D-04 reuses the same probe (Code Examples). Pure/unit-testable with real temp files and `fs.symlinkSync`/`mkfifo` where available; the existing test `decompile-io.test.ts:45-51` ("false for a symlink pointing at a real tokenized file") pins the *old* behaviour and must be inverted.

### Answer 4: What IntelliJ sends for split-single-line-IF (D-12) [VERIFIED: source read this session]

### Anti-Patterns to Avoid
- **Judging bbjlst by exit code or by the presence of any file** (exit code is 0 on failure; a stale sibling can satisfy "a file exists").
- **Running bbjlst with the output directory equal to the input directory** (it would overwrite the input; always a fresh temp dir).
- **Gating only `validateDocument`** (BBjCPL and the live parse publish separately).
- **A boolean tokenized probe** (cannot express D-03).
- **Putting planning IDs in source/test comments** (memory: register-check before closing the phase).
- **Asserting source text for behaviour** (the review's IN-04 problem): test the behaviour with real temp files, a fake runner that models real bbjlst naming, and a skipped-if-absent real-bbjlst smoke test.

**What goes wrong:** the new decompile code passes tests but fails on a real `.bbj`.
**Why:** `fakeBbjlstWrites` (`commands-cjs-execution.test.ts:401-408`) writes `${lastArg}.lst`.
**How to avoid:** replace the fake with one that implements the documented rule for the `-d` flow (`<outDir>/<basename(input)>`), add a case with a pre-existing sibling named like the extension-less base, and add one real-bbjlst smoke test that is skipped when `/opt/bbx/bin/bbjlst` (or a configured home) is absent, using a tokenized sample produced by `bbjcpl` in a temp dir.
**Warning signs:** a test names its input without an extension, or never asserts what bbjlst's argv contained.

### Pitfall 2: Success judged by exit code
**What goes wrong:** `bbjlst` printed "Unable to open file" and exited 0; the command reports success.
**How to avoid:** require the output file, non-empty, not tokenized; include bbjlst's captured stdout/stderr in the error text.

### Pitfall 3: Structural source-guard tests pin the old flow
**What goes wrong:** `decompile-io.test.ts:317-343` (needs `const decompileInPlace = (resolvedFileName) => {`, `await deleteLeftoverLst(resolvedFileName)`, `execWithProgress(argv)` in that order), `decompile-io.test.ts:346-353` (`/denumber/i`), `denumber-command.test.ts:244` (`when` string) and `activation-command-coverage.test.ts` (sequence + 36 subscriptions) all fail on correct changes.
**How to avoid:** list these in the plan as expected edits, rewrite them as behavioural tests in the same commit as the code.

### Pitfall 4: A banner/diagnostic message that trips the old free-text greps
`/denumber/i` over `Commands.cjs` and `process-args.ts` fails if a new user message there says "Denumber". D-04's message belongs in `denumber-command.ts` (which is allowed to say it); keep decompile messages free of that word or narrow the guard first (D-14 IN-04).

### Pitfall 5: Stale compiler diagnostics after a document turns numbered/tokenized
Verdict/kept-check state is keyed by uri and survives edits (`clearVerdictState`, `clearKeptCheck` only on close). Clear them when the classification flips, or the `BBjCPL` list reappears when the doc becomes normal again with old line numbers.

### Pitfall 6: Version semantics differ per client
See Answer 6. Do not hard-code `V + 1`; derive from the server mirror and treat absence as "do not place". Test with a fake messenger whose `applyEdit` bumps the version by 1 and by 2.

### Pitfall 7: `onDidChangeConfiguration` re-entrancy
`update` writes fire change events; the new-key write and the old-key removal each notify. The filter on the old key stops loops, but two overlapping runs (new key written, old key still present, event arrives) may both try to remove the old key. Use a single-flight guard (run again once if an event arrived while running) and read a fresh `getConfiguration('bbj.formatter')` inside the handler.

### Pitfall 8: IntelliJ `isEnabled` and later content change
A file refused at open stays unconnected after Decompile & Replace until reopened; reopen the editor after the replace, and add this as an explicit hand-check step [ASSUMED].

### Pitfall 9: Symlink URI vs real path
Decompile the realpath, open the original URI; otherwise the user gets a second tab for the target and the original tab keeps showing the (now removed) binary state.

### Pitfall 10: Windows
`O_NOFOLLOW`/`O_NONBLOCK` are undefined on Windows (existing code guards), `rename` over an open file can fail with EBUSY/EPERM (report as a cause per D-03), and `-d` with a Windows path is untested [ASSUMED]; the user's Windows hand-check exists for 129, so add one decompile row to the Windows pass if one is run.

### Pitfall 11: Large tokenized file in IntelliJ
5.2 s parse for 1.45 MB (measured). Keep `isEnabled` O(1) after the first read and never read the whole file.

### Pitfall 12: `ROADMAP.md` is already dirty
`git status` shows it modified (130.1 entry added) — edit on top of that, do not `git checkout` it (memory: restore clobbers uncommitted edits).
