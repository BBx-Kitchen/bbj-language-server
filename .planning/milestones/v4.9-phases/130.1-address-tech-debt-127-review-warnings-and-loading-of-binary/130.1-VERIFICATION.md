## Warnings (non-blocking, user-triaged into todos)

1. **WR-03, Denumber stall on non-identical mirror text.** `mirrorVersionFor` waits up to `DENUM_VERSION_WAIT_MS` (5 s) for the server's mirror to equal `outcome.result.text` byte for byte. `bbj-denum-service.ts` has no EOL handling, so a CRLF document that Denumber reports diagnostics for would, by reading, get its success message 5 s late (the run claim is held that long) and an unversioned list, so no problems are placed. The degradation is safe (log copy still written, nothing misplaced), and a test pins the bounded-wait path, but no test reproduces the CRLF case, and I did not reproduce it. Frequency is unverified. This does not falsify D-16 (versioned list, clients drop on mismatch) but it is the one place where a phase change can make an existing flow slower. Recommended: fix before or just after the milestone ships, as the todo suggests (compare with EOLs normalised, or reply first and send the list asynchronously).
2. **WR-04, VFS read in `isEnabled`.** On a modification-stamp change the 7-byte read runs inside an LSP4IJ callback; which thread calls it is unconfirmed. The read is small and failure-safe. Hand-checked with no hang observed.
3. **Info items IN-01..IN-04 (second half)** are cosmetic or narrow races (IN-04: an edit made during a decompile of up to 60 s is discarded by `reloadFiles`).
4. Windows byte-for-byte and Windows path behaviour of the new decompile flow were not exercised (the optional Windows pass was not run). Not a roadmap criterion.
5. Working-tree hygiene before `/gsd-complete-milestone`: leave `com/`, `.planning/milestone.lock` and `.planning/todos/pending/2026-10-04-nested-java-classes-from-bbj-ls.md` unstaged (exact-path staging only).
