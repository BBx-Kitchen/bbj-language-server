<objective>
Close UAT gap G-109-1 against COMP-03: inside a class METHOD body, completion offered program-level
variables (`a$`, `X!` in the user's report), and linking bound them. BBj gives a method its own
variable scope. The METHOD verb documentation
(https://documentation.basis.cloud/BASISHelp/WebHelp/commands/method_verb.htm) says: "The only
variables that are visible within that scope are the parameters specified in the method parameter
list and the fields defined in the class."

**Root cause (debug session, confirmed by this planner's own measurement).** For a plain (non-`#`)
name, `BbjScopeProvider.getScope` delegates to Langium's `DefaultScopeProvider.getScope`. That walk
adds the local symbols of every container up to the root. Inside a method the chain is
MethodDecl → BbjClass → Program. Symbol collection is correct: `a$`/`X!` are keyed on Program and
`b$` on MethodDecl. Only the lookup lacks a method boundary.

**Chosen approach.** The fix is a METHOD boundary in the scope provider's plain-name branch, so
completion, linking, definition, references and type inference agree. It is not a completion-item
filter. The debug session's experiment diff
(`.planning/debug/method-body-completion-program-scope-leak.experiment.diff`) did the same in the
same place and passed the whole suite. The planner re-measured the exact shape below in a scratch
worktree of HEAD `3fbc53f1`, with `isMethodDecl` and a `VariableDecl` subtype test in place of the
experiment's `$type` lambda and type-name set. The results:
- tsc is clean.
- The whole suite reports `numFailedTests=0 numTotalTests=2848` (RUN_BBJ_TESTS=0, --maxWorkers=2).
- Every label set and link result in `<interfaces>` below was measured this way.
This stays within D-01's limits: no Langium patch, fork or upstream PR. It extends the D-03 matrix.
It needs no grammar change, so D-04 does not apply.

**Settled questions** (the evidence behind the exclusion set):
1. *Program variables in a method:* not visible. Sources: the METHOD verb page (quoted above) and the
   Custom Objects tutorial, Methods
   (https://documentation.basis.cloud/BASISHelp/WebHelp/tutorials/custom_objects/custom_objects_05methods.htm):
   "The only method variables shared between the custom class method and the code that called it
   are those that are passed in the method's parameter list." They are excluded.
2. *Class fields without `#`:* not reachable in BBj. The Custom Objects tutorial, Fields
   (https://documentation.basis.cloud/BASISHelp/WebHelp/tutorials/custom_objects/custom_objects_04fields.htm),
   says: "The special symbol # is required in front of a field name in order for a custom object
   method to get direct access to a field." The LS still offers and links a bare field name inside a
   method today (measured: `name$` is offered). That comes from the class-keyed entries, which also
   hold `this!`, `super!`, methods and accessors. Those entries stay untouched on purpose: the gap is
   about program variables, and removing class entries would take `this!` with them. The SUMMARY
   records this as a remaining, separate looseness. It is not fixed here.
3. *Program labels from a method:* the documentation covers only the other direction ("Labels and
   local variables in a method are only visible within that method"). The Custom Objects tutorial,
   Program #4, says SETERR inside a method behaves "similar to ... in a called program". Label
   references are `UserLabelRef`/`SymbolicLabelRef` nodes (reference type `LabelDecl`). They never
   reach the plain-name `SymbolRef` branch this plan changes, so label resolution is unchanged by
   construction. That makes this out of scope, not a decision.
4. *Program-level DEF FN from a method:* the BBj DEF pages say nothing about scope. **Assumption:** a
   program-level DEF FN stays visible, so `DefFunction` is not in the exclusion set. This is the
   conservative side: no new warning on a construct whose validity is undocumented, and the
   compiler on save is authoritative. A presence test pins it.
5. *Kept visible (orchestrator direction):* USE'd Java classes (Program-keyed `JavaClass`), class
   names (`BbjClass`), everything keyed on the class, and the global scope (library members, the
   Java class index, Java package roots).

**Side-effect measurement: a targeted probe, not the conformance harness.** A method that reads a
same-named program variable now gets the standard "Could not resolve reference" Warning. The
private conformance harness cannot observe that. Its `worker.mts` drops every `linking-error`
diagnostic before counting: the `NOT_VALIDATION` set holds `linking-error`, and the `relevant`
filter removes it again in endpoint mode. So a full harness run would show nothing, whatever the
effect. Task 3 therefore runs a temporary local probe that records every diagnostic, linking
included, before and after the fix on three sets:
- `examples/` and `bbj-vscode/test/test-data/` (public, file names may be recorded);
- every private-corpus file that declares a METHOD (834 of 16,884). A file without a METHOD cannot
  change, because the boundary only applies inside a MethodDecl. Counts only, no corpus names.
The planner's own run of this probe found **zero** added or removed diagnostics in all three sets.
In-repo, it covered all 119 `.bbj`/`.bbx` files without the METHOD prefilter: 669 diagnostics in
both runs. Only 24 of those files declare a METHOD, so the executor's prefiltered counts will be
lower. On the corpus it covered the 834 method files: 9,231 diagnostics in both runs, about 33
seconds per run.

Purpose: a method body is a separate BBj scope. Offering or linking program variables there
suggests code that reads an empty local at runtime.
Output: one private walk method plus a one-line call-site change in `bbj-scope.ts`, a new
`test/method-body-scope.test.ts`, extra-label detection in `test/completion-method-body.test.ts`,
and an addendum in `109-COMP03-MEASUREMENT.md`.
