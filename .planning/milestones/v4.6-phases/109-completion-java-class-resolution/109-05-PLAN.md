<objective>
Resolve a nested Java class once, whether it arrives as `Outer.Inner` or `Outer$Inner`, and show it as
`Outer.Inner` everywhere (JINT-02, issue #659, D-09, D-10).

Purpose: the backend echoes the requested spelling as the class name, and the language server caches by
that name, so both spellings are fetched and cached separately; bbj-ls names member types with
getCanonicalName (dotted) but constructor return types with getName (`$`), which produces the pair on a
normal cold start.
Output: `canonicalJavaClassName` applied at every resolution entry point, and
`test/java-interop-nested-class-names.test.ts` on plan 109-04's counting double.
</objective>

<assumption_delta_decision>
- Noun (now primary): the canonical nested-class name, the Java source spelling `Outer.Inner` that getCanonicalName produces. It is the single identity for a Java class in java-interop.ts: the key of `resolvedClasses`, `_inFlightPhase2` and `_pendingResolutions`, and the `JavaClass.name` shown to users.
- Decision: promote.
- Rationale: per D-09 and D-10, one class is fetched and cached once whatever spelling arrives, and the display spelling is `Outer.Inner`. The `$` binary spelling is demoted to a request-time detail: it is sent to the backend only as the spelling that arrived, because Class.forName accepts it directly.
- Invariant test (added in Task 1): both spellings, in either order, produce one backend fetch and the same JavaClass object.
</assumption_delta_decision>
