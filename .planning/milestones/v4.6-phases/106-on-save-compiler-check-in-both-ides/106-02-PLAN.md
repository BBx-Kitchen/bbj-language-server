Reorder `parseProgram()` so the dedicated lane is tried first and on its own (JINT-03; research Pattern 5).

1. In `parseProgram(params, token)`: first `const lane = await this.parseLaneConnection();`. When `lane` is undefined (it could not be opened, or it was retired for this generation), then and only then `await this.connect()` and send the request over the shared connection. When `lane` exists, keep the existing try/catch unchanged (a MethodNotFound answer retires the lane for the generation, disposes it and rethrows). `parseLaneConnection()`/`openParseLane()` already never touch the breaker, never raise the connection-error dialog and never bump the generation; do not change them.
2. Rewrite the `parseProgram` doc comment: the request tries its own connection first, independent of the shared connection's state and breaker, so a shared connection that is down, half-open or still busy with class lookups never delays or short-circuits a parse; the shared connection is used only when the dedicated one cannot be opened or was retired for this generation; the not-routed-through-`sendRequestSafe` reasoning stays. Mention the side effect for a parse that runs before any shared connection exists: the lane then belongs to the current generation, and the shared connection's first connect bumps the generation, which retires that lane and re-probes the endpoint on the next parse (the existing "a reset of either connection clears verdict state" rule).
3. In `java-interop-parse-lane.test.ts`, update the existing tests whose socket-attempt expectations assumed the shared connection opens first, with comments saying why:
   - "a second parse in the same generation … clearCache() makes the next parse try the dedicated connection again": the first parse opens only the dedicated connection (1 attempt, not 2), and after `clearCache()` the next parse reopens only the dedicated connection (+1, not +2).
   - "two same-tick parses open exactly one dedicated socket …": 1 socket attempt in total.
   - "an older server behind the dedicated connection …": the MethodNotFound parse makes 1 attempt; the next parse in that generation opens the shared connection (+1 attempt) and its request travels on that new shared connection's id.
   - "with the peer down …": rename it to say the parse tries its own connection, then the shared one, and rejects as a transport failure without sending the request; expect 2 socket attempts and no `parseProgram` request.
4. Add the tracer test "with the shared breaker open, a parse is answered over its own connection": `peerUp = true`, `connectDelayMs = 0`, fake timers, `refusedSocketAttempts.add(1)`; a `getRawClass('test.Warm')` through the existing `RawClassAccess` cast rejects (the breaker opens); `parseProgram(...)` then resolves with `errors: []`, `socketAttempts` is 2, the only `parseProgram` request carries connection id 2, and a class lookup right afterwards still rejects with the circuit-open message and makes no new socket attempt (the breaker was not closed by the parse).
