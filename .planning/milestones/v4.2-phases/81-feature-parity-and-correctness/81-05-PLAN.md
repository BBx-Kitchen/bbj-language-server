<objective>
Make "Compile BBj File" actually compile: save the file, send `bbj/compile` to the shared language
server off the EDT, and show the result the way VS Code shows its own compile result.

Purpose: `BbjCompileAction.actionPerformed()` today writes one line to the console and does nothing
else — the menu item has never compiled anything (#571). PARITY-01 requires the action to reach
bbjcpl *through* the language server, with no bbjcpl logic duplicated on the IntelliJ side, so this
plan is deliberately thin: a params object, a result object, one `@JsonRequest` method on the
interface LSP4IJ already proxies, a rendering seam, and an action body that saves, dispatches and
renders.

Three constraints shape it. `getServerInterface()` returns exactly one interface, so the new request
has to live on `BbjComposerServer` (or something extending it) or the proxy will never carry it.
Nothing may block the dispatch thread, so the round trip runs in a `Task.Backgroundable` whose body
asserts it is off the EDT as its first statement — the same convention Phase 79 pinned for the run
actions and EM login. And the balloon text and the "Open Settings" remedy are chosen from the
result's machine-readable `reason`, never from its prose, which is exactly why 81-01 defined that
field.

Output: `CompileModels`, `CompileResultPresenter`, one interface method, the rewritten action, a
behavioural test over the whole rendering table and a source guard over the wiring. This plan is
81-05 and depends on 81-01 (the request contract) and 81-04 (the output-directory setting that keeps
the server from refusing every call).
</objective>

## Executor shell and file-access rules (CLAUDE.md — follow verbatim)

A Phase 80 executor stalled for 20 minutes on an unanswered `cd …; git diff` permission prompt. These
rules keep the run autonomous:

- Search and read with the built-in `Grep`, `Glob` and `Read` tools first. Fall back to shell
  `grep`/`find`/`cat` only when a built-in genuinely cannot do the job (for example a pipeline).
- Every shell path is absolute and complete from `/home/coder/repos/bbj-language-server/…`. Never
  rely on the current working directory; never use `.`, `..` or `~` as a search target.
- Never chain `cd` with `grep`, `find`, `cat`, `sed`, `head`, `tail` or `git`. Use `git -C
  /home/coder/repos/bbj-language-server …`. `cd` is acceptable only directly in front of `./gradlew`
  or `npx`/`npm`.
- No bare recursive `grep -r` or `find` over a directory. Scope with `--include`/`-name` or use the
  `Grep` tool with a `glob`. Never point any read at `.env*`, `*.pem`, `*.key` or a credential store.
- Stage commits with `git add <exact path>` only — never `git add -A` or `git add .`.

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **`bbj/compile` is declared on an interface named for the composer.** RESEARCH.md assumption A2:
   `getServerInterface()` returns exactly one class, and introducing a sibling interface would mean
   editing `BbjLanguageServerFactory`, which 81-04 also touches. Declaring the method on
   `BbjComposerServer` keeps the wiring to one file and matches the existing pattern; the naming
   mismatch is cosmetic and is called out in that interface's javadoc.
2. **`org.eclipse.lsp4j.Diagnostic` is reused rather than a hand-rolled DTO.** The connection already
   uses lsp4j's JSON handler, so the standard shape deserialises without a custom adapter and the
   severity enum maps to its integer form. If a future LSP4IJ version changes its JSON handling, the
   symptom would be a null `range` in the rendered body; the presenter is written to render a
   diagnostic with a missing range as message-only rather than throwing.
3. **The action's behaviour is proven by the seam plus source guards, not by driving the IDE.** C-01
   keeps the platform test framework out of the module. Every decision that can be a pure function
   lives in the presenter and is tested; the save-before-dispatch order, the off-EDT assertion and the
   absence of any process launch are asserted as source facts. Live confirmation of the balloons is a
   UAT item, following Phase 79/80 practice.
4. **The client-side wait is a backstop, not the real timeout.** The server already kills a compile
   after 30 s and answers with its own timeout reason. The action's own wait exists only so a lost
   response cannot leave a progress indicator up forever; if UAT sees the client-side wait fire before
   the server's, the two numbers need re-balancing rather than a new mechanism.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-81-18 | Tampering | compiler invocation logic drifting onto the IntelliJ side | high | mitigate | The action holds no argument list, no option read and no process launch; the source guard asserts the absence of a process-launch API and of the compiler binary's own name in the file. This is PARITY-01's explicit requirement, not a style preference. |
| T-81-19 | Denial of service | the EDT blocking on a compile round trip | high | mitigate | Only the document save runs on the dispatch thread, where the platform requires it; the resolution, the request and both waits run inside `Task.Backgroundable`, whose body asserts it is off the dispatch thread as its first statement. The source guard pins the assertion's position and its uniqueness. |
| T-81-20 | Denial of service | a lost response leaving a progress indicator up forever | medium | mitigate | Both waits are bounded and a timeout renders `requestFailed` rather than escaping the task. |
| T-81-21 | Information disclosure | server-supplied text rendered in a balloon | low | accept | The text is the local compiler's own message about the user's own file; VS Code shows the same text in the same situation today, so no new boundary is crossed. |
| T-81-22 | Repudiation | a compile that reports nothing | medium | mitigate | Every result path renders a balloon, including an unrecognised or null reason (Task 2 Test 7), a null server proxy and a failed request; failures are additionally written to the language-server console. |
| T-81-23 | Tampering | a file URI naming something outside the workspace | low | accept | The URI is constructed by the action itself from the open editor's virtual file and never from user input; the server independently refuses any non-`file` scheme (81-01). ASVS L1 local boundary. |
