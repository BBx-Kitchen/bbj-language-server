<objective>
Give the shared language server a real, options-aware `bbj/compile` request: it builds the bbjcpl
argument list from one option table, refuses to run without an explicit output location, spawns the
real compiler without the validate-only flag, and returns a structured success/diagnostics result to
whoever asked.

Purpose: PARITY-01 (#571) requires that IntelliJ's "Compile BBj File" action reach bbjcpl *through*
the language server, with no bbjcpl invocation logic duplicated on the IntelliJ side. Today the only
bbjcpl path in the server is `BBjCPLService.compile(filePath)`, which hardcodes the validate-only
flag, publishes its diagnostics as editor squiggles, and is owned by the debounced background
builder. VS Code's real compile lives in a different place entirely (`Commands/Commands.cjs`), builds
its argv from an 18-entry option table that imports `vscode`, and spawns bbjcpl itself. This plan
creates the third thing both of those need: one `vscode`-free option table, one options-aware service
entry point beside the untouched validate-only one, and one request that returns rather than
publishes.

Two premises in CONTEXT.md were corrected by research and are honoured in their corrected form here.
bbjcpl with no output directory does **not** overwrite the source — it writes a sibling file with the
`.bbj` extension flipped, and refuses on its own when the derived name collides. D-05's guard still
stands, but its rationale is "an explicit output location is required" and no test or comment may
claim an in-place overwrite. And IntelliJ's `createSettings()` object never reaches `config.compiler`,
so the compile output directory travels as the flat `initializationOptions` key
`compilerOutputDirectory`, read in `bbj-ws-manager.ts` exactly as `compilerTrigger` already is.

Output: `compiler-options.ts`, `compile-command.ts`, `BBjCPLService.compileWithOptions`, the
workspace-manager intake, the `main.ts` registration, the VS Code adapter, two bbjcpl fixture homes
and two new vitest files. This plan is 81-01; 81-04 sends the `compilerOutputDirectory` key from
IntelliJ and 81-05 calls `bbj/compile` from the IntelliJ action.
</objective>

## Executor shell and file-access rules (CLAUDE.md — follow verbatim)

A Phase 80 executor stalled for 20 minutes on an unanswered `cd …; git diff` permission prompt. These
rules keep the run autonomous:

- Search and read with the built-in `Grep`, `Glob` and `Read` tools first. Fall back to shell
  `grep`/`find`/`cat` only when a built-in genuinely cannot do the job (for example a pipeline).
- Every shell path is absolute and complete from `/home/coder/repos/bbj-language-server/…`. Never
  rely on the current working directory; never use `.`, `..` or `~` as a search target.
- Never chain `cd` with `grep`, `find`, `cat`, `sed`, `head`, `tail` or `git`. Use `git -C
  /home/coder/repos/bbj-language-server …`. `cd` is acceptable only directly in front of `./gradlew`
  or `npx`/`npm`.
- No bare recursive `grep -r` or `find` over a directory. Scope with `--include`/`-name` or use the
  `Grep` tool with a `glob`. Never point any read at `.env*`, `*.pem`, `*.key` or a credential store.
- Stage commits with `git add <exact path>` only — never `git add -A` or `git add .`.

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **The `reason` vocabulary is a client-facing contract.** CONTEXT.md rates D-01 as *costly* to
   reverse for exactly this reason: once the IntelliJ plugin ships against these strings, changing
   them means coordinating a plugin and a language-server release. The nine values fixed in Task 1 are
   the whole vocabulary; 81-05 maps every one of them. Adding a value later is safe, renaming one is
   not.
2. **The observed bbjcpl stderr wording is from this container's build.** RESEARCH.md assumption A3:
   a different BBj version could word the overwrite refusal or the invalid-output-directory fatal
   differently. Nothing in this plan matches on that wording — classification is `stderr.trim() === ''`
   and the unparsed text is passed through verbatim — but the *fixture* scripts reproduce the observed
   wording, so a reader should not mistake them for a parsed contract.
3. **`setCompilerConfig` is called from `onDidChangeConfiguration` for VS Code only.** IntelliJ never
   delivers a `bbj.compiler` object (RESEARCH.md Pitfall 2), so the initializationOptions seed is never
   overwritten there. If a future LSP4IJ version starts resolving `workspace/configuration` for the
   flat settings object, the VS Code branch would begin overwriting the seed with an object that has
   no `output.directory`, and the guard would start refusing on IntelliJ. Task 1's merge rule (seed
   values survive a config push that does not carry them) is written to make that harmless.
