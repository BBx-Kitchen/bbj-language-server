<objective>
Teach the IntelliJ word lexer about BBj string literals and `rem` comments so bracket characters
inside them stop behaving like structural brackets.

Purpose: `BbjWordLexer` today emits WORD, WHITE_SPACE, SYMBOL and six bracket types; a double quote
falls through to SYMBOL and everything between quotes is lexed as ordinary code. So the parenthesis in
`PRINT "value (not a bracket)"` becomes a real LPAREN, `BbjParserDefinition` reports no string-literal
or comment token sets at all, and `BbjPairedBraceMatcher` allows pairing unconditionally. The visible
result (#568) is bracket-match highlighting, Ctrl+Shift+M navigation and auto-close all firing inside
string literals, on characters that are just text. The fix is entirely in what the lexer *emits*: a
bracket that was never classified as a bracket token cannot be matched, navigated to, or auto-closed.

The two grammar terminals in `bbj-vscode/src/language/bbj.langium` are the specification — the
IntelliJ scanner mirrors them, it does not invent rules. Mnemonics stay untouched: their bodies cannot
contain brackets and the parentheses that follow a mnemonic are real.

Output: a plain-Java `BbjStringCommentScanner` seam with no platform imports, two new token types,
three one-line wiring changes, a behavioural JUnit 5 test class whose method names carry #568's
acceptance wording, and a source guard over the wiring. This plan is 81-02 and is independent of every
other plan in the phase.
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **`rem` is recognised wherever a token can start, with no left-context test.** The grammar terminal
   has no left boundary either (`(?![\w!$%@])` guards only the right side), and the existing lexer's
   greedy word branch already prevents `myrem` from ever starting a token at `rem`. The one shape this
   admits that a human might not expect is `.rem` or `;rem`, where a punctuation token ends and `rem`
   begins a comment. That matches the Langium grammar's behaviour, so the two lexers agree; it is
   recorded here because it is a real behavioural choice, not an oversight.
2. **The lexer itself is proven by the seam plus source guards, not by instantiating it.** C-01
   forbids a platform test framework, and constructing `BbjWordLexer` in a plain JUnit test would pull
   in `IElementType` registration. The seam carries all the scanning logic and is directly tested; the
   three wiring sites are pinned by text assertions. Live-editor confirmation that a parenthesis
   inside a string no longer highlights or auto-closes is a UAT item, following Phase 79/80 practice.
