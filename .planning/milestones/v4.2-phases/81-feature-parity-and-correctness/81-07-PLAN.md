<objective>
Make the compile-error balloon survive whichever LSP4IJ the user's IDE happens to have installed.
81-06 fixed the payload, so the response now deserialises and the plugin reaches its rendering code
for the first time in a live IDE — where it dies with
`NoSuchMethodError: 'java.lang.String org.eclipse.lsp4j.Diagnostic.getMessage()'` at the first
rendered diagnostic. The plugin compiles against the client library vendored inside LSP4IJ **0.19.0**
(the Gradle pin), where that accessor returns a plain `String`. The live IDE resolves LSP4IJ through
`<depends>com.redhat.devtools.lsp4ij</depends>`, which carries no version — and LSP4IJ **0.20.0 and
later bundle a client library whose diagnostic message accessor returns a two-branch value instead**.
Return type is part of the JVM method descriptor, so the call site becomes unresolvable. The success
path sends an empty diagnostics list and never touches a diagnostic, which is why only the
syntax-error case breaks.

Purpose: an IntelliJ plugin descriptor cannot pin the version of a plugin it depends on — there is no
version attribute on `<depends>`, and `<idea-version>` constrains only the platform. So no build-side
pin can make the runtime match. The only fix that works on every install is for the one place that
reads a diagnostic's message to stop depending on the accessor's exact descriptor.

Output: a reflective, shape-normalising message read in `CompileResultPresenter` with a safe
fallback; tests that pin both shapes using duck-typed stand-ins the pinned classpath cannot otherwise
produce; the first test that goes from a JSON-RPC envelope all the way to balloon body text; a source
guard against a typed accessor creeping back; and a recorded decision on which LSP4IJ generation the
build classpath should track.

This plan is gap closure for G-81-5 from `81-UAT.md` (test 5, blocker). It depends on 81-05 (the
presenter and action it fixes) and 81-06 (the boundary test it extends); both are complete. It
changes no TypeScript.
</objective>

## Flagged assumptions

Surfaced, not dropped.

1. **Reflection is the only mechanism that compiles against both generations.** Writing the
   two-branch type literally in source would not compile against the pinned 0.21.1 classpath, and
   naming the plain-string type would not compile against 1.0.0. There is no overload set that spans
   both. A duck-typed read is therefore not defensive over-engineering here; it is the only
   expressible option that does not require shipping two binaries.
2. **Range and position accessors stay typed.** They are unchanged upstream and pinned by the LSP
   `uinteger` contract, so making them reflective would add cost and noise for no coverage. If a
   future client library changes them, the same class of failure returns — accepted, and recorded as
   a threat rather than pre-solved.
3. **The rest of the plugin's LSP4IJ coupling is out of scope.** `ServerStatus`,
   `LanguageServerManager`, `LSPClientFeatures`, `LSPCompletionFeature`, `LSPDocumentLinkFeature`,
   `LanguageClientImpl` and the connection providers carry the same unpinned-runtime hazard. Phase 83
   ("LSP4IJ experimental-API canary tests") is the natural home for that sweep; widening this
   blocker fix into it would trade a shippable fix for an open-ended audit.
4. **Reflection is not cached.** The lookup runs once per rendered diagnostic on a user-triggered
   action that renders a handful of lines. Caching would add a mutable static for no measurable gain
   and one more thing to get wrong.

  <action>
    **(a) The tolerant read.** In `CompileResultPresenter`, add a package-private static
    `String messageTextOf(Object diagnostic)` plus two private helpers, and stop calling the
    accessor through a compile-time descriptor.

    `messageTextOf(Object)` resolves the no-argument accessor named `getMessage` on
    `diagnostic.getClass()` and normalises whatever comes back. Take `Object`, not the typed
    parameter: that is what lets Task 2 drive it with stand-ins the pinned classpath cannot produce.

    The reflective invoke helper — a private static `Object invokeNoArg(Object target, String
    methodName)`:

    - returns `null` for a null target;
    - resolves `target.getClass().getMethod(methodName)`, and when `accessor.canAccess(target)` is
      false calls `accessor.setAccessible(true)` (this module is on Java 17, and a stand-in declared
      in a non-public test class would otherwise fail the access check);
    - returns the invocation result;
    - catches `ReflectiveOperationException` and `RuntimeException` and returns `null`. Nothing
      thrown here may escape into the background task — that escape is the entire failure being
      fixed.

    The normaliser — a private static `String unwrapMessage(Object value, int depth)`, bounded by a
    private static final `MAX_MESSAGE_UNWRAP_DEPTH = 3` so it is visibly terminating:

    - `null`, or depth past the bound, yields the empty string;
    - a `String` yields itself;
    - otherwise try `getLeft` via `invokeNoArg`; a non-null result recurses at `depth + 1` (a
      two-branch value holding text on its left branch);
    - otherwise try `getRight`; a non-null result recurses at `depth + 1` (a two-branch value holding
      a markup object on its right branch);
    - otherwise try `getValue`; a `String` result yields itself (the markup object's own text);
    - otherwise fall back to `String.valueOf(value)`, so an unrecognised shape still shows something
      rather than nothing.

    Duck-type on the accessors' non-null results rather than on `isLeft()`: a right-valued
    two-branch object returns null from `getLeft()`, so the null check alone discriminates, and the
    normaliser then works on any object exposing that accessor pair — including stand-ins that
    implement no shared interface.
