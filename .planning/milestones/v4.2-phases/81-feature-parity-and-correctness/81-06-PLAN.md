<objective>
Make the compile-error balloon actually appear in IntelliJ. Today a syntax error produces
`Failed to compile xxx.bbj org.eclipse.lsp4j.jsonrpc.MessageIssueException: Message could not be
parsed.` because the language server puts `Number.MAX_SAFE_INTEGER` (9007199254740991) in every
diagnostic's `range.end.character`, and `org.eclipse.lsp4j.Position.character` is a Java primitive
`int` (max 2147483647). Gson cannot read that number into an `int`, so LSP4J rejects the whole
response before `CompileResultPresenter` ever runs. The success path sends `diagnostics: []`, never
serializes a `Position`, and therefore works — which is exactly why only the syntax-error case broke.

Purpose: this is a one-value protocol defect on a field nothing downstream even reads
(`CompileResultPresenter` uses only `range.start`). The LSP specification already caps positions at
the `uinteger` maximum, 2^31 − 1 = 2147483647 — the same number as `Integer.MAX_VALUE` — so the fix
is to say what the spec always required, in one named constant, at both sites that emit a whole-line
range.

Output: a small `lsp-position.ts` module holding the sentinel and its rationale; both emitting sites
importing it; a TypeScript wire-shape assertion on a real `compile-errors` result; a source guard so
the value cannot drift back; and a JUnit test that parses a captured response envelope through
LSP4J's own Gson, closing the cross-language boundary that no test on either side covered.

This plan is gap closure for G-81-4 from `81-UAT.md`. It depends on 81-01 (the `bbj/compile` handler
and its tests) and 81-05 (the `CompileModels` DTO the JUnit test deserializes into); both are
complete. It changes no Java main source.
</objective>

## The value being changed

| | Today | After |
|---|---|---|
| `range.end.character` | `Number.MAX_SAFE_INTEGER` = 9007199254740991 | `END_OF_LINE_CHARACTER` = 2147483647 |
| LSP contract | violates `uinteger` (0 … 2^31 − 1) | at the `uinteger` maximum |

## Flagged assumptions

Surfaced, not dropped.

1. **2147483647 is a better sentinel than the real line length.** bbjcpl reports no column, and the
   source text is not in hand at either emitting site — using the real length would mean new file
   I/O for a highlight convention. Both editors clamp an over-long end position to the line, so the
   rendered squiggle is identical. If a future client is found that does *not* clamp, the fix is to
   compute the length where the text is already available, not to shrink the sentinel.
2. **Plain Gson is the right deserializer in the JUnit test only if it is LSP4J's Gson.** The test
   must build its Gson from `new MessageJsonHandler(…).getGson()`, not `new Gson()`: LSP4J registers
   adapters (notably for integer-valued enums such as `DiagnosticSeverity`) that a bare Gson lacks,
   and a bare Gson would silently null out `severity` and prove less than it appears to.
3. **The negative control pins current Gson behaviour.** Gson throws `JsonSyntaxException` (a
   `JsonParseException`) when a JSON number will not fit an `int` field. If a future Gson becomes
   lenient the negative control will fail; the response then is to widen the expected type and keep
   asserting that the oversized payload does not yield a usable `Position`, never to delete the test.
