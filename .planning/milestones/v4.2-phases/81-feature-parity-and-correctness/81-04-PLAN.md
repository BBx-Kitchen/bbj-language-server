<objective>
Give the IntelliJ plugin the one setting the compile action needs — a compile output directory — and
route it to the language server through the channel that actually works.

Purpose: 81-01's `bbj/compile` refuses to run without an explicit output location, so without a place
to configure one the action would always refuse. CONTEXT.md D-05 asked for exactly one new setting to
make the action usable, deliberately not the full compiler-option UI (that is PAR-V2-04). D-05 also
assumed the value would ride along in `BbjLanguageClient.createSettings()`; research disassembled
LSP4IJ 0.19.0 and disproved that path — the push side is only ever triggered by LSP4IJ's own generic
per-server settings UI, which this plugin never populates, and the pull side resolves
`section: "bbj"` against a *flat* JSON object with no `"bbj"` key and returns null. The value that
does reliably reach the server is the flat `initializationOptions` object built in
`BbjLanguageServerFactory`, which is exactly how `compilerTrigger` already works, and which the
existing settings-apply restart re-delivers for free.

So this plan adds a persisted field, a directory-chooser row in the settings dialog, one
`addProperty` call, and a plain-Java normalisation seam that both the factory and the tests share. It
deliberately leaves `BbjLanguageClient` untouched and records why.

Output: `CompilerInitOptions`, the `BbjSettings` field, the dialog row, the configurable wiring, the
factory key, a behavioural test and a source guard. This plan is 81-04; 81-01 reads the key on the
server side and 81-05 is the action that depends on both.
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **The new setting takes effect on the next language-server start, not instantly.** Applying the
   settings dialog already schedules a restart, and a restart re-sends fresh initialization options,
   so in practice the value lands within the existing debounce. RESEARCH.md assumption A4 records that
   CONTEXT.md never asked for hot reload without a restart. If UAT finds a user typing a directory and
   compiling before the restart completes, the remedy is a dialog note, not new push wiring.
2. **`BbjLanguageClient` is left untouched on purpose.** CONTEXT.md D-05's literal wording routes the
   value through `createSettings()`; the orchestrator's correction 2 and RESEARCH.md Pitfall 2
   override that mechanism while keeping the decision. Adding a nested key there would be harmless but
   dead, so it is omitted and the source guard asserts the file is unchanged, making the deviation
   visible rather than silent.
3. **No filesystem validation of the configured path.** RESEARCH.md Open Question 2 recommends letting
   bbjcpl's own "Invalid output directory" failure surface through the server's failure path instead.
   `BbjSettingsComponentSourceGuardTest` independently forbids filesystem construction in this
   component, so front-loading validation here would also break an existing guard.
