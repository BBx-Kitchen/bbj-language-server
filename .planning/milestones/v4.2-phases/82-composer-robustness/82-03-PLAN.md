<objective>
Stop a composer from rewriting text it never saw. Today all three edit-in-place apply paths compute
`doc.getLineStartOffset(capturedLine)` and apply the pre-dialog decode's offsets inside a write
command with no re-check, so if the document changed while the modal dialog was open the edit either
throws or — the more concerning case — silently rewrites whatever text now occupies that range
(#567). This plan puts one plain-Java guard in front of every apply path: re-read the captured line
from the live document, re-run the same decodeCall request the launch used against that current text
at the captured column, compare the whole decode result, and write only on a match — with the
document's modification stamp re-checked as the first statement inside the write command so the
async gap between the two cannot be exploited either.

Purpose: COMP-02's decision is already recorded as abort and notify. This is also the half of the
composer work that `.exceptionally` alone can never catch, because a silent rewrite throws nothing —
which is exactly why PITFALLS.md Pitfall 12 insists both halves ship in one phase and route through
one notification path. That path now exists, built by 82-01 and 82-02.

Output: `DecodeEquality`, `StaleEditGuard`, the three rewired apply flows, two behavioural test
classes over a fake document double, and one source guard proving no write escapes the guard.
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **The decodeCall requests are pure functions of line text and column.** `composer-commands.ts`
   carries no document state, so re-running a decode on identical text yields an identical result;
   that is what makes "compare the fresh decode to the captured one" a valid staleness test rather
   than a heuristic. If the server side ever gained state, the guard would start reporting spurious
   mismatches — visible as an abort with a balloon, never as a corrupted edit.
2. **Equality is field-wise rather than canonical-JSON.** Both were open; field-wise wins because the
   comparison then names exactly which fields matter, is readable in review, and needs no JSON
   library on the plain-Java classpath. The cost is that a future field added to a decode DTO must be
   added to the comparator too — which the comparator's javadoc says explicitly.
3. **A line inserted above the call aborts the edit.** The captured line index no longer points at the
   call, the re-decode at that index finds nothing, and the user gets a warning balloon offering to
   reopen. This consequence is accepted deliberately; relocating a moved call is a deferred idea.
4. **The guard assumes it is called on the dispatch thread.** Every caller is a continuation that has
   already returned from `dialog.showAndGet()`, which only returns on the dispatch thread. The
   document reads in the guard's first step therefore need no extra hop; the write does hop, because
   it happens after the async re-decode.
5. **The balloon and the "Reopen composer" action are proven by UAT.** C-01 keeps the notification
   platform off the test classpath; the guard's decisions are tested behaviourally and the rendering
   is confirmed live (D-12, item 3).

  <action>
    **(a) The comparator.** Create `DecodeEquality` in `com.basis.bbj.intellij.composer` as a final
    class with a private constructor, carrying no `com.intellij` import. This task adds only
    `public static boolean sameMsgbox(MsgboxDecodeResult a, MsgboxDecodeResult b)`; the two window
    comparators are Task 2's.

    `sameMsgbox` returns true when both arguments are null, false when exactly one is, and otherwise
    compares field by field: `found`; the `edit` payload's `callStart` and `callEnd` (with a null
    `edit` on one side only counting as different); `trailingArgs` as a list; and the whole `initial`
    payload — `message`, `title`, `assignTo`, `buttonSet`, `icon`, `defaultButton`, `flags`,
    `customButtons`, `trailingArgs`, `editMode` and `useConstants`. Use `java.util.Objects.equals`
    throughout so null on either side is handled without a branch per field.

    Comparing `initial` and `trailingArgs`, not only the ranges, is the substance of the decision: the
    dialog's result was computed from the pre-dialog call's arguments, so if those changed underneath
    it the composed statement no longer reflects what the user was looking at, and aborting is the
    safe answer even when the ranges happen to line up. Say that in the method's javadoc, and add a
    sentence stating that a field added to a decode DTO must be added here too — the comparator is
    the contract, not the DTO.

    **(b) The guard.** Create `StaleEditGuard`, a final class with no `com.intellij` import, carrying
    two nested interfaces and four injected collaborators in one constructor, following
    `BackendNoticePolicy`'s shape:

    - `public interface DocumentView { int lineCount(); String lineText(int line); long modificationStamp(); }`
    - `public interface WriteGate { void runWriteCommand(Runnable body); }`
    - fields: a `DocumentView`, a `WriteGate`, a `Consumer<Runnable>` run-on-EDT executor, a
      `Consumer<ComposerNotices.Notice>` notifier, and a `long` wait; plus
      `public static final long REDECODE_TIMEOUT_MILLIS = 10_000L`.

    One generic method:
    `public <D> CompletableFuture<Void> applyIfUnchanged(String kindLabel, int capturedLine,
    int capturedCol, D capturedDecode, BiFunction<String, Integer, CompletableFuture<D>> reDecode,
    BiPredicate<D, D> sameDecode, Runnable applyEdit)`.

    Its body, in this order and no other. First, on the calling thread — which is always the dispatch
    thread, because every caller has just returned from a modal dialog — treat a null
    `capturedDecode`, a negative captured line, or a captured line at or beyond `view.lineCount()` as
    a stale document: notify with `ComposerNotices.staleDocument(kindLabel)`, issue no request, and
    return an already-completed future. Otherwise read the current text of the captured line and the
    current modification stamp into local variables; these two reads are the snapshot everything else
    is judged against.

    Second, call `reDecode.apply(currentLineText, capturedCol)`, bound it with the same idiom the flow
    seam uses — take the future's `copy()` and apply the wait to that, never to the receiver the
