<objective>
Close the second half of #538: the three composer dialogs' `refresh()` chains. Each one issues a
preview request per keystroke and observes only its success — a failure is never observed at all, so
the OK button keeps whatever enabled state the last good preview left and the user can accept a
statement that no longer reflects what the server would produce. This plan routes all three through
the flow seam 82-01 built, adds an in-dialog "Preview unavailable" state that disables OK, clears
that state on the next success, and rate-limits the balloon to one per dialog session so a keystroke
storm during a server restart does not become a balloon storm.

Purpose: COMP-01 asks for a terminal handler on *every* composer chain, launcher and dialogs alike.
The dialog half is where the user-visible harm lives — a stale statement that OK will happily
accept — and it is also where a naive fix produces a new problem, because the refresh chain fires per
keystroke. The sequence counter each dialog already keeps is the arbiter for both outcomes, and the
rate limiter keeps the notification honest.

Output: `observe(...)` and `once(...)` on `ComposerFlow`, the three rewritten `refresh()`/`apply()`
pairs, six more behavioural tests, and one source guard covering all three dialogs.
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **The dialogs' behaviour is proven by the seam plus source guards, not by driving the IDE.**
   `DialogWrapper` and `setOKActionEnabled` need the platform, which C-01 keeps off the test
   classpath. Everything that can be a pure function — the observe chain, the sequence discard and
   the rate limiter — is tested behaviourally; the three wiring sites are asserted as source facts
   and confirmed live at UAT (D-12, item 1).
2. **The summary label is the "existing error/summary label" D-05 names.** MSGBOX has `summary`
   alongside three field-specific error labels; the two window dialogs have `flagsSummary` and
   `eventSummary` and no error label at all. `summary`/`flagsSummary` is the one label each dialog's
   `apply()` already rewrites on every successful preview, which is what makes "clear on next
   success" fall out of the existing code rather than needing new state.
3. **The window dialogs never called `setOKActionEnabled` before.** MSGBOX gates OK on
   `preview.valid`; the two window dialogs leave OK always enabled. Adding
   `setOKActionEnabled(true)` to their `apply()` is therefore a new call whose only purpose is to
   undo the failure state — it must not become a general validity gate, which those dialogs do not
   have and this phase does not add.
4. **10 s for a preview and 30 s for a launch.** A preview is a pure local computation on the server,
   so a wait an order of magnitude shorter than the launch chain's is right; the number exists so a
   lost response cannot leave OK disabled forever, not to police server latency.

    `public static final long REFRESH_TIMEOUT_MILLIS = 10_000L;` — an order of magnitude below the
    launch wait, because a preview is a pure local computation on the server.

    `public <T> CompletableFuture<Void> observe(CompletableFuture<T> request, long timeoutMillis,
    Consumer<T> onSuccess, Consumer<Throwable> onFailure)`. Bound the request the same way `launch`
    does — take its `copy()` and apply the wait to that, never to the receiver the LSP4IJ proxy owns.
    Terminate with exactly one handler. On a throwable, dispatch `onFailure` through the injected EDT
    executor. On a normal completion with a null value, dispatch `onFailure` too, with a throwable

    success. On a normal completion with a non-null value, dispatch `onSuccess` through the same
    executor. Return the terminal future so nothing in the package is left unobserved.

    because only the caller knows whether its sequence number is still current, and a superseded

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| composer dialog → language server | Every keystroke sends a preview request over the LSP4IJ proxy while the dialog is modal |
| language server → dialog UI | The preview payload drives the statement text, the summaries, the schematic and the OK button's enabled state |
| language server → IDE balloon/console | Refresh failures are surfaced through the same notice seam and notification group as launch failures |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-82-07 | Tampering | OK accepted while the previewed statement is stale | high | mitigate | A failed or null preview whose sequence is current disables OK and labels the dialog "Preview unavailable"; OK is re-enabled only by a successful preview. The source guard asserts one `setOKActionEnabled(false)` and one sequence check per path in each of the three dialogs. |
| T-82-08 | Repudiation | a refresh failure that reports nothing | high | mitigate | Every refresh request is terminated by one handler in the flow seam; a throwable, a timed-out wait and a null payload all reach the failure callback, which always writes the in-dialog label. `ComposerFlowTest` Tests 8, 9 and 10 pin the three inputs. |
| T-82-09 | Denial of service | a balloon storm during a server restart | medium | mitigate | The dialog's notifier is a one-shot wrapper using an atomic check-and-set, so however many keystrokes fail, one balloon is raised per dialog session; the per-keystroke state lives in the label. Tests 12 and 13 pin both the limit and its per-session scope. |
| T-82-10 | Denial of service | a preview request that never completes leaving OK disabled forever | medium | mitigate | The observe chain is bounded by a 10 s wait applied to a `copy()` of the proxy's future; an elapsed wait renders the failure path, and the next successful keystroke restores OK. |
| T-82-11 | Tampering | a stale response overwriting a newer one | high | mitigate | Both callbacks check the captured sequence number against the dialog's counter before touching anything, and the check precedes the notifier so a superseded failure cannot consume the session's balloon allowance. | T-82-12 | Denial of service | the EDT | high | mitigate | The request stays on the LSP4IJ future; both callbacks are dispatched through the injected executor using the dialog's existing `ModalityState.any()`. No blocking wait is added on the dispatch thread. |
