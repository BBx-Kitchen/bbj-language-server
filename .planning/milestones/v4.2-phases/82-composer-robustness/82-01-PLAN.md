<objective>
Make a failed composer request visible. Today `ComposerLauncher.launch()` runs a three-level nested
continuation pyramid in which each inner level returns a fresh future nobody observes, so a server
restart, a dropped connection or a hung request produces nothing at all — no balloon, no console
line, no log entry (#538). This plan replaces that pyramid with one composed chain behind a
plain-Java flow seam that has a single terminal handler and a bounded wait, and routes every failure
through one plain-Java notice seam rendered as a balloon in the existing "BBj Language Server"
notification group.

Purpose: COMP-01 requires a terminal handler on every composer chain plus a regression test that
forces one chain to fail and asserts the notification. It also sets the failure-surfacing convention
that 82-03's stale-offset guard inherits rather than inventing a second one — the exact build order
PITFALLS.md Pitfall 12 and ARCHITECTURE.md's Wave 6 call for.

Output: `ComposerNotices` (the presenter), `ComposerFlow` (the orchestration seam), the
`ComposerNoticeRenderer` balloon/console call site, a rewritten `ComposerLauncher.launch()`, two
behavioural test classes and one source guard.

Scope note: CONTEXT.md D-11 proposed two plans for the phase. The phase ships as three
(82-01 launcher chain, 82-02 dialog refresh chains, 82-03 stale-edit guard) purely because the
launcher slice alone fills a task's file budget; nothing is dropped, deferred or simplified, and
D-11's actual constraint — COMP-01 green before the COMP-02 production change begins — is preserved
by the wave ordering.
</objective>

## Executor shell and file-access rules (CLAUDE.md — follow verbatim)

A Phase 80 executor stalled for 20 minutes on an unanswered `cd …; git diff` permission prompt. These
rules keep the run autonomous:

- Search and read with the built-in `Grep`, `Glob` and `Read` tools first. Fall back to shell
  `grep`/`find`/`cat` only when a built-in genuinely cannot do the job (for example a pipeline).
- Every shell path is absolute and complete from `/home/coder/repos/bbj-language-server/…`. Never
  rely on the current working directory; never use `.`, `..` or `~` as a search target.
- Never chain `cd` with `grep`, `find`, `cat`, `sed`, `head`, `tail` or `git`. Use
  `git -C /home/coder/repos/bbj-language-server …`. `cd` is acceptable only directly in front of
  `./gradlew` or `npm`/`npx`.
- No bare recursive `grep -r` or `find` over a directory. Scope with `--include`/`-name` or use the
  `Grep` tool with a `glob`. Never point any read at `.env*`, `*.pem`, `*.key` or a credential store.
- Stage commits with `git add <exact path>` only — never `git add -A` or `git add .`.
- The IntelliJ module's JDK is `JAVA_HOME=/opt/java/default`; every Gradle command in this plan
  carries it.

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **A test double implements `BbjComposerServer` directly.** The interface extends lsp4j's
   `LanguageServer`, so the double must also stub `initialize`, `shutdown`, `exit`,
   `getTextDocumentService` and `getWorkspaceService`. Those five are stubbed to throw
   `UnsupportedOperationException`, which is correct — the flow seam must never call them, and a
   future lsp4j generation that adds an abstract method to `LanguageServer` will break the test's
   compilation loudly rather than silently changing behaviour. Phase 83's BUILD-05 canary work is
   the place that coupling gets pinned deliberately.
2. **The bounded wait is a backstop, not the real timeout.** 30 s for the launch chain matches the
   language server's own compile timeout and sits under Phase 81's 45 s client wait. It exists so a
   lost response cannot leave a composer invocation silent forever; if UAT ever sees it fire before
   the server's own timeout, the two numbers need re-balancing rather than a new mechanism.
3. **The balloon itself is proven by UAT, not by a test.** C-01 keeps the platform off the test
   classpath, so every decision that can be a pure function lives in the two seams and is tested;
   the rendering call site is asserted as a source fact and confirmed live (D-12).
4. **`copy().orTimeout(...)` rather than `orTimeout(...)` on the proxy's own future.** `orTimeout`
   completes the receiver exceptionally, and the receiver here belongs to the LSP4IJ proxy. Timing
   out a copy leaves the proxy's future untouched. If a future LSP4IJ version returns a future that
   does not support `copy()`, the symptom is a compile error in `ComposerFlow`, not a runtime
   surprise.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IntelliJ composer → language server | Caret line text and column cross into the `bbj/composer/*` custom LSP requests over the LSP4IJ proxy |
| language server → IDE balloon/console | Server-side failures and throwable text are rendered in a notification balloon and mirrored to the language-server console |
| user editor state → composer chain | The caret's line, line text and column are captured on the EDT and carried across an async boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-82-01 | Repudiation | `ComposerLauncher.launch()` chain | high | mitigate | The nested continuation pyramid is replaced by one composed chain with a single terminal handler that maps every throwable to a `REQUEST_FAILED` notice and every null stage to `NOT_READY`; the source guard fails the build if any continuation reappears in the launcher. `ComposerFlowTest` Tests 1 and 2 pin the outer and innermost failures. |
| T-82-02 | Denial of service | a composer request that never completes | medium | mitigate | Every stage is bounded by a wait measured in seconds applied to a `copy()` of the proxy's future, so the receiver the proxy owns is never force-completed; an elapsed wait renders `REQUEST_FAILED` with a timed-out body (`ComposerFlowTest` Test 5). |
| T-82-03 | Denial of service | the EDT | high | mitigate | The chain stays on the LSP4IJ futures; only the success continuation is handed back through the injected run-on-EDT executor with the launcher's existing default modality. No blocking wait is introduced anywhere on the dispatch thread. |
| T-82-04 | Information disclosure | throwable text rendered in a balloon and the LS console | low | accept | The text is the local language server's own failure describing the user's own file; Phase 81 already renders equivalent text in the same group and console, so no new boundary is crossed. ASVS L1 local boundary. |

| T-82-06 | Spoofing | a notice attributed to the wrong composer | low | mitigate | The kind label is derived from the `Kind` enum by one private mapping used by every notice, so a balloon can never name a composer other than the one invoked. |
| T-82-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager install task exists in this plan; `build.gradle.kts` is asserted unchanged and no dependency is added or upgraded. |
