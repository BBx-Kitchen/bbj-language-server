verify, extract, install, record and cleanup as private statics wired directly to the IntelliJ

cleanup 79-REVIEW recorded as IN-03.

be covered by regression tests that `./gradlew test` runs green. The Windows-branch tests are also
this phase's attempt to reproduce the Windows auto-install failure recorded in 80-UAT.

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **`Files.isExecutable` is host-dependent, so the pipeline reads it through an injected probe.**
   On Linux a file copied without a chmod is not executable, so a Windows-target cache-hit case run
   on this Linux host would answer "not cached" for a file that a real Windows host would accept.
   The seam therefore takes `NodeExecutableResolver.PathProbe` as a collaborator (production:
   `NodeExecutableResolver.REAL_FILESYSTEM`) rather than calling `Files.isExecutable` directly.
   This is a reuse of an existing seam, not a new one.
2. **A fixture's pinned digest is a literal in the test, not computed in the test.** Computing the
   expected digest from the same bytes the verifier reads would make the verify step vacuous. The
   executor computes each digest once with `sha256sum`, writes it into the test and into the
   fixtures README; changing a fixture without updating the pin then fails a test, which is the
   intent.
3. **The Windows branch is exercised on Linux, never on Windows.** CI has `ubuntu-latest` runners
   only. The Windows-branch tests prove the pipeline's own branch logic; they cannot prove Windows
   filesystem or process behaviour. If they all stay green, the SUMMARY must say the 80-UAT
   auto-install failure was not reproducible from the pipeline logic alone and a todo must ask for a
   live Windows check with `idea.log` and the contents of the plugin's `bbj-intellij-data/nodejs`
   directory.
4. **Zip-slip is structurally impossible in the current extractor and stays that way.** The zip
   branch writes only to `destDir.resolve("node.exe")` regardless of the entry's own name, so a
   crafted entry path cannot escape. The tar branch delegates path handling to the external `tar`,
   and its only defence is that verification precedes extraction. Both facts are pinned by guards
   rather than changed.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| nodejs.org → plugin data directory | A downloaded archive crosses from the network into a temp file, then into an extraction directory, then into the plugin's Node data directory as an executable |
| archive entry names → local filesystem paths | Zip entry names and tar member names are attacker-influenceable strings that a naive extractor would resolve into filesystem paths |
| temp extraction directory → the rest of the filesystem | The recursive cleanup walks a directory whose contents came from an archive, and could follow a link out of it |
| committed test fixtures → the test JVM | Four archives in the repository are extracted for real by the test suite |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-83-01-01 | Tampering | zip extraction path handling | high | mitigate | The zip branch writes only to `destDir.resolve("node.exe")` and never to the entry's own name, so a `../`-bearing entry cannot escape the destination. The property is preserved by the move and pinned by a scoped guard inside the extraction method's body. |
| T-83-01-02 | Tampering | tar extraction path handling | high | mitigate | Path handling is delegated to the external `tar`, so the defence is ordering: `NodeArchiveVerifier.verify` runs against the source-pinned digest before extraction, and a guard asserts verification precedes extraction inside `install`'s body. A mismatched archive is never handed to `tar`. |
| T-83-01-03 | Tampering | symlink-following recursive delete (79-REVIEW IN-03) | high | mitigate | The recursive delete uses a `Files.walkFileTree` visitor with no follow-links option, so a link inside the extraction directory is deleted as a link. Regression test plants a link aimed outside the directory and asserts the target survives; a guard asserts the follow-links option name is absent from the file. |
| T-83-01-04 | Tampering | an unverified archive reaching install | high | mitigate | A non-verified `NodeArchiveVerifier.Result` throws before the extraction directory is even created; the behavioural test asserts nothing was extracted and nothing installed. |
| T-83-01-05 | Spoofing | the download URL | medium | mitigate | The URL is assembled from a pinned version, a pinned base URL and an injected target, and the resulting archive name must have an entry in the pinned digest table; the six-combination test fails if any pair produces a name with no pin. |
| T-83-01-06 | Information disclosure | temp archive and extraction directory left behind | medium | mitigate | Both are created under a configurable temporary root and deleted in `finally` blocks on every path; the tests assert the temporary root is empty after success, after a verify failure, after a missing-binary failure and after a cancel. |
| T-83-01-07 | Denial of service | a completion that throws inside the drain loop | medium | mitigate | `DownloadCompletions.dispatch` isolates each hand-over, so one failing editor-banner refresh cannot swallow the other waiting callers'. |
| T-83-01-08 | Elevation of privilege | the executable bit on the installed binary | low | accept | The bit is set only on non-Windows targets, on a file the plugin itself just wrote into its own data directory, from a digest-verified archive. ASVS L1 local boundary. |
| T-83-01-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager install task exists in this plan; `build.gradle.kts` is not modified and no dependency is added or upgraded. The four fixture archives are built locally from plain ASCII files, not downloaded. |
