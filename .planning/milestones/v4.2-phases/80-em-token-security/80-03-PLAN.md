<objective>
Tell the user, once per distinct backend, when IntelliJ is not keeping the Enterprise Manager token in
the native OS keychain — and keep the whole internal-API dependency inside one method.

Purpose: `BbjEMTokenStore` calls `PasswordSafe.getInstance()` with no idea which store resolved behind
it. On a machine where PasswordSafe is set to KeePass or to memory-only, the EM JWT is protected far
less than the user assumes, and nothing says so. #552 asks for a one-time notification naming the
backend. The backend is only visible through `PasswordSafeSettings`/`ProviderType`, which are
`@ApiStatus.Internal` on the pinned `ideaIC-2024.2` platform, so research Pitfall 7 requires the access
to sit behind a single narrow method — and requires that a detection failure warns rather than
silently passing as keychain, which would defeat the point of the issue.

Output: a plain `TokenBackend` enum, a plain `BackendNoticePolicy` seam with injected collaborators, a
single `resolveBackend()` method, a WARNING balloon in the existing notification group, and
red-then-green JUnit 5 coverage. This plan is 80-03 of the four-plan split (D-18); it runs in wave 2
because it edits `BbjEMTokenStore.java`, which 80-01 rewrites in wave 1.
</objective>

1. **The `PasswordSafeSettings` accessor shape is assumed to be an application service.** CONTEXT.md
   confirms the class, `getProviderType()` and the `ProviderType` constants exist in `app-client.jar`

   `ApplicationManager.getApplication().getService(PasswordSafeSettings.class)` first; if that does not

   compiled in the SUMMARY — this is exactly the internal-API fragility D-11 isolates.

   "Open Password Settings" action uses the public
   `ShowSettingsUtil.getInstance().showSettingsDialog(project, "Passwords")`. If the page does not open
   in the manual UAT below, record the working selector in the SUMMARY and adjust — do not drop the
   action, and do not silently point it at the plugin's own settings page.
3. **`DO_NOT_STORE` is folded into `MEMORY_ONLY` per D-11.** The user-facing consequence is the same
   (the token does not outlive the session), so the balloon text for both says the token is kept in
   memory only. If a reviewer wants the two distinguished, that is a text change, not a structural one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IDE-wide PasswordSafe configuration → the plugin's credential storage | An IDE or organisation policy the plugin does not control decides how strongly the EM JWT is protected |
| Internal platform API (`PasswordSafeSettings`, `ProviderType`) → plugin code | An unversioned, `@ApiStatus.Internal` contract crosses into the plugin |
| Plugin → user-visible notification | The balloon text leaves the process and is visible to anyone at the screen |
