<objective>
Make the IntelliJ plugin's client-side EM JWT expiry check fail closed: every token that cannot be
positively decoded is treated as expired, and a token EM itself returns in an unusable shape is
rejected at login instead of being written to PasswordSafe.

Purpose: `BbjEMTokenStore.isTokenExpired()` has four independent `return false` sites (lines 58-60,
65-67, 77-79, 85-88). The last three are #535's fail-open branches — a two-part token, a payload with
no `exp`, and any decode/parse exception all report "not expired", so the plugin hands an
unverifiable token to the run path. Fixing them as three separate edits is exactly the partial-fix
failure mode research Pitfall 5 describes, so D-03 replaces them with one three-valued classification.
D-05 closes the matching hole at the other end: `performLogin()` stores whatever non-empty,
non-`ERROR:` text `em-login.bbj` wrote without ever decoding it, so without the login gate a non-JWT
login result would "succeed" and then every Run would report the token expired.

Output: a plain-Java `JwtValidity` classifier beside `BbjEMTokenStore`, `isTokenExpired` reduced to a
fail-closed delegate, the login-time gate, and red-then-green JUnit 5 coverage under `./gradlew test`.
This plan is 80-01 of the four-plan split (D-18) and must be merged before 80-04 builds its trust
cache on top of the expiry check (STATE.md sequencing constraint).
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **TOKEN-01's `ordering` edge-probe row is unresolved.** The probe asks whether output order is
   specified and stable when elements compare equal. `check` returns a single scalar classification
   for a single token — there is no collection, no comparison of equal elements and no output order to
   specify. The row is left unresolved rather than resolved against a fabricated criterion. If a
   reviewer disagrees, the nearest real property is purity: `check` holds no state between calls, so
   the same `(token, now)` pair classifies identically regardless of call order. That property is
   implied by the class having no fields, which Task 1's acceptance criteria assert.
2. **`em-login.bbj`'s output shape is assumed to be a bare 3-part JWT.** D-05 turns anything else into
   a login failure. If a deployment's EM wraps the token (whitespace, a prefix, a JSON envelope),
   login now fails where it previously "succeeded" and then failed on every Run. The message is
   deliberately specific so that case is diagnosable on sight; the trailing `.trim()` already applied
   to the subprocess output is preserved so trailing whitespace alone cannot cause it.
