<objective>
Close G-80-1: widen the Windows owner ACE by exactly the two extended-attribute bits Windows
requires for a `GENERIC_READ`/`GENERIC_WRITE` open, so BBj can actually open the owner-only temp
file the plugin created for it.

Purpose: 80-02 gave the Windows temp file a single `ALLOW` ACE carrying eight permissions. Windows'
`CreateFile` folds `FILE_READ_EA` into `GENERIC_READ` and `FILE_WRITE_EA` into `GENERIC_WRITE`, and
an access check denies the whole request when any single requested bit is ungranted. `em-login.bbj`
opens that file at line 49 with `open(ch,mode="O_CREATE,O_TRUNC")outputFile!`, so the open is denied
in full and BBj reports `!ERROR=18 ... User not allowed`. Java's `AclEntryPermission.READ_NAMED_ATTRS`
and `WRITE_NAMED_ATTRS` map 1:1 onto those two native bits and the JDK writes exactly the bits it is
given — no generic expansion. The POSIX branch has no extended-attribute sub-permission (owner
read+write is one coarse unit), which is why Linux, macOS and the `ubuntu-latest`-only CI never see
this, and why 80-02 carried it as a pre-flagged, never-executed assumption. The same helper backs
`bbj-em-validate-*.tmp`, so Windows token validation is affected identically and is fixed by the same
two lines.

Output: `OWNER_PERMISSIONS` at ten permissions instead of eight, a widened floor assertion, a named
regression test for the two bits, a source guard scoped to the initializer, and the Windows recheck
carried forward as a human UAT item — this repository has no Windows runner and this plan does not
pretend otherwise.
</objective>

**Gap G-80-1 (blocker, UAT test 1, TOKEN-02, #536).**

Reported: `!ERROR=18 ([C:\Users\beff\AppData\Local\Temp\bbj-em-login-8853933440741698129.tmp] User not
allowed)` at `[49] open(ch,mode="O_CREATE,O_TRUNC")outputFile!` in `em-login.bbj`, IntelliJ IDEA
2026.2, Windows host, plugin installed. The login never completes.

Root cause (diagnosed, CONFIRMED, in `.planning/debug/windows-owner-only-tmp-error18.md`):
`OwnerOnlyAcl.OWNER_PERMISSIONS` omits `READ_NAMED_ATTRS` and `WRITE_NAMED_ATTRS`. Per Microsoft's
documented generic-rights mapping, `GENERIC_READ` expands to `STANDARD_RIGHTS_READ | FILE_READ_DATA |
FILE_READ_ATTRIBUTES | FILE_READ_EA | SYNCHRONIZE` and `GENERIC_WRITE` to `STANDARD_RIGHTS_WRITE |
FILE_WRITE_DATA | FILE_WRITE_ATTRIBUTES | FILE_WRITE_EA | FILE_APPEND_DATA | SYNCHRONIZE`. Comparing
that against the eight-permission set, the *only* uncovered bits are `FILE_READ_EA` and
`FILE_WRITE_EA`. Adding the two Java permissions that map onto them makes the single owner ACE cover
the entire `GENERIC_READ|GENERIC_WRITE` request, which is exactly what a surgical fix means here:
ten permissions, not the fourteen a full-control grant would carry.

What is being closed, from the gap's `missing:` list:
1. Add `AclEntryPermission.READ_NAMED_ATTRS` and `AclEntryPermission.WRITE_NAMED_ATTRS` to
   `OwnerOnlyAcl.OWNER_PERMISSIONS`, still exactly one `ALLOW` ACE for the owner, no inherit flags.
2. Update `OwnerOnlyAclTest`'s floor assertion and add a regression test asserting the two
   named-attribute bits.
3. Re-run the manual Windows icacls/write-through check (UAT test 1) — CI has no Windows runner.

Item 3 is a human step. It is **not** a task in this plan, because no Windows host is reachable from
this environment; it is carried into the SUMMARY as a human UAT item and re-run by
`/gsd-verify-work` when a Windows host is available. This plan closes items 1 and 2 and makes the
Windows recheck the stated acceptance recheck for the gap.

**Residual risk to record, not to pre-emptively fix.** The debug session downgraded but did not
disprove a second lead: that `bbj.exe` might run under a different Windows identity than the account
the ACE names. The permission-floor gap is independently sufficient to produce the exact reported
symptom, so it is fixed first and alone. If the Windows recheck still fails after this change, the
next diagnostic step is to capture `icacls` output for the temp file alongside the identity the BBj
process actually runs as — not to widen the ACL further on speculation. The documented escalation, if
and only if a same-account open is proven still denied, is granting the owner full control (all
`AclEntryPermission` values in one `ALLOW` entry — still owner-only). Do not take that step in this
plan.
</gap_context>
