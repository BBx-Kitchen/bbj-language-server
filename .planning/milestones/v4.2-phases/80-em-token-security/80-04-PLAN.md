<objective>
Stop re-running the 10-second `em-validate-token.bbj` subprocess on every Run when the same token was
already validated moments ago, without letting the trust record outlive a logout, a re-login, or a
different token value.

Purpose: `BbjRunBuiAction` and `BbjRunDwcAction` each call `validateTokenServerSide(project, token)`
unconditionally right after the expiry check (lines 76-85 of each, identical apart from the client
name), so the edit-run-edit loop #542 describes spawns a BBj subprocess and waits up to 10 seconds on
every launch. Nothing in the module records that a validation already happened. The cache that fixes
this is exactly the construct research Pitfall 6 warns about: built on a fail-open expiry check, or
keyed on "a token exists" rather than on the bytes, or invalidated only by a timer, it widens the
vulnerability instead of duplicating it. So it lands last (D-18, STATE.md sequencing constraint), keyed
on a SHA-256 of the token bytes, invalidated unconditionally by both store mutations, with a five-minute
window that is a UX optimisation and never the only thing between a revoked token and a successful run —
`web.bbj` still presents the token to EM at launch.

Output: a plain-Java `TokenValidationCache` beside `BbjEMTokenStore`, one base-class read-through entry
point, the two duplicated blocks collapsed onto it, and red-then-green JUnit 5 coverage.
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **The trust window is a UX optimisation, and its risk is explicitly accepted.** For up to five
   minutes after a successful validation, a token revoked in EM will skip the plugin's server-side
   check. It will still fail at launch, because `web.bbj` presents the token to EM every time. If a
   reviewer judges five minutes too long, D-15 permits lowering it to no less than 60 seconds by
   changing one constant; it may not be raised.
2. **Concurrent cold-cache Runs may each validate once.** The `AtomicReference` swap guarantees the
   entry is never torn and never partially written, but two Runs that both miss before either records
   will both spawn the subprocess. That is at most two calls where the old code made two calls anyway,
   so it is a strict improvement — stated as the guarantee rather than hidden.
3. **The digest is not a secrecy boundary against an attacker who already reads process memory.** It
   prevents the plaintext token from being retained in a long-lived static field and from appearing in
   a heap dump of the cache, which is the property Pitfall 6 asks for; it is not protection against a
   debugger attached to the IDE.

    State: `public static final long TRUST_WINDOW_MS = TimeUnit.MINUTES.toMillis(5);` — one constant,
    five minutes (D-15). A private immutable `record Entry(byte[] tokenDigest, long validatedAtMillis)`.
    A `private final LongSupplier clock` and a `private final AtomicReference<Entry> entry = new AtomicReference<>()`.
    `public static final TokenValidationCache SESSION = new TokenValidationCache(System::currentTimeMillis);`
    is the single production instance; the constructor is package-private so tests inject a fixed clock,
    exactly as `BbjNodeVersionCache` does.

    `private static byte[] digestOf(String token)` computes `MessageDigest.getInstance("SHA-256")` over
    `token.getBytes(StandardCharsets.UTF_8)`. The token plaintext is never stored in a field, never
    logged and never returned — the digest is the only retained representation (D-14, Pitfall 6).

    `public boolean isTrusted(@Nullable String token)` returns false for a null or empty token, false
    when there is no entry, and otherwise true only when `MessageDigest.isEqual(entry.tokenDigest(), digestOf(token))`
    and `clock.getAsLong() - entry.validatedAtMillis() <= TRUST_WINDOW_MS`. A different token value is a
    miss by construction because the digest differs. Expiry is evaluated here, on read — there is no
    timer and no background thread (D-16).

    `public void recordValidated(@NotNull String token)` swaps in `new Entry(digestOf(token), clock.getAsLong())`
    through the `AtomicReference`. `public void invalidate()` sets the reference to null. Both are single
    atomic swaps of an immutable value, so a concurrent reader sees either the old entry or the new one
    and never a torn one.

    read-through entry point and the only decision site: when `isTrusted(token)` is true return true
    without calling `serverCheck`; otherwise run `serverCheck.getAsBoolean()`, call `recordValidated`
    only when it returned true and the token is non-null and non-empty, and return that result. A false

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stored JWT → the EM server-side validation subprocess | The only place the plugin learns a token is still accepted by EM |
| Cached trust verdict → the next Run's launch decision | A remembered verdict substitutes for a live check for up to the window |
| Token plaintext → any retained in-process state | A long-lived static holding the token would be a new disclosure surface |
