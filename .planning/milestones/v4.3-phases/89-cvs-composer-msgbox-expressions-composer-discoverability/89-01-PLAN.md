<objective>
Deliver the first working composer cue end-to-end on the shared language server and in VS Code:
a server-side `textDocument/codeLens` that marks every `addWindow(...)` call with a plain-text
`Compose addWindow` cue (D-04, D-05), visible without placing the caret (D-06), and a VS Code
`bbj.openComposerAt` command that opens the existing addWindow composer from that cue.

This plan introduces the new primary representation of a composer cue — one shared server-side
lens, per D-01 — and proves the whole path on one composer kind before later plans add MSGBOX,
addChildWindow, CVS and SETOPTS (plan 89-09) and route config files (plan 89-11). It also proves
Roadmap Success Criterion 5: cue positions come from the text and CST the document build already
produced, with no re-parse per request (Pitfall 11).

Purpose: DISC-01 (#650) — a persistent, clickable cue on composer lines in both IDEs. IntelliJ
renders this same LSP response through LSP4IJ's Code Vision bridge (plan 89-04 adds the click
target, plan 89-06 runs the render spike).
Output: the cue contract module, the Langium CodeLensProvider, a bounded handler, and the VS Code
click command, each with unit tests.
</objective>
