<settled_facts>
Research is disabled for this project; these were settled by reading the installed `vscode-languageclient` 10.1.0 sources and are not open questions.

- **`LanguageClient` has no `restart()` in 10.1.0.** `node_modules/vscode-languageclient/lib/common/client.d.ts` declares `needsStop(): boolean`, `isRunning(): boolean`, `start(): Promise<void>`, `stop(timeout?: number): Promise<void>` and `dispose(timeout?: number): Promise<void>`. The only `Restart` identifiers in the file are the `CloseAction.Restart` enum member and a `"restart"` string in an unrelated enum. A restart is therefore `stop()` then `start()` on the same instance — as D-10 anticipated.
- **Notification handlers survive stop→start on the same instance.** `client.js` keeps `_notificationHandlers`; on every `start()` it copies each entry into `_pendingNotificationHandlers` and re-registers them against the new connection. So the handlers registered in `activate()` remain live after a gate-driven restart, and constructing a second `LanguageClient` would be the only way to lose them.
- **`stop()` throws when the client is not running.** `shutdown()` returns early for `Stopped`/`Initial`, and otherwise throws `Client is not running and can't be stopped. It's current state is: <state>` unless the state is `Running`. The gate must therefore guard with `needsStop()` and catch, rather than calling `stop()` unconditionally.
- **`extension.ts` shape today.** `let client: LanguageClient` is module-level (line 36); `startLanguageClient()` constructs it and performs the one initial `client.start()` with a `.catch` that shows `BBj language server did not start: <detail>`; `deactivate()` calls `client.stop()`; the two existing status-bar items are created at priority 100 (suppression) and 99 (BBjCPL); the `bbj/resolvedConfigPath` listener at line 883 is the registration shape the new handler mirrors.
</settled_facts>

`request(delayMs)` clears the single stored timer handle, then schedules the restart action — the same cancel-then-schedule shape, so overlapping requests coalesce into one restart and the most recently requested delay wins. The module doc comment records why the gate reuses the *existing* client instance: the client re-registers its stored notification handlers on every `start()`, so a second instance would silently drop every handler `activate()` registered.
