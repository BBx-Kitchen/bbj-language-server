<objective>
Give the composer exactly one way to spell a BBj hex literal, and route every place that writes one
through it.

G-88-3 is two defects with one cause: there is no shared hex-literal formatter, so each generated
line kind hand-rolls its own syntax and two of them are wrong.

1. `setopts-catalog.ts:455/457` wraps the `$…$` mask in a literal pair of double quotes. Per
   `bbj.langium:949-950`, `STRING_LITERAL` and `HEX_STRING` are two distinct terminals, so
   `"$BFFF…$"` lexes as a 34-character plain string that is never hex-decoded — `AND()` then
   compares it against `opts$`'s 16 decoded bytes and BBj raises `!ERROR=17 (Strings must be the
   same length.)`. This was reproduced live by the tester and in-process against the production
   function.
2. The absolute edit-in-place path deletes the `$…$` wrapper: `setopts-in-code-request.ts:162`
   derives `hexRange` from the literal's CST node so it SPANS the delimiters (pinned by an existing
   test), while both writers — `setopts-composer-webview.ts:91-93` in VS Code and
   `ComposerLauncher.java:501` in IntelliJ — replace that range with bare digits, because that
   writer was built by #474 for config.bbx where bare hex IS correct, and 88-06 routed BBj-program
   absolute mode into it unchanged. Delimiters in, bare digits out, producing
   `SETOPTS 20C20240000000000000000000000000`.

This plan picks ONE side of that contract and fixes it there: `hexRange` keeps spanning the whole
literal token (its documented, test-pinned meaning), and the writers put a complete literal back.
Never both — that would double the delimiters. Choosing the writer side also normalises a
previously-generated bad line: replacing the whole token rewrites `"$00C2…$"` or `$00C2…$` alike
into one correct `$…$` literal.

Purpose: make the composer's output valid BBj wherever it is written, on both hosts, from one
formatter per host.
Output: `bbjHexLiteral` / `BbjHexLiteral.of`, both in-place writers corrected, and a test oracle
that can actually fail on a delimiter defect.

Explicitly out of scope:
  - The decoder's tolerance of the invalid quoted form (`parseHexLiteral`) and the test-fixture
    corpus written in that form — plan 88-11 owns those files.
  - Anything about G-88-2 (the IntelliJ Alt+Enter hang) — plan 88-12 owns that.
  - Declaring 88-RESEARCH.md Assumption A2 settled. Unit tests here prove the emitted TEXT; only a
    live BBjServices run proves the runtime accepts it, and plan 88-13 stages that check.
  - The config.bbx composer's own bare-hex syntax (#474). It is correct for that file format and
    must stay bare; this plan adds an explicit discriminator precisely so it cannot drift.
</objective>
