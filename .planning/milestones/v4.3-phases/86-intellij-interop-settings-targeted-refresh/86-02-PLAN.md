<settled_facts>
Research is disabled for this project; these were settled by reading the checked-in sources and the live install, and are not open questions.

- **The real key and its exact on-disk form.** `/opt/bbx/cfg/BBj.properties` line 67 of this dev container reads `com.basis.languageServer.addr=localhost\:5008\:true` — colons inside the value are escaped with a backslash, which is standard `java.util.Properties` escaping. The value after unescaping is `localhost:5008:true`, i.e. `host:port:enabled`.
- **Unescaping is delegated to `java.util.Properties`, not hand-rolled.** `Properties.load(Reader)` performs exactly the unescaping BBjServices' own writer produced, and handles every other properties escape correctly for free. The parser in this plan therefore takes an already-unescaped value and only splits and validates it. A hand-rolled backslash strip would be a second, weaker implementation of a documented format. The pure parser is still tested against a still-escaped value to prove that skipping the unescape step yields not-detected rather than a wrong port.
- **Duplicate keys resolve last-wins.** `Properties.load` stores each parsed entry, so a later occurrence of the same key replaces an earlier one. That is the ordering rule for a repeated `com.basis.languageServer.addr`, and it is pinned by a test rather than left implicit.
- **The existing detector is dead code against real installs.** `BbjSettings.detectJavaInteropPort` (lines 103-152) matches `java.interop.port=` or `bridge.port=` as substrings; neither appears in a real `BBj.properties`. It is removed in plan 86-03, which owns `BbjSettings.java`; this plan does not touch that file.
- **`getBBjClasspathEntries` stays as it is.** It is a separate hand-rolled line scan over the same file for a different key prefix. Rewriting it onto `Properties` is out of scope for this phase and would change behaviour for keys with escapes.
- **The stat-keyed memo shape to copy.** `BbjNodeVersionCache` uses a `ConcurrentHashMap.compute(...)` read-check-load-store under the map's per-bin lock, a `lastModified + ":" + length` stamp, injected collaborators through a package-private constructor, a `SESSION` static instance for production, and package-private `clear()`/`size()` probes for tests. Its javadoc explains why `compute` rather than `get`-then-`put`: two threads racing a miss for the same key would otherwise both load.
- **The result-record convention to copy.** `BbjSettingsLookups`' `NodeLookup`/`HomeLookup`/`ConfigLookup` are records with a trailing `failed` boolean and a documented rule that a failed result carries no information in its other fields. For the port, a failed read and a genuinely absent key produce the same user-visible outcome (5008 plus the same hint), so this plan deliberately collapses them into one `detected` boolean instead of carrying a separate `failed` flag — and says so in the record's javadoc.
- **`5008` is the language server's own `DEFAULT_PORT`** and is already the Java default of `BbjSettings.State.javaInteropPort`. IntelliJ's serializer omits a field equal to its Java default, which is exactly why an explicit 5008 cannot be represented by the integer alone and why the boolean flag in plan 86-03 exists.
</settled_facts>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|

| parsed file content → network target | The port parsed out of that file becomes the TCP port the java-interop health probe and the language server connect to (consumed in plan 86-03). |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-86-06 | Denial of Service | a malformed, truncated or hostile `BBj.properties` throwing out of the parser and breaking the Settings dialog or the health probe | high | mitigate | `readFrom` catches `IOException` and `RuntimeException` and returns the not-detected result; `parseAddrValue` has no throwing path for any input. The malformed matrix in the detector test enumerates null, empty, blank, host-only, four-segment, non-numeric, out-of-range and still-escaped values. |
| T-86-07 | Tampering | a port value outside the legal range, or a non-numeric value, being carried into a connection attempt | high | mitigate | The parser validates 1-65535 before reporting detection, and `sanitizePort` re-validates the persisted explicit port, so no reader can receive an out-of-range port from either source. |
