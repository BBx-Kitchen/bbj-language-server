## Planner assumptions

- D-05's example signature `runScriptToOwnerOnlyFile(argv, prefix, timeoutMs)` cannot work as one call: both builders put the output path inside argv, so the file must exist before argv is built. The runner module therefore has two entry points: `createScriptOutputFile(tmpFilePrefix)` makes the owner-only file, and `runScriptToOwnerOnlyFile(argv, outputFile, timeoutMs)` launches, reads, trims and always unlinks. Together they do everything D-05 lists, in one module with one test file. The split also lets each caller keep the creation at its base position relative to its own try (see the D-07 item below). It replaces the builder-callback signature of the earlier revision, which moved EM login's file creation inside the handler's try and so changed an error path.
- D-08 lets the runner live in process-runner.ts or next to em-auth. It must be next to em-auth (src/em-script-runner.ts): em-login-username.test.ts mocks process-runner.js with three named exports, so a fourth export there would be undefined under that mock and the test would need editing.
- D-08's "re-export" of getEMCredentials is a one-line delegating export in extension.ts, because D-14 forbids em-auth.ts from holding the secret storage in a module-level variable. em-auth's version takes the storage as an argument; extension.ts passes the activation's storage, which is the same object ensureValidToken uses (context.secrets).
- Per D-07 and the user's decision of 2026-09-29, no error path changes. EM login's four pre-launch steps (output-file creation, the login info string, argv building, the debug line) stay before the handler's outer try, so a failure there still rejects the command with the original error and shows no `EM login failed` message; a launch or read failure still becomes `EM login failed: Error: <stderr or message>`; the ERROR: and unusable-token messages are unchanged. EM validate had no step outside its try at base and still has none, so every failure still returns false. test/em-auth-error-paths.test.ts pins this: it is written and committed while the source is still the base, passes there, and passes unedited after the move and the fallback deletion; a source-order check pins the try boundaries. One base quirk is kept on purpose: a throw between creating an output file and the launch leaves the empty owner-only file behind, as the base does. Cleaning it up would need a new try around those steps, which is new behaviour.
- D-15 exception, approved by the user on 2026-09-29 as the single exception in this phase: 'both output-file paths in extension.ts are created through createOwnerOnlyFile before their launcher call' counted two create/launch pairs, which D-05 exists to merge into one. No file list makes `toBe(2)` hold afterwards, so that one test is re-expressed at equal or greater strength (in the runner, one create and one launch, each inside its own entry point, and an unlink in finally; in em-auth.ts, two creations pairwise before two runs and no direct create or launch; in extension.ts, no EM create, build or launch). It is the only expect() change in the phase: the Task 1 guard command proves exactly its three base count lines are gone, the file's expect lines outside the rewritten test are exactly the base's, and no-shell-command-construction's expect lines are byte-identical; plans 01, 02 and 04 edit no expect line of an existing test. Every other guard change is a file-list change. Plan 04's SUMMARY names it as the user-approved exception to D-15.
- D-10: the research check came back positive (five commands-cjs-execution tests drive a username/password credential through runWeb), so the branch stays per D-10's own rule. Roadmap criterion 3's "legacy branch gone" is met for the settings read (removed in Phase 112) and the stored-credentials fallback (this plan); the SUMMARY records the rest.
- ensureValidToken's `__token__` check stays as written (Claude's discretion; keeping it is the behaviour-neutral choice under D-11).
- The edge probe left REF-11 unclassified. The behaviour-neutral edge taken here: identical user-visible messages and the same escape-or-show outcome on every path (pinned by the error-path test), the same timeouts and temp-file names, and the same registration order (pinned by plan 02's test).
