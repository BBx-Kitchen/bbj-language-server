From bbj-vscode/test/bbj-test-module.ts (read this session):
- The constructor builds `const fakeJavaClasses: JavaClass[] = [createBBjApiClass(this.classpath), createHashMapClass(…), createJavaLangStringClass(…), createJavaLangClassClass(…), createSysGuiClass(…)]`. It pushes each class into `this.classpath.classes` and calls `this.resolveClass(clazz)`, then adds the classpath document. New classes go into this array, BEFORE the addDocument call; the research's Pitfall 1 rule to never add classes through a later seam still holds.
- `makeMethod(container, name, returnType, paramSpecs = [])` creates `isStatic: false`. `makeField(container, name, type, opts: { isStatic?: boolean } = {})`. resolveClass keeps a provided isStatic (`isStatic ?? false`).
- The createHashMapClass shape: `{ $type: JavaClass.$type, name: 'java.util.HashMap', packageName: 'java.util', $container: container, $containerProperty: 'classes', classes: [], fields: [], methods: [], constructors: [], deprecated: false }`, followed by `clazz.methods = [...]`.

How the linking block resolves (verified by a planning probe that ran the whole block against exactly this fixture: 41 passed, 1 pre-existing skip, 0 failed):
- `use java.util.Date`, `java.util.List`, `new java.util.LinkedList()`, `java.sql.Date.valueOf(…)` and `java.lang.Boolean.TRUE` resolve through the package tree that storeJavaClass builds (root packages via `javaInterop.getChildrenOf()`); none of them needs the global index. `valueOf` must be static and `TRUE` must be a static field, because a class-reference receiver offers static members only.
- `use java.util.Map.Entry` and `new java.util.Map.Entry()` need the nested class named 'java.util.Map.Entry' with packageName 'java.util' (dotted, not `$`). storeJavaClass stores it as 'Map.Entry' inside java.util, and the JavaSymbol scope finds it as 'Entry'.
- toString() on a BBj class: createBBjClassMemberScope in src/language/bbj-scope.ts (line 538) falls back to `javaInterop.getResolvedClass('java.lang.Object')` members.

The known side effect (planning ran the whole hermetic suite with this fixture): exactly one failed test, scope-cost-regression.test.ts "PREFIX member signature types stay preloaded despite body pruning (#505) > a signature type is preloaded while a body-local type stays pruned", with "expected [ 'java.util.ArrayList' ] to include 'java.util.List'". Its fixture text names `java.util.List` (a field type) and `java.util.Map` (a parameter type), and it spies on resolveClassByName expecting both to be requested. They are now preloaded, so the scope computation never asks for them.
