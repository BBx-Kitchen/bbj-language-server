## Planner assumptions

- **Sibling copies, not npm aliases.** The BBj sources import `langium` by its bare name, and each version needs its own generated files, so two full copies with real installs are required. npm aliases, which plan 05 used successfully for a grammar-string repro, cannot satisfy bare imports. The minimal package follows the same sibling pattern for the same reason.
- **Inputs are a superset of plan 05's, fixed now, before any real-server measurement.** They are plan 05's three unclosed-call strings, plus the three literal strings (with a trailing newline) from composer-codelens.test.ts, which the maintainer named as the suite that timed out. Likewise plan 05's DEF FN line, plus the literal text of the failing completion test. The thresholds and counts are plan 05's, unchanged. The "at least one input/document" verdict shape is also plan 05's.
- **Why the ladder passes the real parser config at the runtime-grammar rung.** Plan 05 built its parsers with createServicesForGrammar's defaults: recovery unset, case-sensitive, and the default token builder. The real server parses with recovery on, case-insensitive keywords, and every keyword in the ID token category. This is recorded as the reason the top-down route is not a repeat of plan 05, not as a diagnosis; the no-recovery rung measures it.
- **Runtime.** If each regressed 4.4.0 document costs about 2 s, the slowdown probe needs roughly a minute per configuration: 6 inputs times 4 runs. Hence the 600 s per-probe and 1500 s outer timeouts. The under-a-minute goal from CONTEXT's specifics applies to the deliverable, and it is reported rather than gated, because the iteration counts are fixed.
- **Node.** Measurements run on the container's Node 24, the Node the local suite runs on, and both versions share the binary. The generator runs on Node 22 only because langium-cli's own jsonschema dependency breaks on Node 24.
