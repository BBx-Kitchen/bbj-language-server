<objective>
Fix two already-diagnosed defects in the VS Code extension and the shared language server. Root causes are confirmed — this is implementation, not investigation.

**#671 — stale OutputChannel.** `activate()` captures the language client's own channel once and hands that object to `Commands.setOutputChannel(...)`. Because `clientOptions` pass no `outputChannel`, vscode-languageclient owns it (`_disposeOutputChannel = true`) and `client.stop()` disposes it through `cleanUpChannel()`; `start()` lazily creates a new one that nobody re-hands over. Every later write throws `Channel has been closed` (VS Code's `extHostOutput.ts` `validate()` guard). The fix is ownership: create the channel in `activate()`, pass it as `clientOptions.outputChannel`, dispose it through `context.subscriptions`.

**#672 — transient config read causes spurious restarts.** `defaultReadFile` swallows every read error and returns `null`; `evaluate()` maps `null` to `''` through `consumedConfigSnapshot`, which is indistinguishable from "the PREFIX line was deleted". One unreadable moment therefore emits `config-missing`, then `prefix-changed` when the identical bytes return: two restarts for zero content change. The fix is a three-way classification — content, absent, unreadable — where unreadable notifies nothing and leaves the snapshot untouched.

Purpose: the two defects compound. Each #672 restart disposes the #671 channel, which is what turns a silent performance annoyance into the user-visible "Channel has been closed" and a GUI run that never launches BBj.

Output:
- `extension.ts`: extension-owned channel, wired into `clientOptions`, plus a defensive append helper on the reload path
- `config-watcher.ts`: `ConfigReadResult`, `isAbsentReadError`, a new optional `readConfigFile` dep, and an unreadable read that returns before the snapshot moves
- the two committed repro test files inverted to assert the CORRECT behaviour
- three neighbouring suites' `vscode` mocks updated for the new channel ownership
