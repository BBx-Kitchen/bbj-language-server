<objective>
Fix GitHub issue #667: INPUT/READ/ENTER verification lists must accept a lone numeric literal or expression (for example `pick:(c)`, `n:(4)`, `n:(a+1)`), a lone `LEN=min,max`, and a verify list that is followed by further input items, while existing string- and hex-keyed options keep parsing exactly as today.

Purpose: valid BBj code (see the "inputlist" section of https://documentation.basis.cloud/BASISHelp/WebHelp/commands/read_verb.htm) currently gets red parser errors in both VS Code and IntelliJ, which share this language server.

Output: a two-line grammar change in `bbj.langium`, regenerated (gitignored) parser sources, #667 parser tests and a parse-only `.bbj` fixture.

Root cause, confirmed live at planning time against the committed grammar with a parser probe:
1. `VerifyOptions` in `bbj-vscode/src/language/bbj.langium` (around lines 634-636) requires a string-keyed `VerifyOption` before the optional trailing `LastVerifyOption`. `n:(4)`, `pick:(c)`, `n:(a+1)`, `x$:(LEN=1,5)` and `ENTER n:(4)` fail with "Expecting: one of these possible Token sequences: [STRING_LITERAL] [HEX_STRING] but found: '4'".
2. The rule closes with the `RPAREN_NL` terminal, which the token builder (`bbj-token-builder.ts`, around lines 129-134) only emits for a `)` followed by a line end or `;`. `INPUT x$:("end"=3000),y$` fails with "Expecting token of type 'RPAREN_NL' but found `)`".

Fix shape, proven on an exported copy of the committed tree at planning time: all 18 probe cases parse with the intended AST shapes, parser.test.ts plus example-files.test.ts stay at 215 passed and 1 skipped, and tsc reports no errors. The only generated-type side effect is that `VerifyOptions.$type` widens to `'RPAREN' | 'RPAREN_NO_NL' | 'VerifyOptions'`. That is a known Langium inference quirk already present on 12 other types in the committed ast.ts (for example SqlCloseStatement and Mnemonic), so it is benign.

Scope (v4.3 lean): only the `VerifyOptions` rule changes. `VerifyOption`, `LastVerifyOption`, `InputVariable`, the token builder and every LSP feature provider stay untouched. A grep at planning time found no non-generated consumer of `VerifyOption`, `LastVerifyOption` or `VerifyOptions`; the scope computation and variable-scoping checks only use `isInputVariable` on the variable itself. Not addressed: a space between the colon and the paren (`n: (4)`), dependency upgrades, and the Node 24 generate breakage beyond using the fallback below.
</objective>
