## Cross-phase integration

The gsd-integration-checker traced the wiring and ran the targeted suites (148 tests green).
I re-checked the key points in the code myself:

- **101 ↔ 102 wire contract — WIRED.** `ParseProgramParams`/`Result`/`ParseError` field sets match
  between `bbj-ls` `data/*.java` and `bbj-parser-service.ts`. The application error codes
  -33001..-33005 in `ParserWorker.java:71-86` match `bbj-parser-service.ts:90-94`. MethodNotFound
  (-32601) latches the service off.
- **102 wiring — WIRED.** Registered in `bbj-module.ts:97`. Called from the debounced compile
  path in `bbj-document-builder.ts:279-281`, behind `isEnabled()`. Live diagnostics are
  appended with their own source, so they don't pass through `mergeDiagnostics` and BBjCPL
  and Langium diagnostics are left untouched.
- **98 ↔ 99 ↔ 100 — WIRED.** All conformance regression files parse clean through
  `conformance-regressions.test.ts`. The line-break validator and lexer tokens still agree
  with the grammar after the 99/100 changes.
- **Ready for 103 — YES.** `BBjParserService.isEnabled()` (`bbj-parser-service.ts:184`) is the
  switch the conditional suppression can hang off. It resets per connection generation.
- **Latent cross-repo risk.** 101-REVIEW CR-02 says the `-33004 service-unavailable` path is
  unreachable on the Java side (construction failure escapes as a raw exception). The TS client
  treats any non-MethodNotFound failure as a logged failure rather than a diagnostic (PSRV-08),
  so users see no symptom. The code-to-reason mapping is still off until CR-02 is fixed.
