<objective>
Pin the coordinate conversion against every case PSRV-05 names, make the clamp-never-drop policy a
tested property rather than a defensive intention, and give the live parser's errors the same
per-document cap the existing diagnostics setting already applies to parse errors.

Purpose: the endpoint hands over BBj's own editor coordinates verbatim and the contract makes
converting them the client's job. A live probe against the real endpoint measured the reported end
character exceeding the anchor line's true length in three of four cases, so clamping is the ordinary
path for real errors, not a rare edge. This plan is where that becomes a fixture suite.
Output: `getMaxErrors()`, the cap wired into the live path, and
`test/parser-coordinate-converter.test.ts` covering the four PSRV-05 document shapes plus the
out-of-range shapes.

**Relationship to plan 01.** Plan 01 wrote the converter as production code with its bounds in
place, and proved one in-range error end to end. This plan owns the cases: each of PSRV-05's four
document shapes, each of the out-of-range shapes, and the cap (D-12). Where a fixture shows the
converter producing a wrong range, the fix belongs here — amending `bbj-parser-service.ts` is
explicitly in scope for task 2, and a fixture is never adjusted to match a wrong result.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| service response → published LSP diagnostics | Four integer coordinate fields and a message string computed outside this process are turned into the `Range` and text of a `Diagnostic` delivered to both IDEs. This plan is where that conversion is pinned. |
| the diagnostics setting → the live path | A number pushed at runtime through the configuration handler now also governs how many live parser errors are shown. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-102-01 | Tampering / Denial of Service | `parseErrorToRange` in `bbj-parser-service.ts` | high | mitigate | The fixture suite in task 2 asserts, for every case, that no produced range carries a negative line or character and none exceeds the LSP unsigned-integer maximum. An over-range `Position` makes a JVM language client's deserializer reject the whole publish-diagnostics message, hiding every diagnostic for that document — availability of diagnostics, not cosmetics. The out-of-range, inverted-range and zero-start cases are the direct tests of this mitigation. |
| T-102-06 | Denial of Service | the live diagnostic list published per document | low | mitigate | A server that returns an unbounded error list cannot flood the editor: the list is sliced to the configured cap before conversion, per document. Task 1. |
| T-102-07 | Tampering | a cap value pushed through the configuration handler | low | mitigate | A cap argument that is not a positive finite number falls back to the module default rather than to zero, so a malformed pushed setting cannot silently blank every live diagnostic. Task 1. |
| T-102-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager install task exists in this plan or this phase; every dependency used is already declared and already imported elsewhere in this package. No legitimacy checkpoint is required. |
</threat_model>
