Create `com.basis.bbj.intellij.concurrency.PreviewDebouncer`, a plain-Java trailing-edge coalescer
over the existing `Scheduler` seam. It must not reference any IntelliJ platform type — like
`Scheduler`, `KeystrokeDebouncer` and `StaleEditGuard`, it has to run on the plain JUnit 5 classpath.

Shape: a final class with constructor
`PreviewDebouncer(Scheduler scheduler, long delayMs, KeystrokeDebouncer.UiThread uiThread, Runnable action)`
— reuse `KeystrokeDebouncer.UiThread` rather than declaring a second identical functional interface —
and one public method `trigger()`.

`trigger()` reads the `volatile Runnable pending` field, calls `scheduler.cancel(previous)` when it is
non-null, builds a new task `() -> uiThread.run(action)`, stores it in `pending`, and hands it to
`scheduler.schedule(task, delayMs)`. Never call `scheduler.cancelAll()`: the production scheduler is
shared, and cancelling every pending task would silently kill an unrelated coalescer — the same rule
`KeystrokeDebouncer` documents.

The task body dispatches through `uiThread` rather than running the action inline, because the
production `Scheduler` is an `Alarm` on a pooled thread while the action reads Swing state.

Write the class javadoc to state what this seam is for and how it differs from `KeystrokeDebouncer`:
`KeystrokeDebouncer` debounces a text-keyed background *lookup* whose result is applied only when the
field's text is unchanged; `PreviewDebouncer` debounces a UI-thread *action* whose own staleness is
handled downstream by the caller's sequence number, so it carries no text key and no staleness check
of its own.

Create `PreviewDebouncerTest` in the test package `com.basis.bbj.intellij.concurrency` — it must be in
that package to see the package-private `ManualScheduler`. Cover every case in the behavior block,
driving time only through `advanceBy`/`runPending`, never a real sleep or timer.
