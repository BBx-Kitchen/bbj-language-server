<objective>
Close the one observable truth Phase 93 failed: extend this phase's own malformed-payload guard from
the range arrays it already covers to the three language-server-supplied **line numbers** that still
reach `Document.getLineStartOffset(int)` unchecked.

Purpose: COMP-05 (#591) and the phase goal's "never raises an IDE-internal error". Plans 93-03 and
93-05 closed this failure class for `flagsRange`, `eventMaskRange`, `hexRange` and every catalogs
sub-list. But `ComposerLauncher.openSetoptsInCodeAbsolute` (`ed.line`) and `openSetoptsInCodeChain`
(`chain.startLine`, `chain.endLine`) still pass server-supplied integers straight into
`Document.getLineStartOffset(int)`, which throws `IndexOutOfBoundsException` for any line `< 0` or
`>= getLineCount()`. The throw lands on the EDT inside the `WriteCommandAction` body — the exact "IDE
Internal Error balloon" class this phase exists to eliminate, two lines below a guard this phase
already added for the neighbouring field. Per D-01 the guard covers the whole present-day family of
untrusted fields, not only the ones an issue happens to name; per D-10 the abort reuses the existing
`MALFORMED_EDIT` notice rather than inventing a new reason.

`StaleEditGuard.applyIfUnchanged` does not already cover this: a server that deterministically
returns the same out-of-range line on both the initial decode and the guard's re-decode compares
equal (not stale), so the guard proceeds and the crash still happens.

Output: two new plain-Java predicates on the existing `ComposerEditRanges` seam, two guarded call
sites, an extended behavioural test, and a re-pointed source guard. No new files.
</objective>
