<settled_facts>
Research is disabled for this project; these were settled by reading the installed code and are not open questions.

- **Node `fs.watch` on a non-recursive directory.** Linux (inotify) reports an in-place save as `change` and an atomic write-temp-then-rename as `rename` events for both the temp basename and the target basename. macOS reports most create/delete/rename traffic as `rename` and coalesces bursts. Windows (`ReadDirectoryChangesW`) reports `rename` for create/delete/rename and `change` for content writes. The `filename` argument may be `null` on some platforms and for some events. Consequences this plan bakes in: the watcher ignores `eventType` entirely and dispatches on the filename only; a `null` filename is treated as "possibly the target" and runs the gate; watching the *directory* rather than the file means an inode replacement is still observed. Watches are opened with `persistent: false` so a live watch never keeps the Node process alive, and an `'error'` event closes the handle and logs once (deleting the watched directory stops event delivery on Linux and raises `error` on macOS/Windows).
- **No `fs.watchFile` polling fallback in this phase** (a Claude's-discretion item in 85-CONTEXT.md). There is no reliable in-process signal for "this is a network share where `fs.watch` is unreliable", so a fallback would be speculative. The watch factory is injected instead, so a polling adapter is a later drop-in with no call-site change.
- **`bbj-ws-manager.ts` line 139** holds the single PREFIX line-scan expression that this plan moves, verbatim, into `config-path-resolver.ts`. Read that line before editing; do not retype it from memory.
</settled_facts>
