Plan 88-08 proved, at the shipped-bundle layer, that VS Code's half of both gaps is closed: the
installed extension serves the hover decode and both `bbj/composer/setopts/*` requests, its
manifest registers all three composer entry points, and the shared server answers diagnostics and

IntelliJ side — no IntelliJ sandbox exists in this devcontainer, confirmed directly by
`.planning/debug/g-88-2-composer-never-activates.md`.

This plan closes the largest remaining piece of the IntelliJ gap that does not need an IDE. The
g-88-2 debug session's weakest link was evidentiary, not behavioural: it could not find any plugin
zip whose timestamp was consistent with having been built and handed to the tester before the UAT
round, so "IntelliJ was running a stale plugin too" stayed corroborated rather than proven. The

the SETOPTS-in-code intention is registered, that its description resources ship (the exact
resource class that threw `PluginException: Intention Description Dir URL is null` in Phase 82 and
was fixed by 82-04), and that the bundled language server carries this phase's hover code. That
turns the human's job from "find out whether the plugin has the feature" into "install this exact
artifact and tell us what you see".

VS Code and 19/20/21 for IntelliJ that assume a current build without ever saying to make one.
Both gaps exist because that step was skipped. A standing pre-UAT rebuild step at the top of the
checklist is the durable fix.

Finally it asks the human the three questions only a human can answer — the two gap retests and
88-RESEARCH.md Assumption A2's live-BBjServices mask-width falsification — and writes their verdict
into `88-UAT.md`.
