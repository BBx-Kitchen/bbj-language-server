<objective>
VS Code's two SETOPTS-in-code edit-in-place writers apply their edit using line/range values
captured at decode time, with no re-decode and no document-version check immediately before
`vscode.workspace.applyEdit`. The composer panel is a non-modal `ViewColumn.Beside` webview, so the
user can keep typing in the `.bbj` file for the whole time it is open; nothing stops the apply from
silently replacing whatever now occupies the stale captured range. IntelliJ's equivalent paths are
already proven safe against exactly this by a wired, tested `StaleEditGuard`; VS Code's are not.

This plan ports that guard's behavioural contract to VS Code as a new shared module, wires it into
both edit-in-place apply handlers, and pins a document mutation between decode and apply with tests.

Purpose: ROADMAP Success Criterion 3 / DISC-06 is that a user can **safely** edit in place the two
statically-safe shapes. Plan 88-14 fixed the arithmetic that *computes* the region; this plan fixes
the *safety of applying* that region against a document that may have changed since it was computed.
Both halves are required before the word "safely" is met on VS Code.
Output: `bbj-vscode/src/setopts-stale-edit-guard.ts` (new), a `guard` field on both panel argument
types, a guarded apply in both webviews, the guard construction in `setopts-in-code-ui.ts`'s two
editable branches, and `bbj-vscode/test/setopts-stale-edit-guard.test.ts` (new).

Scope boundary: client-side only, and only the two edit-in-place paths. The compose-new insert path
stays deliberately unguarded — it has no captured *range* to go stale, matching the reference
guard's own documented exclusion of the create flow. No server-side file changes: the decode itself
is correct and independently re-confirmed. No `bbj-intellij/` change: that host already has the
guard. The four Warnings and two Info findings carried in `88-VERIFICATION.md` (the scanner's
control-flow disqualification list, the hover branch's try/catch placement, the orphaned minify
bundle, the code-action handler's undifferentiated null, case-sensitive extension matching, and the
all-Leave compose-new no-op edit) are NOT in this plan's scope and must not be touched here.
</objective>

## Flagged assumptions

- **The compose-new insert path stays unguarded, by design.** VS Code captures the insert line when
  the panel opens, so a large edit above the cursor could land the composed block on a shifted line.
  That is a misplacement of a well-formed new block, not a replacement of code the composer does not
  own, and the reference implementation excludes its own create flow from the guard for the same
  reason. If a future round decides VS Code should resolve the insert line at Apply time instead,
  that is a separate, behaviour-changing decision and belongs in its own plan.
- **`vscode.TextDocument.version` increments on undo/redo even when the text returns to its previous
  content.** This plan therefore does NOT use a panel-open version snapshot as the primary check:
  the authoritative check is the re-decode comparison, and the version is used only for the narrow
  in-flight window between the re-decode resolving and the write starting. A type-then-undo sequence
  therefore does not produce a false refusal.

<threat_model>
## Scenario this plan closes

The careless-user scenario is the realistic one, and it needs no attacker. The composer opens as a
non-modal panel beside the editor. The user leaves it open, switches back to the `.bbj` file, adds a
few lines above the chain (or deletes one), switches back to the panel and presses Apply. The panel
writes the composed block over `[startLine, endLine)` — line numbers computed before those edits —
and whatever code now occupies that range is destroyed. On the chain path the range is multi-line,
so an entire unrelated block can vanish; the loss is silent, because the write itself succeeds.

The attacker-flavoured variant is the same mechanism with a second writer: any process or extension
that edits the open document while the panel waits (a formatter on save, a source-control revert, an
agent-driven refactor) shifts the same captured range. Nothing in the current code distinguishes
that from the user's own deliberate state. The mitigation is identical for both: refuse to write
when the document is not provably the one the range was computed against.

The fix is fail-closed in every branch — a changed document, an unrecognisable re-decode, a missing
document, a failed or timed-out check all refuse the write. A refusal costs the user one re-open of
the composer; an approval of a stale range costs them code.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Composer webview -> extension host | The panel posts an `apply` message carrying the raw form selection; the extension host turns it into a document write. The panel runs with `enableScripts: true` under a per-load nonce CSP with `default-src 'none'`. |
