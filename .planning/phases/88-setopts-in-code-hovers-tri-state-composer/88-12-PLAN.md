<objective>
Make the composer reachable in IntelliJ, and stop our server from being able to freeze someone
else's modal dialog.

The re-diagnosis is unambiguous and neither half is in Phase 88's composer code. IntelliJ computes
ALL intention availability for the caret inside ONE modal, EDT-blocking progress dialog titled
"Searching for Context Actions..." (`ShowIntentionActionsHandler.calcCachedIntentions`). LSP4IJ
registers `LSPIntentionAction0..19` with an EMPTY `<language/>`, so they are evaluated in every
`.bbj` file, and their availability check blocks on `textDocument/codeAction` through
`ProgressIndicatorUtils.awaitWithCheckCanceled(Future)` — the single-argument, NO-TIMEOUT overload.
On our side, Langium gates `addCodeActionHandler` at `DocumentState.Validated` while hover is gated
at the much earlier `DocumentState.Linked`, and `awaitDocumentState` has no timeout either: it
registers a phase listener and settles only if that document is actually rebuilt to `Validated`.
A live probe against the tester's own workspace measured hover at 53434ms and codeAction at
56016ms, with `Java class resolution chain timed out after 30000ms` in stderr. So hover passed (UAT
test 5) and Alt+Enter hung (UAT test 7) in the same session on the same build, and
`ConfigureSetoptsInCodeIntention` — correct in itself — was never reached.

Two fixes, chosen because each one alone would still leave a real failure mode:

1. Bound our answer. We cannot make LSP4IJ time out, and we should not want to: any client that
   waits on a language server's reply deserves a reply. A server that can hold a request open
   forever while a modal dialog blocks the editor's UI thread is our defect regardless of who
   waits badly. So `textDocument/codeAction` gets the same document-state gate hover uses, plus a
   hard budget after which it answers with nothing rather than nothing-yet.
2. Add a second door. D-03 chose the lightbulb as IntelliJ's trigger and its own reversibility note
   says an additional trigger "can be layered on later without touching the request/DTO surface" —
   this is that later. An editor context-menu action reaches the same launcher without passing
   through IntelliJ's shared intention search at all, so a future foreign plugin's slow intention
   can degrade Alt+Enter without making the composer unreachable.

It also corrects the evidence. 88-08's reassuring "codeAction 205ms / 15000ms" ran on an
already-warm, already-`Validated` document and never reproduced the Alt+Enter ordering; the same
request took 56 seconds when issued cold. The probe is re-run in the correct ordering here.

Purpose: the composer opens in IntelliJ, and our server can no longer be the thing that hangs a
modal.
Output: a bounded code-action handler with the cold measurement to prove it, and a non-intention
entry point.

Explicitly out of scope:
  - Anything about G-88-3's literal syntax (plans 88-10 and 88-11).
  - Changing `BBjCodeActionProvider`'s own behaviour. It stays exactly as it is; only when and for
    how long it is waited on changes.
  - Removing or weakening the lightbulb intention. It stays registered and unchanged — this plan
    adds a path, it does not replace one.
  - Declaring G-88-2 closed. No IntelliJ sandbox exists in this devcontainer (probed directly by
    plan 88-09), so a live Alt+Enter retest is the only thing that can, and plan 88-13 stages it.
</objective>
