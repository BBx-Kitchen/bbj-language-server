<objective>
`decodeInCode`'s chain edit-in-place branch computes its replace region from document line
numbers — the origin statement's line plus one, through the `SETOPTS` statement's own line — rather
than from the reassignment statements' own CST ranges. For a chain the codebase's own safety walk
classifies `safe: true` but whose reassignment shares a physical line with the `SETOPTS` statement
via `;`, that arithmetic yields an empty replace range while still reporting `editable: true` with a
populated `chain` payload; both writers then insert the newly composed lines into the empty gap and
leave the original reassignment in place, silently changing the program's effective options vector.
The all-on-one-line variant yields an inverted range instead.

This plan anchors the region on the reassignment statements themselves and fails the edit gate
closed — hover decode intact — whenever the region cannot be expressed as whole lines the chain owns
outright.

Purpose: DISC-06 / ROADMAP Success Criterion 3 promises that editing a canonical
`var$=OPTS … SETOPTS var$` block in place is safe and that every other shape gets hover decode only
(D-04). Today a shape the scanner calls safe gets an edit that corrupts the file, so that promise is
unmet.
Output: a statement-anchored region computation plus a named not-editable reason in
`setopts-in-code-request.ts`, the link statement nodes the scanner must expose for it, and
edit-range-layer test coverage for every line-sharing shape.

Scope boundary: this is a server-side correctness fix inside the edit-in-place half of DISC-06, so
the composer's trigger surface (D-03), its compose-new codegen (D-05) and its tri-state form layout
(D-06) are all delivered and untouched — no client, dialog, webview, intention, Code Action,
manifest, example or QA-checklist file changes in this plan. The two shapes D-04 names stay exactly
the two shapes that get an edit action; what changes is that a shape whose edit cannot be expressed
as a whole-line region now falls on the hover-decode-only side of that line instead of being handed a
wrong range.
</objective>

ASVS level 1, block-on severity `high`. This plan touches no authentication, session, access-control,
cryptography, serialization or network boundary, so the ASVS L1 chapters for those are not applicable;
