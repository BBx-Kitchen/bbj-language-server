<objective>
Make the decoder refuse the syntax BBj itself refuses, and make the test corpus tell the truth.

The debug session named a contributing cause that is as important as the two defects themselves:
`parseHexLiteral` (`setopts-code-scanner.ts:141-156`) accepts `"$08$"` exactly as readily as `$08$`.
`BBjValueConverter` has already stripped the quotes by the time the AST value is read, so the
decoder cannot tell the two apart at the value level and never tries. Because the wrong form
round-tripped cleanly, it spread from the generator into the decode-side fixtures
(`setopts-in-code-request.test.ts:55,91,166`, and most of `setopts-code-scanner.test.ts` and
`hover.test.ts`), and no test anywhere compared generated output against real BBj syntax. That is
why "33 passing composer tests" coexisted with a live `!ERROR=17`.

So this plan does two things. It narrows the decoder to the grammar's own `HEX_STRING` terminal
shape, consulting the literal's raw source text since the converted value cannot distinguish the
two terminals. And it migrates the decode-side fixture corpus to the syntax a real BBj program
actually contains — the same bare form `examples/issue475-setopts-in-code.bbj` uses throughout.
After this, an invalid literal fails loudly at the decode layer instead of being quietly honoured.

Then it closes the contract with the one test nobody had: splice the formatter's output into the
delimiter-spanning `hexRange` and prove the resulting line re-decodes to the new digits. Plan 88-10
fixed the writing side; this proves the two halves compose rather than double up.

Purpose: remove the leniency that let the defect hide, and pin the composed contract end to end.
Output: a stricter decoder, a truthful fixture corpus, and a round-trip gate.

Explicitly out of scope:
  - The generated-text fixes themselves (plan 88-10) and the `hexRange` field's own definition,
    which stays delimiter-inclusive exactly as its existing test pins it.
  - Any change to the unsafe-reason vocabulary, the chain walk, or the hover markdown. A quoted
    mask simply reaches the EXISTING `unparseable-mask` verdict instead of being decoded.
  - G-88-2 (plan 88-12) and the live retest (plan 88-13).
</objective>

**Why the value cannot decide it.** `bbj.langium:949-950` declares two terminals:
`STRING_LITERAL: /"([^"]|"{2})*"/` and `HEX_STRING: /\$[0-9a-fA-F]*\$/`; `StringLiteral` (line 830)

value. The raw token text is reachable as `expr.$cstNode?.text`, which for a `HEX_STRING` includes
its `$` delimiters (the existing test at `setopts-in-code-request.test.ts:87` proves the CST node
spans them).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-authored `.bbj` source → the decoder | Arbitrary user text reaches `parseHexLiteral`, `detectSetOptsShape` and the chain walk |
| decoder verdict → the edit gate | `editable` is assigned directly from the scanner's safety verdict, so a false decode becomes an unsafe write |
| decoder verdict → hover text | A decode shown to the user is a claim about what the line does at runtime |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-88-25 | Spoofing | a quoted string masquerading as a decodable hex literal | high | mitigate | Task 1 narrows acceptance to the grammar's own terminal shape using the raw token text, the only place the distinction survives the value converter; all three decode sites get explicit negative coverage |
| T-88-26 | Tampering | the edit gate opening on a line the decoder misread | high | mitigate | The gate is derived from the decoder, so Task 1's narrowing closes it automatically; Task 3 pins the absolute case as an explicit not-found negative |
| T-88-27 | Repudiation | a test corpus that certifies syntax the runtime rejects | medium | mitigate | Task 2 migrates every mask/argument fixture to real BBj syntax and Task 3 adds the round-trip gate, so a future invalid form fails a test instead of round-tripping |
| T-88-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan adds no dependency and installs no package; no package-legitimacy checkpoint applies. |

Denial of service is not applicable: the narrowing is a bounded regular-expression test on a single
token, adding no traversal, no allocation growth and no new I/O. ASVS level 1, block-on `high`: no
unmitigated `high` remains.
