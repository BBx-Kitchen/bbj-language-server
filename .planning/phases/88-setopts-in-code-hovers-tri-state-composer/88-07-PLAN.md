<objective>
Close gap G-88-1's real code defect: `matchStatement()` in `setopts-code-scanner.ts` silently
treats BBj's idiomatic byte-range accessor (`A$(1,1)`) as if it never touched the tracked
variable, so `traceOptsChain` reports a chain as `safe: true` with an empty `links`/`effect`
instead of an unsafe verdict.

Empirically confirmed against the current tree (both of the user's exact reported lines return
`{ safe: true, links: [], effect: { set: [], clear: [] } }`):

  a$=OPTS; A$(1,1)=IOR(A$(1,1),$C2$); SETOPTS A$        -> safe:true, 0 links, empty effect
  LET A$=OPTS / LET A$(2,1)=AND(A$(2,1),$7F$) / SETOPTS A$ -> safe:true, 0 links, empty effect
  A$=OPTS / A$[1]=IOR(A$[1],"$08$") / SETOPTS A$        -> safe:true, 0 links, empty effect
  A$=OPTS / A$(1,1)="x" / SETOPTS A$                    -> safe:true, 0 links, empty effect

That violates the module's own documented invariant ("any ambiguity resolves toward an unsafe
verdict, never toward a false link or origin"), produces a hover that reads `Sets: (none)` for a
chain that really does set bits, and — worse — opens the D-04 edit gate on a shape D-04 says must
get hover decode only. `createDecodeInCodeHandler` currently answers `editable: true` for those
lines and hands the composer a reassignment range spanning the user's byte-range statements, so
applying an edit would rewrite `A$(1,1)=IOR(A$(1,1),$C2$)` as a full-width whole-variable
assignment.

Direction chosen: **explicit unsafe reason**, not "track the indexed mutation". Rationale, per the
module's existing design:
  - `SetOptsChainLink`/`foldChainEffect` carry no byte offset; a mask like `$7F$` written at
    `A$(2,1)` would fold as a byte-1 mask and decode to the wrong option — a silently wrong answer
    is strictly worse than a named "cannot determine".
  - `createDecodeInCodeHandler` derives `editable` directly from `safe`, and the composer replaces
    the whole `(originLine, setoptsLine)` region with generated full-width lines. Marking a
    byte-range chain safe would let the composer clobber the user's one-byte writes with a
    16-byte-vector rewrite whose runtime behaviour is exactly what 88-RESEARCH.md Assumption A2
    has not yet falsified against a live BASIS runtime.
  - D-04 already names this class ("Any other shape … gets hover decode only — no edit action is
    presented"). A named unsafe reason restores D-04, and D-02's hover contract still holds: the
    chain hover keeps telling the truth about what it can and cannot decode.

The `mask-call` hover shape (hovering the `IOR` token itself) is already correct on these exact
lines and is deliberately untouched — it never consults `matchStatement`.

Purpose: restore the fail-closed safety boundary both the hover (D-02) and the edit gate (D-04)
depend on, for the single most idiomatic way BBj code mutates one byte of the OPTS vector.
Output: one new `SetOptsUnsafeReason` with its user-facing sentence, two explicit classification
sites in `matchStatement`, and executing regression coverage for both reported reproductions.

Explicitly out of scope (no code exists to change): the stale/un-rebuilt VS Code extension and
IntelliJ plugin installs that caused the "no hover at all" half of G-88-1 and all of G-88-2. Those
resolve by rebuilding and reinstalling both extensions before the next UAT round — a standing
pre-UAT step, not this plan's work. Do not touch hover formatting, the composer UI, or any
IntelliJ file.
</objective>
