<objective>
Prove the SETOPTS-in-code decode hover end-to-end on the thinnest possible path: one new pure
scanner module, one branch in the existing `BBjHoverProvider`, one absolute `SETOPTS <hex>`
statement, verified by a real hover request against a parsed document.

Purpose: this phase's single largest architectural risk is *where* the hover branch attaches.
Langium's `AstNodeHoverProvider.getHoverContent` only calls `getAstNodeHoverContent` for nodes
that `References.findDeclarations(cstNode)` resolves to a declaration. A hex `StringLiteral`
resolves to nothing, so a branch added inside `getAstNodeHoverContent` (as 88-PATTERNS.md and
88-RESEARCH.md both suggest) would silently never fire for D-02 shape (a). This tracer settles
that question on the first commit instead of after five layers are built on top of it.

Output: `setopts-code-scanner.ts` with the shape-(a) detection path, the hover wiring, an
exported `resolveLibFunction`, and the regression tests that pin all three.
</objective>
