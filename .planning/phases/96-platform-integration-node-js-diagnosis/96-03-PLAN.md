<objective>
Fix the two 83-REVIEW findings that change what the Windows attestation actually produces, before the
attestation runs. `extractZip` matches its target entry with
`entry.getName().endsWith("node.exe")` — a loose suffix test on the `.zip` branch, which is the
Windows-only code path PLAT-06 attests. And `install()`'s outer `finally` calls
`Files.deleteIfExists(tempFile)` unguarded, so a cleanup failure replaces whatever real exception the
try block was about to throw.

Purpose: PLAT-06's attestation captures `idea.log` when it fails (D-13 step 4), and D-15 turns a
failure into a `WINDOWS.md` entry and its own debug session. Both are worthless if the logged
exception names file deletion instead of the download or verification that actually failed. D-14
folds exactly these two findings and no others — the remaining three are Unix-only or Settings-side
and stay deferred.

Output: an exact relative-path entry match built from the literals `archiveFileName()` already
assembles, a swallow-and-log outer cleanup mirroring the sibling `deleteRecursivelyQuietly`, the
one-line `Target.nodeExecutableName()` reuse folded in alongside (IN-02), and a new committed decoy
fixture that makes the entry-match fix provable.
</objective>

`deleteRecursivelyQuietly` (same file) is the swallow-and-log model for the WR-02 fix:
```
private static void deleteRecursivelyQuietly(Path root) {
    try {
        deleteRecursively(root);
    } catch (IOException e) {
        // Best-effort cleanup: a failure here must never mask an earlier exception.
    }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| nodejs.org over HTTPS -> temporary archive file | Remote bytes entering the machine, gated by a source-pinned SHA-256 before use. |
| archive entries -> extracted filesystem paths | Archive-controlled names selecting which entry becomes the installed executable. |
| pipeline exception -> idea.log | The only evidence channel PLAT-06's attestation has when the install fails. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-96-03-01 | Tampering | `extractZip` entry selection | medium | mitigate | A loose suffix match lets any entry whose name ends with the executable file name be installed as the Node binary. Closed by an exact relative-path equality test built from the same literals `archiveFileName()` assembles, and proven by a committed fixture that places a wrong-path decoy FIRST so the old implementation would have installed it. Severity is bounded below high because the archive's bytes are already verified against a source-pinned digest before `extractZip` ever runs — this is robustness inside an integrity-checked artifact, not an untrusted-input path. |
| T-96-03-02 | Repudiation | `install()`'s outer `finally` | high | mitigate | A cleanup failure replacing the real exception destroys the evidence PLAT-06's attestation depends on, and would send a Windows failure investigation at the wrong root cause. Closed by a swallow-and-log single-file helper mirroring the existing `deleteRecursivelyQuietly`, with a test asserting the verification failure message survives. |
| T-96-03-03 | Tampering | pinned-digest verification ordering | high | mitigate | Every fix in this plan sits downstream of the digest gate, and none may reorder or weaken it. Held in place by `NodeInstallPipelineSourceGuardTest`'s existing pins that verification precedes both the extraction call and the install step, which this plan runs unmodified. |
| T-96-03-04 | Tampering | committed test fixtures | medium | mitigate | A fixture changed without updating its pin would silently weaken the very test that proves the fix. Mitigated by the README's hand-transcription rule — the digest is recorded from a real `sha256sum` run and pinned as a literal in the test, never computed from the bytes under verification. |
| T-96-03-05 | Denial of Service | Unix `tar` extraction path | low | accept | WR-01 (cancellation not honoured mid-extraction) and WR-03 (unclosed `tar` stdin) remain open and are explicitly not folded (D-14). Both are Unix-only and cannot affect the Windows `.zip` path PLAT-06 attests. Accepted for this phase; they stay recorded in STATE.md's Blockers. |
| T-96-03-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no package-manager dependency and runs no install step. 96-RESEARCH.md's Package Legitimacy Audit records the gate as not applicable for this phase, with no `[ASSUMED]`, `[SUS]` or `[SLOP]` packages. The Node.js archive this pipeline downloads is not a package-manager install and is covered by the pinned-digest control above. |
