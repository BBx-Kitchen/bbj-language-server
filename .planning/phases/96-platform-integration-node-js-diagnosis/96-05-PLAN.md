<objective>
Make `NodeExecutableResolver` the single Node.js decision engine, and give it the two facts it is
currently missing. Today it validates parse, absolute, exists, regular-file and executable — but
never the minimum version, so a too-old configured Node.js starts the language server. And
`BbjNodeDownloader.getCachedNodePath()` returns null for both "nothing downloaded yet" and "the cache
directory itself is inaccessible", so those two states collapse into zero recorded rejections and no
caller can tell them apart.

Purpose: ROADMAP criterion 4 — a developer whose Node.js is unusable is shown the diagnosis that
matches reality, with "not yet downloaded" and "cache directory inaccessible" distinguishable to
every caller, and a configured-but-unusable path either consulting the cached download or
deliberately not, with the decision written down. D-05 supplies that decision: yes, it consults the
cached download, reached by unifying the two seams rather than patching the weaker one.

This plan builds the engine and its presentation seam. The sibling plan that rewrites the editor
banner consumes both, and lands after the notification base, per the ROADMAP ordering note.

Output: a sixth validation step, two new `Reason` constants, one additive overload that leaves the
existing 24-case test file untouched, a cache-accessibility accessor, a rewired startup path, and a
platform-free `NodePresentation` seam whose text and action set both vary by reason.
</objective>

<assumption_delta_decision>
**Primary noun:** the unified Node.js decision engine.
**Transition:** two independent engines become one — a singular-to-plural boundary crossed in the
promote direction, not the add-alongside direction.
**Decision: PROMOTE.** `NodeExecutableResolver` is promoted to the single Node decision engine; the
parallel `NodeAvailability` seam is demoted and retired (its deletion lands in the sibling banner
plan, which is its last caller). A second engine is NOT added alongside.
**Rationale:** the two engines already disagreed twice, and both disagreements reached users. First,
on fall-through: the resolver tries configured, then detected, then cached and explicitly falls
through a rejected candidate, so the language server already starts off the cached download when a
configured path is broken — while `NodeAvailability.decide` stops dead at a non-empty configured
path, so the banner claims Node.js is missing on a machine whose server is running fine. Second, on
version: the resolver never checks the minimum version while the banner does, so a too-old configured
Node.js is rejected by the banner and accepted by startup. Keeping two engines, or keeping
`NodeAvailability` as a thin wrapper that still branches independently, leaves exactly the drift
surface that produced both bugs.
**Not re-opened.** This is CONTEXT.md D-05, already decided; recorded here for traceability only.
</assumption_delta_decision>

The two version collaborators, already used together in three places:

functional-interface type is needed.

`BbjNodeDownloader.getCachedNodePath()` returns `@Nullable Path` and swallows the `IOException`:
```
public static @Nullable Path getCachedNodePath() {
    try {
        return productionPipeline().cachedNodePath();
    } catch (IOException e) {
        return null;
    }
}
```
The exception originates in `getNodeDataDirectory()`'s `Files.createDirectories`, NOT in
`NodeInstallPipeline.cachedNodePath()`, which is documented never to throw.
`private static @NotNull Path getNodeDataDirectory() throws IOException` resolves
`Paths.get(PathManager.getPluginsPath(), "bbj-intellij-data", "nodejs")`.

`BbjLanguageServer.resolveNodePath(Project)` is the startup call site, lines 56-77: it reads the

`Resolution` types directly, since it lives in the same package and those are plain enums and a
plain class — that stays platform-free.

The banner's three current action labels, which the action-id vocabulary must cover:
