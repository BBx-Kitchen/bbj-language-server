<objective>
Move server-side EM token validation out of the run-action base and into the EM-token lifecycle
neighbourhood, so the run-action base returns to being about launching processes.

Purpose: EM-03 (#617). `validateTokenServerSide` (:291-331) and `validateTokenTrusted` (:345-347)
sit on `BbjRunActionBase`, which is a run-action base class, not a credential-lifecycle one. Both
move together into a new class beside `BbjEMTokenStore` and `TokenValidationCache` — moving only one
would leave half the token-validation story behind, which is the exact complaint #617 filed. The
riskiest part of this plan is not the move; it is re-pointing the two source guards that pin the
moved code, one of which is a published-advisory pin.
Output: `EmTokenValidator` plus its unit test, a leaner run-action base, two re-pointed guards.
</objective>

<interfaces>
The signatures this plan establishes, so the guard literals in Tasks 2 and 3 are unambiguous:

- `public boolean validateTokenServerSide(@Nullable String bbjPath, @Nullable String scriptPath, @NotNull String token)`
- `public boolean validateTokenTrusted(@Nullable String bbjPath, @Nullable String scriptPath, @NotNull String token)`
- the single call site in `buildWebRunCommandLine` reads `validateTokenTrusted(bbjPath, emValidatePath, token)`

Both path parameters are nullable and both methods return false when either is null. That is not a
new behaviour: today's `validateTokenServerSide` resolves those two values internally and returns
false when either comes back null, and `buildWebRunCommandLine` reaches the call site with a
`bbjPath` it never null-checked. Preserving the null-tolerance at the new boundary is what keeps the
launch behaviour identical.

`TokenValidationCache.SESSION.validateThrough(token, supplier)` is unchanged and is still the only
decision site for the window.
</interfaces>
