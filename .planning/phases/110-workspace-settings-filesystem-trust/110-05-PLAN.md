<objective>
Gate the workspace-scoped `bbj.configPath` behind VS Code Workspace Trust in the client: one helper
computes the effective value (D-06), and every handoff to the server uses it. That covers
`initializationOptions`, the `synchronize.configurationSection` push through a middleware that builds the
payload itself (D-21), the pull-model answer, and the client's own config-association fallback. Trust
being granted re-pushes the settings (D-07). The server, `config-path-resolver.ts`'s resolution and
IntelliJ stay as they are (D-05, D-09).

Purpose: issue #511 shows a repository's `.vscode/settings.json` can point the config reader at a file
the user never chose. The roadmap keeps `configPath` un-anchored for system-wide config files, so only
the workspace-scoped value is gated.

D-08, stated plainly: `bbj-vscode/package.json` declares no `capabilities`, so VS Code treats the
extension as not supporting Workspace Trust and does not activate it in Restricted Mode. This plan does
not change that. Criterion 2 is therefore shown by unit tests with a stubbed `vscode.workspace`
(`isTrusted`, `inspect`, `onDidGrantWorkspaceTrust`), not by a live Restricted Mode session.
Output: `config-path-trust.ts`, the wired client, the cache fallback on the helper, and
`test/extension-config-trust.test.ts`.
</objective>
