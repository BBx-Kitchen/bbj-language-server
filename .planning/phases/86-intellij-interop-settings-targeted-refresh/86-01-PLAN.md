<objective>
Route IntelliJ's "Refresh Java Classes" through the language server's existing targeted `bbj/refreshJavaClasses` request instead of `requestRestart(0)`, so a refresh reloads the Java class cache without taking the IDE's language features offline — with the whole decision surface (outcome classification, reason-keyed presentation, single-flight guard) in platform-free seams that plain JUnit covers, and a source guard proving the full-restart behaviour survives only as a user-clicked fallback.

Purpose: CFG-04 (#632). Today the action restarts the entire language server, which drops diagnostics, completion, hover and the Structure View for every open file. The roadmap's first success criterion is a go/no-go on LSP4IJ issuing a targeted custom request without a restart; D-11 answers it GO, on the evidence that this plugin already issues `bbj/compile` (Phase 81) and `bbj/resolvedConfigPath` (Phase 84) through the same dynamic proxy. Recording that closure here is also what lets Phase 87's SETOPTS command layer skip a spike.
Output: `refreshJavaClasses()` on `BbjComposerServer`; a rewritten `BbjRefreshJavaClassesAction`; `JavaClassesRefreshFlow`, `JavaClassesRefreshPresenter` and `RefreshInFlightGuard` in a new `refresh` package; four new test classes; the new request name pinned cross-language in `ComposerRequestContractTest`.
</objective>

<settled_facts>
Research is disabled for this project; these were settled by reading the checked-in sources and are not open questions.

- **The go/no-go is already answered by the codebase.** `BbjLanguageServerFactory.getServerInterface()` returns `BbjComposerServer.class`, and LSP4IJ builds a dynamic proxy over it. Two custom request families (`bbj/compile`, `bbj/resolvedConfigPath`) are already dispatched over that proxy from a background task with no server restart. Adding a third is the same mechanism. No spike is needed and no `workspace/executeCommand` fallback is required.
- **`bbj/refreshJavaClasses` already exists server-side.** `bbj-vscode/src/language/main.ts` line 36 registers `connection.onRequest('bbj/refreshJavaClasses', …)` returning `true`/`false`, delegating to `reloadJavaClassesAndRevalidate()`. VS Code's `extension.ts` line 803 already calls it with `client.sendRequest`. Both are read-only for this plan.
- **`ComposerRequestContractTest` needs four separate edits, not one.** Its `DECLARED_REQUESTS` set is asserted equal to the names reflectively derived from `BbjComposerServer`'s `@JsonRequest` methods, so the new name must be added there or that test fails. Its `everyRequestNameIsNamespacedAndLowerCase` test only tolerates camel case for segments listed in `allowedCamelCaseSegments` (currently `decodeCall`, `resolvedConfigPath`) — `refreshJavaClasses` must be added to that set or the new name fails the per-segment check. Its cross-language search reads only three TypeScript files (`composer-commands.ts`, `compile-command.ts`, `resolved-config-path-request.ts`); the new name lives in `bbj-vscode/src/language/main.ts`, so a fourth path constant is required. Its class javadoc says "The nine names".
- **`ComposerFlowTest.FakeComposerServer` is the only implementation of `BbjComposerServer`** in the repo (`private static class` at line 80). Adding an abstract method to the interface breaks its compilation, and nothing in the test source set compiles — including new test classes — until it gets the override. The convention for methods that flow never calls is a body that throws `UnsupportedOperationException`.
- **`BbjComposerService.server(project)` returns a future that completes with `null`** when the server is not running; the javadoc says callers must handle the null case. It also calls `LanguageServerManager.getInstance(project).start(SERVER_ID)` internally, which is why the action itself never needs to reference that type.
- **`BbjServerService` surface used here:** `getInstance(Project)`, `logToConsole(String, ConsoleViewContentType)`, `requestRestart(long)`, `getCurrentStatus()`. `requestRestart(long)` is the only permitted restart entry point in the plugin (EDT-05).
- **`BbjCompileAction` renders a balloon on every outcome including success.** The refresh action is deliberately tighter: success is console-only. Do not copy `render()` verbatim.
- **The existing `update()`/`getActionUpdateThread()` pair on the refresh action is correct** (`ServerStatus.started` gate, `ActionUpdateThread.BGT`) and stays byte-identical.
</settled_facts>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IntelliJ plugin → language server (local stdio JSON-RPC via LSP4IJ) | A new client-initiated request crosses the boundary and triggers a full Java classpath reload plus re-validation on the server side. |
| plugin → user surface | A console line and, on failure, one balloon carrying an exception's own message and an action that restarts the language server. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-86-01 | Denial of Service | repeated Refresh Java Classes invocations each starting a full classpath reload on the server | high | mitigate | A per-project single-flight guard drops every invocation while one refresh is in flight, and the request is bounded at `REFRESH_TIMEOUT_SECONDS` (60 s) so a lost response cannot hold the guard forever; the release sits in a `finally`. Both properties are pinned by `RefreshInFlightGuardTest` and the action source guard. |
| T-86-02 | Denial of Service | a blocking proxy lookup or request running on the dispatch thread freezing the IDE | high | mitigate | Every blocking call runs inside a `Task.Backgroundable` whose first statement is the platform's off-dispatch-thread assertion; the source guard pins that assertion to exactly one occurrence, and the only dispatch-thread work is the already-running console note. |
| T-86-03 | Tampering | an unexpected boolean or a version-skewed response shape crossing the LSP4IJ boundary | medium | mitigate | The response type is the server's existing `Boolean` and is not widened (D-16); `false` is classified as a distinct `DECLINED` outcome rather than treated as success, and every exception path is classified rather than swallowed. Covered by `JavaClassesRefreshFlowTest`. |
| T-86-04 | Information disclosure | a raw exception message rendered into the failure balloon body | low | accept | The message originates in the plugin's own JVM or the local language server, both already fully visible to this user in the tool-window console; no remote or multi-tenant surface exists. This matches the accepted `ComposerNotices.detailOf()` position recorded as an advisory Phase 82 follow-up. |
| T-86-05 | Elevation of privilege | the balloon's restart action being invoked without user intent | low | mitigate | The restart is reachable only from a `NotificationAction` body, structurally fenced by the source guard to exactly one occurrence located after the notification-action construction; no code path reaches it automatically. |
| T-86-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no package-manager install task and no new dependency; the Gradle and LSP4IJ pins are unchanged, so the package-legitimacy gate has nothing to audit. |
