<assumption_delta_decision>
**Primary noun:** the *effective java-interop port* — one value resolved by one accessor, `BbjSettings.getEffectiveJavaInteropPort()`.

**Decision:** `promote`.

**What changed.** Before this phase there was exactly one representation of the port: the persisted `int javaInteropPort`, which conflated three different things — the user's explicit choice, the value detection produced, and "never configured". This phase introduces a second case (auto-detected versus explicitly chosen), which is the singular-to-plural transition the detector flagged.

**Why promote rather than add alongside.** The generalized representation — a mode plus a resolved value — becomes primary: every reader (`initializationOptions`, the health probe, the Settings dialog's reset) asks the accessor, and the accessor is the only place that knows which mode is active. The raw `javaInteropPort` field is demoted to what it now actually is: storage for the explicit variant only, meaningful solely when `javaInteropPortAutoDetect` is false. Adding the flag alongside a still-authoritative raw field is exactly the shape that reproduces the #608 bug in a new form — a reader that keeps consulting the int would silently ignore detection, and a writer that keeps writing the int under auto-detect would silently destroy the user's explicit choice. The demotion is fenced structurally by `EffectiveInteropPortSourceGuardTest` (no reader outside `BbjSettings` may read the raw field for the effective value) and behaviourally by `InteropPortSettings.portToPersist` (auto-detect never writes the field).

**Invariant test.** Already authored, not new: the explicit-5008 regression pair in `InteropPortSettingsTest` from plan 86-02 asserts both directions of the promotion — auto on with a detected 6000 yields 6000; auto off with a stored 5008 and a detected 6000 yields 5008. It goes red the instant a future phase reintroduces the singular assumption by deriving the port from the int alone.
</assumption_delta_decision>

<settled_facts>
Research is disabled for this project; these were settled by reading the checked-in sources and are not open questions.

- **There are exactly four readers of the port today**, confirmed by a repository-wide search: `BbjSettingsConfigurable` (three sites — `isModified`, `apply`, `reset`), `BbjLanguageServerFactory.initializeParams` (line 52), `BbjJavaInteropService.checkConnection` (line 120), and `BbjSettingsComponent`'s own field getter and setter. Nothing else reads it.
- **`BbjJavaInteropService.checkConnection` runs off the dispatch thread** — its `Alarm` is constructed with `Alarm.ThreadToUse.POOLED_THREAD` — and it deliberately re-reads settings on every five-second tick rather than caching, which is why switching it to the accessor is what makes a live properties change visible without a watcher.
- **`BbjSettingsConfigurable.reset()` calls `getState()` at its top**, and `getState()` fills `bbjHomePath` by auto-detection when it is empty. By the time the port block runs, `state.bbjHomePath` already carries the auto-detected home, so the port block does not need the separate `bbjHome` local the old code reused.
- **`BbjSettingsComponent` references `BbjSettings` zero times today.** `BbjSettingsLookups` is a different symbol and does not match the `BbjSettings.` prefix. Keeping that count at zero is what makes the component's no-I/O guarantee checkable with a single assertion.
- **`getEffectiveJavaInteropPort()` cannot be unit-tested.** `BbjSettings.getInstance()` resolves an application service and this repo has no platform test harness. The decision content was therefore extracted into `InteropPortSettings` in plan 86-02, and the wiring is fenced by source guards here.
- **`apply()` must capture the stored port before writing either field**, because `portToPersist` takes the current persisted value as an argument. Writing the flag or the port first would feed it the value it is about to produce.
- **`isModified()` must not compare the port while the dialog's checkbox is on.** With auto-detect on, the greyed field displays a detected number that `apply()` deliberately never persists, so a raw comparison would make the settings page claim to be modified forever. `InteropPortSettings.portSettingModified` encodes that.
- **The `ComponentValidator` on the port field stays exactly as it is.** A disabled field does not prompt the user, and the 1-65535 rule it enforces still applies the moment the field becomes editable.
- **`scheduleRestart()` in `apply()` is unchanged.** `initializationOptions` is the only channel carrying the port to the server on IntelliJ, so a port change genuinely needs the coalesced restart Apply already performs.
- **Detection is captured when the dialog opens, not per keystroke in the BBj home field.** This is the discretion D-09 leaves open ("if the hint must follow BBj Home edits"), and it is resolved deliberately: editing the home field inside one dialog session does not re-run port detection, because the port only takes effect at the next server start and Apply restarts the server anyway. Resolving it this way keeps `HomeLookup`, the home debouncer and their tests untouched, and keeps the dialog's filesystem work at exactly one cached stat per open.
</settled_facts>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| persisted settings file → plugin | `BbjSettings.xml` is user-writable state whose auto-detect flag and stored port are reinterpreted by a migration at load time. |
| filesystem → dispatch thread | The Settings dialog resolves `BBj.properties` detection while the user is interacting with it. |
| plugin → language server / java-interop socket | The effective port becomes an initialization option and a TCP connect target. |

| T-86-11 | Tampering | a hand-edited or corrupt `BbjSettings.xml` carrying an out-of-range explicit port into a connect attempt | high | mitigate | The accessor routes the explicit branch through `InteropPortSettings.sanitizePort`, so any value outside 1-65535 resolves to the default; the migration also treats an invalid saved port as no signal, so it cannot flip a fresh install into a bogus explicit mode. Both rules are covered by plan 86-02's tests and pinned to one call site by the new source guard. |
| T-86-12 | Denial of Service | filesystem work on the dispatch thread freezing the Settings dialog | high | mitigate | Detection is resolved exactly once per dialog open, through the stat-keyed cache, and with auto-detect off not even a stat is performed; the component itself holds no reference to the cache, the settings service or the decision class, which the extended component guard asserts. |
| T-86-13 | Tampering | a silent overwrite of the user's explicitly chosen port by auto-detection | high | mitigate | `portToPersist` returns the previously stored value whenever the checkbox is on, so no code path other than the user's own Apply with the checkbox off writes the field; the flag rather than the numeric value records the choice, which is what makes an explicit 5008 representable at all. |
| T-86-14 | Spoofing | a writable `BBj.properties` redirecting the java-interop connection | medium | accept | Same rationale as the detection plan: write access to the BBj installation already implies control of the BBj runtime and classpath.
