<objective>
Stop the lightbulb popup from throwing. The three composer intentions
(`ConfigureMsgboxIntention`, `ConfigureAddWindowIntention`, `ConfigureAddChildWindowIntention`) are
registered as `<intentionAction>` extensions and return `IntentionPreviewInfo.EMPTY` from
`generatePreview`. On an EMPTY preview the platform falls back to
`IntentionPreviewComputable.tryCreateFallbackDescriptionContent`, which asks
`IntentionActionMetaData.getResourceLocation` for the per-intention description resource — and that
method calls `classLoader.getResource("intentionDescriptions/<SimpleClassName>")` and throws
`PluginException("Intention Description Dir URL is null …")` when the directory is absent. The plugin
has never shipped an `intentionDescriptions/` tree at all, so every preview computation on one of
these entries produces an IDE error report. The dialogs themselves still open; the defect is the
error report, and it pre-dates this phase (the registrations landed in `cdbd1699`, #433/#435).

Purpose: G-82-6 is the one open gap from phase 82's UAT. It was reported while exercising the
stale-edit abort (UAT test 6) but is independent of it — the stale-edit behaviour itself is still
unconfirmed and stays a UAT item. Closing this removes the error report that made test 6 unreadable
and, with the `plugin.xml`-driven guard, makes it impossible for the next intention to reintroduce it.

Output: nine resource files under `src/main/resources/intentionDescriptions/`, three one-line
`generatePreview` changes, and two plain-JUnit test classes — one enumerating the descriptor, one
pinning the preview wiring.

## Executor shell and file-access rules (CLAUDE.md — follow verbatim)

A Phase 80 executor stalled for 20 minutes on an unanswered `cd …; git diff` permission prompt. These
rules keep the run autonomous:

- Search and read with the built-in `Grep`, `Glob` and `Read` tools first. Fall back to shell
  `grep`/`find`/`cat` only when a built-in genuinely cannot do the job (for example a pipeline into
  another program, which the verification commands below use deliberately).
- Every shell path is absolute and complete from `/home/coder/repos/bbj-language-server/…`. Never
  rely on the current working directory; never use `.`, `..` or `~` as a search target.
- Never chain `cd` with `grep`, `find`, `cat`, `sed`, `head`, `tail` or `git`. Use
  `git -C /home/coder/repos/bbj-language-server …`. `cd` is acceptable only directly in front of
  `./gradlew`.
- No bare recursive `grep -r` or `find` over a directory. Scope with `--include`/`-name` or use the
  `Grep` tool with a `glob`. Never point any read at `.env*`, `*.pem`, `*.key` or a credential store.
- Stage commits with `git add <exact path>` only — never `git add -A` or `git add .`.
- Create files with the `Write` tool, not a `cat << 'EOF'` heredoc.
- The IntelliJ module's JDK is `JAVA_HOME=/opt/java/default`; every Gradle command in this plan
  carries it.

## Verified platform facts (checked against the pinned IDE, ideaIC-2024.2)

Confirmed by disassembling the platform classes on this machine's Gradle cache — treat these as
given, no re-verification needed:

1. `IntentionActionMetaData.INTENTION_DESCRIPTION_FOLDER == "intentionDescriptions"`, and
   `getResourceLocation` calls `ClassLoader.getResource(...)` on the **directory** path
   `intentionDescriptions/<dirName>` before it ever looks for a file — a missing directory entry is
   the exact null that raises the reported `PluginException`.
2. `BeforeAfterActionMetaData.DESCRIPTION_FILE_NAME == "description.html"`,
   `BEFORE_TEMPLATE_PREFIX == "before"`, `AFTER_TEMPLATE_PREFIX == "after"`,
   `EXAMPLE_USAGE_URL_SUFFIX == ".template"` — hence `before.bbj.template` / `after.bbj.template`.
3. `<dirName>` defaults to the action class's **simple name** (the reported message names
   `ConfigureMsgboxIntention` directly); an `<intentionAction>` may override it with an explicit
   `<descriptionDirectoryName>` child, which none of the current three uses.
4. `IntentionPreviewInfo.Html` is a public final class implementing `IntentionPreviewInfo` with a
   public `Html(java.lang.String)` constructor in 2024.2 — no `HtmlChunk` import is required.
5. Gradle's `jar` task writes directory entries (the existing jar lists `icons/` as a 0-byte entry),
   so the directory URL the platform needs will resolve from the packaged plugin.
6. The composed plugin jar is `bbj-intellij/build/libs/bbj-intellij-0.1.0.jar` — `gradle.properties`
   declares no `version`, so `build.gradle.kts`'s `getOrElse("0.1.0")` decides it.
7. The Gradle `test` task's working directory is the module directory, which is why the existing
   `*SourceGuardTest` classes resolve sources as `Paths.get("src", "main", …).toAbsolutePath()`.
   Reuse that idiom; do not invent a repo-root search.

## Flagged assumptions

Surfaced, not dropped:

1. **Shipping the resource and returning an Html preview are both kept, deliberately.** Either alone
   would silence the reported exception, but the Settings › Editor › Intentions page reads the
   resource independently of the popup, and a future intention that goes back to an EMPTY preview
   would re-enter the fallback path. Redundancy here is cheap and the failure it prevents is an IDE
   error report.
2. **The guard asserts against the source tree, not the runtime classpath.** The IntelliJ Platform
   Gradle plugin composes the test classpath itself, so a `getResource` assertion inside the JUnit
   run would pin build-tool behaviour rather than the shipped artifact. The packaged-jar inspection
   in Task 3 covers the packaging half instead, where the real question lives.
3. **The before/after templates are illustrative, not executable fixtures.** They are rendered
   side-by-side in the settings page. The values used are semantically real (MSGBOX mode `36` =
   Yes/No buttons `4` + Question icon `32`; window flags `$00040083$` = Border `$40000$` + Maximizable
   `$80$` + Close box `$2$` + Resizable `$1$`), so the documentation does not teach a wrong constant.
4. **The stale-edit behaviour of UAT test 6 is untouched by this plan.** The user's report bundled two
   observations; the java-interop editor banner is `BbjJavaInteropNotificationProvider` and is not a
   defect, and the stale-edit abort itself remains an open human-verification item, restated in the
   verification section below.

| build → shipped artifact | Resources must survive `processResources` and `jar` as directory entries plus files to be reachable at run time |
