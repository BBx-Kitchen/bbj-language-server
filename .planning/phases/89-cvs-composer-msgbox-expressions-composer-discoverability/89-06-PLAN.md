<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 3: Decide how config files get the shared cue — this reverses a pinned Phase 84 invariant</name>
  <decision>How the config.bbx SETOPTS composer receives its composer cue in both IDEs (D-01 and D-02)</decision>
  <context>
    D-01 makes one server-side `textDocument/codeLens` the only cue source and retires VS Code's client-side
    SETOPTS lens. D-02 requires the config.bbx composer to get that cue in this phase.

    Neither IDE sends a config file to the language server today:
    - VS Code's language client selects only `bbj` documents;
    - IntelliJ maps only the BBj language, and Phase 84 pinned that in
      `BbjConfigFileTypeRegistrationTest` ("exactly one LSP4IJ language mapping — naming BBj — so a config
      file never reaches the language server").

    Undo cost if chosen wrongly: a revert of two client registrations, one builder filter and one test —
    no data or published contract. It is still a human call because it overturns a prior phase's pinned
    decision. Plans 89-11 and 89-12 implement option `route` and run only if this line records `route`.
  </context>
  <options>
    <option id="route">
      <name>Route config files to the language server under their own `bbx-config` language id (recommended)</name>
      <pros>
        Literal D-01/D-02: one lens mechanism for all five composers in both IDEs, with no plugin-side
        rendering code. The server never parses, indexes or diagnoses the config file — a builder filter
        drops it. The VS Code client-side SETOPTS lens is retired in the same plan, so there is never a
        double cue. Phase 84's real goal (never treated as BBj source, no BBj diagnostics) is preserved
        and re-pinned as a refined invariant.
      </pros>
      <cons>
        Overturns Phase 84's "never reaches the server" guard. The config file's text reaches the local
        server process. Other feature requests on the config file get fast cancellation answers instead of
        none. In IntelliJ, opening only a config file starts the BBj server.
      </cons>
    </option>
    <option id="bridge">
      <name>Keep config files off the language-server document channel; bridge through a custom request</name>
      <pros>Phase 84's invariant stays literally true; the lens data is still server-computed.</pros>
      <cons>
        Two lens transports. VS Code keeps a client-side provider registration for config files. IntelliJ
        needs its own Code Vision provider for the config file type (new platform API surface and EDT care).
        Requires re-planning plans 89-11 and 89-12.
      </cons>
    </option>
    <option id="defer">
      <name>Defer the config.bbx cue</name>
      <pros>Smallest change now.</pros>
      <cons>
        Contradicts D-01 (retirement not done, half-migrated) and D-02 (config.bbx cue in this phase, not
        deferred). IntelliJ config files keep no cue. Needs an explicit deferral recorded against DISC-01.
      </cons>
    </option>
  </options>
  <resume-signal>Type `route`, `bridge` or `defer`. The executor records `Config routing decision: <choice>` verbatim in 89-06-SUMMARY.md. On `bridge` or `defer`, the orchestrator must re-plan 89-11 and 89-12 before they execute.</resume-signal>
