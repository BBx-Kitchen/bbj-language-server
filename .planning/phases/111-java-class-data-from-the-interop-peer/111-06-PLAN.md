<objective>
Close the two gaps 111-VERIFICATION.md recorded against SEC-03 (and the D-02 bound that the SEC-04
plan delivered on the hover path). Both are also findings in 111-REVIEW.md.

1. A method or constructor entry from the peer with no `parameters` key at all survives
   `sanitizeJavaClassDto` (which by contract leaves an absent list for the caller's own `??= []`),
   but no caller ever defaults it. Phase 2 of `resolveClass()` then throws a TypeError on
   `undefined.entries()` / `for...of undefined`. The single `catch (e) { console.error(e) }` swallows
   it, and every method and constructor after that entry is left without `resolvedReturnType`,
   `docu` or linked parameters. D-03 lists `parameters` among the arrays that default to `[]`. The
   fix follows the existing `javaClass.fields ??= []` pattern in Phase 1.
2. Hover's javadoc-file fallback bounds the javadoc body (`MAX_JAVADOC_LENGTH`), but
   `toMethodDocToMethodData` copies `methodDoc.name` and every `params[i].name` unbounded into the
   bold signature header. D-02 requires hover's fallback path to be bounded. The fix bounds both
   names with `truncateText(…, MAX_JAVA_IDENTIFIER_LENGTH)`. A name that is not a string falls back
   to the node's own name, which is already bounded, so the new bound cannot throw (D-03).

Both fixes were measured at planning time. The planner ran a scratch probe test against HEAD
`25ea70bd`, made a temporary source edit, ran the probe again, then restored both source files and
deleted the probe. The bbj-vscode tree was clean afterwards. Results:
- Absent `parameters` at HEAD: the method case and the constructor case both fail with
  "expected undefined to deeply equal []". With the two `??= []` lines, both pass.
- MethodDoc fallback at HEAD, with a 5,000-character method name and parameter name: the hover
  string is 10,043 characters. With the bound it is 2,091. A method name 42 plus parameter name 7
  renders `__Object HashMap.42\(Object 7\)__` at HEAD; with the fix it renders
  `__Object HashMap.put\(Object \)__`.
- The six regression files listed under verification stayed green with the edit (102 tests), and
  tsc was clean.

The two gaps touch disjoint files. Task 1 is the tracer: it proves the severe crash fix end to end
through the real `resolveClass()` pipeline. Task 2 closes the hover render path. Only one plan is
used, because the project prefers lean gap closure and base-check degrade runs plans sequentially
anyway.

Purpose: ROADMAP criterion 1 says a malformed peer response must be rejected or truncated, not
crash resolution. D-02 says every path that renders Java class data is bounded, including hover's
fallback.
Output: two defaulting lines in `java-interop.ts`, one bounded-name helper in `bbj-hover.ts`, and
four regression tests split across the two existing phase test files.
</objective>
