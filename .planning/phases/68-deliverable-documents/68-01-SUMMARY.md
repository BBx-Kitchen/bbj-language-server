## Accomplishments

## Decisions Made

- **`failure_scenario:` sourced from COVERAGE, not 67-APPLY-SET.md, for EASY-FIXES.md rows.** D-04 says row content is lifted from 67-APPLY-SET.md; empirically, `derive-apply-set.mjs`'s own `firstThreeLines` truncation left 67-APPLY-SET.md's copy of `failure_scenario:` shorter than the COVERAGE original for 41 of 77 rows. Since a must_haves.truth requires this field to be identical to its COVERAGE source after whitespace-collapse, `unit`/`location`/`dimension`/`severity`/`effort`/`failure_scenario` are all read from the record's own COVERAGE fields; only the six fields with no COVERAGE equivalent (`verdict`, `fix_applied`, `user_facing`, `verification`, `commit`, `notes`) are lifted from 67-APPLY-SET.md by `finding_id`.
- **`proposed_labels:`'s PRIO and effort components are mechanically derived**, not judgment: INVENTORY §3d's locked severity→PRIO table (critical/high→PRIO 1, medium→PRIO 2, low→PRIO 3) and the already-recorded effort value. Only the area component is a genuine placeholder (`PENDING-AREA`), matching the "Labels are applied from INVENTORY §3d's locked scales, never re-derived" principle in D-09.
- **Task 2's own `check` assertions require the full field sets to exist**, so `renderEasyRow`/`renderMajorBlock` were extended to their complete 14/16-field shape (with `PENDING-APPROACH`/`PENDING-AREA`/empty `issue:` placeholders for genuine judgment content) within this plan, rather than deferring field *scaffolding* to a later plan — only the judgment *content* behind the placeholders remains pending.
- **`git cat-file -e` (via `child_process.execFileSync`) is used for sha resolvability**, added in Task 2. The threat model's "no child_process" note in the register is explicitly scoped to Task 1's own acceptance criteria; T-68-05 requires exactly this mechanism for Task 2.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Off-scale-effort detection compared the full annotated effort string instead of its bare leading digit**
- **Found during:** Task 3 (Reconciliation section authoring, before the task's commit)
- **Issue:** `easyVerdictAndEffort`'s off-scale check compared the entire joined `effort:` field text against `['2','4','8']`. Two records (`P63-D8-006`, `P63-D8-007`) carry COVERAGE effort text `"2 (revised 2026-08-18: recorded as 1, ...)"`, which is not string-equal to `"2"` even though its bare leading number is on-scale — pulling them incorrectly into the "off-scale" list of `P61-D4-010`/`P61-D8-005`, producing "Two records — ... four IDs" in the generated Reconciliation prose.
- **Fix:** Extract the leading digit sequence via regex before comparing against `{2,4,8}`, matching the same bare-number extraction already used for the MAJOR-REFACTORS severity/effort distribution. Also made the "Two records" lead-in dynamic (`${offScaleEffortIds.length} records`) rather than a hardcoded literal, so a future corpus change cannot silently desync the prose from the count.
- **Files modified:** `.planning/phases/68-deliverable-documents/derive-review-docs.mjs`
- **Verification:** Regenerated both documents; `EASY-FIXES.md` §Reconciliation now reads "`2` records — `P61-D4-010` and `P61-D8-005` —"; `node derive-review-docs.mjs check` exits 0.
- **Committed in:** `6dcb450` (Task 3 commit — caught and fixed before commit, so no separate fix commit exists)
