<objective>
Close the Windows half of #536: the temp files that carry plaintext EM JWT output are owner-only from
creation on a filesystem with an ACL attribute view, exactly as they already are on POSIX, and the
call fails closed rather than producing a default-permission file when neither capability exists.

Purpose: `BbjProcessSecretEnv.createOwnerOnlyFile()` (lines 114-125) is the single choke point both
secret-file callers already use. Its POSIX branch (115-119) sets the owner-read/owner-write permission
set at creation and is the already-shipped fix (commit `1b731e4`) that TOKEN-02 verifies. Its
non-POSIX fallback (120-124) is a plain two-argument temp-file creation whose comment argues the
per-user temp directory is restrictive enough — a reasoned position, not an equivalent guarantee, and
the gap #536 asks to close. Replacing it with an explicit `acl:acl` attribute supplied at creation
gives Windows the same no-window property POSIX already has.

Output: a pure `OwnerOnlyAcl` builder in `lsp/`, a three-outcome `createOwnerOnlyFile`, new behavioural
tests that run on this Linux host, an extended source guard, and the manual Windows verification
recorded as a human UAT item. This plan is 80-02 of the four-plan split (D-18); it shares no file with
any other plan in the phase.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` — the phase scope replaces "the current default-permission **fallback**"
with a first-class Windows mechanism, so owner-only file creation stops having one primary
implementation plus a degraded fallback and gains a second equally-first-class implementation.

**Primary noun:** *the owner-only attribute supplied at creation*. That is now the thing the code names
and the thing every branch must produce; "POSIX permission bits" and "Windows ACL entry" are two
variants of it, not a primary and a substitute.

**Decision: `promote`.** `createOwnerOnlyFile` is restructured around a strategy the filesystem's
supported attribute views select (`selectOwnerOnlyStrategy`), with `posix` and `acl` as peer variants
and no third "do our best" path — the old fallback is deleted rather than demoted, because a branch
that produces a default-permission file is not a variant of "owner-only at creation". The absence of
both variants is an error, not a third variant (D-08). No accepted debt.

**Invariant test (accepted, implemented in Task 2):** every supported strategy yields an explicitly
restricted file and an unsupported filesystem raises rather than falls through —
`selectOwnerOnlyStrategy` is asserted over all three view sets, so a future phase that reintroduces a
silent fallback turns that test red immediately.
</assumption_delta_decision>
