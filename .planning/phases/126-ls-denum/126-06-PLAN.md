## Save-signal finding (planning research, 2026-10-03)

The user asked for format-on-save to keep its once-per-edit dedupe and Format Document to offer
every time. That needs a signal, available before or at the format request, that says "this format
belongs to a save". None is robust:

1. LSP: `textDocument/formatting` and `rangeFormatting` carry no trigger kind. Format-on-save calls the same provider as Format Document (`FormatOnSaveParticipant` uses
   `formatDocumentWithSelectedProvider(..., FormattingMode.Silent, ...)`; providers never see the
   mode).
2. VS Code runs every extension's `workspace.onWillSaveTextDocument` listener inside one
   extension-host save participant. The language client sends `textDocument/willSave` and
   `willSaveWaitUntil` from that same listener. In VS Code 1.40 the participant list was fixed, and
   this participant came last, after `FormatOnSaveParticipant`
   (`src/vs/workbench/api/browser/mainThreadSaveParticipant.ts` at tag 1.40.0). Today every
   participant has ordinal 0 and they run in registration order
   (`textFileSaveParticipant.ts`). The built-in participants register at `LifecyclePhase.Restored`
   (`contrib/codeEditor/browser/saveParticipants.ts:465`). The extension-host participant registers
   when the extension host connects, and that host starts on window idle after
   `LifecyclePhase.Ready` (`nativeExtensionService.ts:137`). Their order is therefore a race, and an
   extension-host restart always puts the extension participant last. A flag set in
   `onWillSaveTextDocument` usually arrives after the save's format request has been answered.
3. Waiting a short time for a `willSave` or `didSave` before offering only guesses from timing.
   It would also delay every explicit offer.

Fallback, as the user decided: offer on every request. Two VS Code facts soften repeated saves:
- `NotificationsModel.addNotification` (`workbench/common/notifications.ts:224-235`) closes a
  showing notification with the same message and buttons before it adds the new one, so offers
  replace each other instead of stacking.
- Format-on-save skips auto-saves (`SaveReason.AUTO`).

IntelliJ does not offer formatting today (UAT test 4), so it never sends these requests. No server
method or payload changes, and `ComposerRequestContractTest` is not affected.
