<objective>
Give the IntelliJ addWindow and addChildWindow dialogs the same gate VS Code has (DISC-07, #623): each malformed statement field shows the language server's error in a red label under it, and OK stays disabled until the preview is valid.

This plan:
- adds the per-field error strings and `valid` to the two preview DTOs, pinned at the LSP4IJ Gson boundary;
- renders an error label under every statement field and replaces the unconditional OK enable with `setOKActionEnabled(p.valid)`;
- pins, with a source guard, that neither dialog carries a validation rule of its own.

Purpose: IntelliJ can no longer insert text that VS Code refuses, and both IDEs gate on one shared verdict.
Output: DTO fields, updated dialogs, boundary tests and a source guard.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| language-server preview verdict → IntelliJ OK action | The server's `valid` flag decides whether the dialog may write |
| dialog OK → document write | The composed statement is inserted into the user's source |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-90-17 | Tampering | `AddWindowComposerDialog.apply` / `AddChildWindowComposerDialog.apply` enabling OK for a malformed statement | high | mitigate | `setOKActionEnabled(p.valid)` replaces the unconditional enable; the source guard forbids `setOKActionEnabled(true)`; OK also stays disabled during the debounce window and on a failed preview |
| T-90-18 | Tampering | plugin and server version skew where the server omits `valid` | low | accept | The Java `boolean` defaults to false, so OK stays disabled — fail closed; the bundled server always matches the plugin |
| T-90-SC | Tampering | npm/pip/cargo installs | low | accept | No dependency is added |
</threat_model>
