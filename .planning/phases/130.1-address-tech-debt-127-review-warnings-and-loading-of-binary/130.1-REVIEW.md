# Phase 130.1 Code Review

## Warnings

### WR-01: A failed lazy start is swallowed, so commands hit a dead client
**Files:** `bbj-vscode/src/extension.ts:1001-1007` (`startLanguageClient`), `bbj-vscode/src/language-client-starter.ts:17-46, 66-80`, `bbj-vscode/test/extension-activation.test.ts`
`startLanguageClient` ends in `client.start().catch(...)` and resolves after showing a popup, so the starter's cached promise always fulfils even when the server failed to spawn. The documented contract (cached rejection, `onStartError`, no retry) is dead code in production, and `extension.ts` passes no `onStartError`. Callers that `await clientStarter.ensureStarted(); client.sendRequest(...)` then send on a client in `StartFailed` state: `bbj.refreshJavaClasses`, `bbj.denumber` (`sendDenum`), in-code SETOPTS, and the `registerJavaClasspathCommands` lambda. The user sees the "did not start" popup and then a second, opaque error. The failure is never retried in the session. The activation test of the same name asserts only on the popup; its mocked `sendRequest` always succeeds, so its title is false.
**Fix:** let the start function reject so the starter caches a real failure; show the popup from the `onStartError` handler passed to `startOnServerDocuments`; have command paths surface the rejection, or clear `pending` on failure so a later trigger can retry. Assert that `sendRequest` was not called.

### WR-02: `TokenizedBbj.isTokenized` remembers a transient read failure as "not tokenized"
**File:** `bbj-intellij/src/main/java/com/basis/bbj/intellij/tokenized/TokenizedBbj.java:135-159`
The Javadoc says "a failure counts as not tokenized and is not remembered", but `readsTokenized` swallows `IOException` (and `!file.isValid()`) and returns `false`, which `cachedVerdict` stores until the modification stamp changes. `BbjLanguageServerFactory.isEnabled` then lets the binary through to the language server.
**Fix:** a tri-state read, for example throw on `IOException` in the compute path, which `cachedVerdict` already treats as "answer false, store nothing".

### WR-03: `mirrorVersionFor` can stall a successful Denumber for 5 s
**File:** `bbj-vscode/src/language/bbj-denum-service.ts:374-378, 416-466`
The success message waits until the mirror text equals `outcome.result.text` exactly, or until `DENUM_VERSION_WAIT_MS` (5 s) passes. If the editor's text is not byte-identical (EOL normalisation into a CRLF document, for example), the wait always times out. The message arrives 5 s late, the `running` claim is held for that time, and the list goes out unversioned, so no problems are placed. This applies only when diagnostics are non-empty; how often it triggers is unverified.
**Fix:** compare with EOLs normalised; better, reply immediately and send the versioned list asynchronously; at least release `running` before waiting.

### WR-04: Blocking VFS I/O inside `LSPClientFeatures.isEnabled`
**File:** `bbj-intellij/src/main/java/com/basis/bbj/intellij/lsp/BbjLanguageServerFactory.java:98-105`
On a cache miss, `isTokenized` opens the file inside a hot LSP4IJ path that may run on the EDT or under a read action. Which threads call it is unconfirmed.
**Fix:** on a stamp change, answer "enabled" and compute the verdict on a pooled thread that re-triggers connect or disconnect, or at least guard with `isDispatchThread()`.
