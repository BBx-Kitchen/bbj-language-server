# Phase 130.1 Plan 01: Decompile through a private bbjlst output directory Summary

**Decompile & Replace now runs `bbjlst -l [-xlst] -d<private dir>`, verifies the listing by file rather than exit code, and replaces the original atomically; verified against the real BBj 26.03 bbjlst for .bbj, .pub, extensionless and .lst inputs.**

## Accomplishments

- Root cause of the phase 127 hand-check failure fixed: `bbjlst -l` names its listing after the input minus the extension, so the old wait for `<input>.lst` never succeeded and could clobber a sibling file. With `-d<dir>` the listing has exactly the input's name inside that directory, for every extension.
- Success is judged only by the listing: it must appear, settle in size, be non-empty and no longer start with `<<bbj>>`. Each failure names its cause and carries bbjlst's own output under "Details".
- The original is replaced by a staged same-directory copy (`COPYFILE_EXCL`, target's permission bits, atomic rename); the staged file is removed on failure, never in place of the target.
- No private directory is left behind: replace always removes it; read-only keeps it only as the home of an opened document and removes it on any earlier failure.
- Dead `.lst` machinery (`lstPathFor`, `deleteLeftoverLst`, `waitForDecompileOutput`, `DecompileOutput`, `WaitOptions`), the "in place" flag, the second tokenized check, the file-name alias and the two source-text guards are gone.

## Decisions Made

- The shared core removes its directory on every failure itself (including a failing bbjlst launch), so neither command can forget it; the commands add cleanup only for steps after the core returns.
- `verifyListing` also rejects an absent listing, so a caller that skips the wait still gets a named cause.
- Read-only decides cleanup on whether a document was shown from the directory, not on which statement threw.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] replaceWithListing could delete a file it did not create**
- **Found during:** Task 2 (writing the staged-name collision test)
- **Issue:** The plan says to remove the staged file "on any failure". When the exclusive copy itself failed because the staged name was already taken, the cleanup would have unlinked whatever sat at that path, defeating the point of `COPYFILE_EXCL`.
- **Fix:** Track whether this call's own copy succeeded and only unlink then; a new test plants a file at the staged name and asserts it survives.
- **Files modified:** `bbj-vscode/src/decompile-io.ts`, `bbj-vscode/test/decompile-io.test.ts`
- **Verification:** `npx vitest run test/decompile-io.test.ts` passes
- **Committed in:** `bf13f8a1`

**2. [Process note] Task 2 tests were not red first**
- Task 1 (a tracer) already implemented the helpers and the Commands flow, so the Task 2 behaviour tests passed on first run, except the staged-name collision test, which exposed deviation 1. This is a consequence of the plan's task split, not a skipped step.
