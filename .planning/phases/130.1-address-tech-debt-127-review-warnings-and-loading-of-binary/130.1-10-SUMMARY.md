## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Hand check step 1 failed: a tokenized program opened in a window without another BBj file got no decompile prompt**
- **Found during:** Task 2 (the user's hand check, VS Code step 1)
- **Issue:** VS Code showed "The file is not displayed in the text editor because it is either binary or uses an unsupported text encoding." and no prompt. `activationEvents` held only `onLanguage:bbj` and `onLanguage:bbx-config` (the `onCommand:` entries went away in #600). A file shown as binary creates no text document, so `onLanguage:bbj` never fires; in a window with no other BBj text file open the extension was not active, so the `tabGroups.onDidChangeTabs` listener in `open-file-prompts.ts` never saw the tab. The listener's activation-time scan of open tabs would have caught the file once the extension was active. The manifest and `open-file-prompts.ts` confirm this chain; the failing step itself was not re-run in a live VS Code by the executor. Separately, `bbj.decompile` and `bbj.decompileReadonly` had no menu entry, so after a missed prompt only the Command Palette remained.
- **Fix (commit `a701165c`):** added `onStartupFinished` to `activationEvents`; added `explorer/context` entries for both commands (groups `BBj@6` and `BBj@7`) with the when clause `!explorerResourceIsFolder && resourceScheme == file && (resourceLangId == bbj || resourceExtname == .pub || resourceExtname == .src || resourceFilename =~ /^[^.]+$/)`. The extensionless case uses a filename regular expression (a bare name without a dot, so dotfiles such as `.env` are excluded) instead of `resourceExtname == ''`, because the regular-expression operator is the documented form and the empty-string comparison could not be confirmed. Both handlers already accept the Explorer argument: `resolveDecompileTarget` takes `params.fsPath` first and falls back to an active `bbj` editor, otherwise shows the "no active BBj file" warning. New test `bbj-vscode/test/decompile-manifest.test.ts` pins the activation event, both Explorer entries, the when-clause parts and the target resolution.
- **No `editor/title` entry:** the only way to target the binary placeholder is `activeEditor == 'workbench.editors.files.binaryFileEditor'`, an undocumented pane id, and it would put the command on the title bar of every binary file. The Explorer entries cover every name a tokenized program carries, so the entry was left out.
- **Side effect of `onStartupFinished` (resolved by deviation 3):** `activate()` now runs in every VS Code window, including workspaces with no BBj file. It registers the commands, composers and the settings migration and creates the status bar items (hidden until the server reports), which is cheap. It also starts the language client, which spawns the language server process, and the server's `initializeWorkspace` always calls `loadClasspath` and `loadImplicitImports` against the Java interop socket (default `localhost:5008`), even with no workspace folder. When BBjServices is not reachable the first failed connect raises one error popup (`Failed to connect to the Java interop service. Check that BBj Services is running and ...`, once per outage, from `java-interop-connection.ts`). So a user with the extension installed but no BBj running now gets that popup, a Node server process and a connection attempt in non-BBj windows. The user should decide whether to keep that or to restructure (for example start the server lazily on the first BBj document and activate on startup only for the tab listener); nothing was changed.

**2. [Scope change by the user] Decompile no longer passes `bbjlst -l`, reversing the phase's earlier decision to always use it**
- **Found during:** Task 2 (the user's hand check, step 9, `tok-numbered.bbj`)
- **Issue:** `bbjlst -l` removes the line numbers but leaves the numeric jump targets behind. The sample `0010 PRINT "Hello" / 0020 GOSUB 0100 / 0030 END / 0100 PRINT "Sub" / 0110 RETURN` decompiled to `PRINT "Hello" / GOSUB 0100 / END / PRINT "Sub" / RETURN`, a broken program that Decompile & Replace then wrote over the original. Without `-l`, `bbjlst` returns a numbered program unchanged and an unnumbered program unchanged (both re-checked byte for byte against `handcheck/src/` with the real `/opt/bbx/bin/bbjlst`). A numbered result then gets the existing line-numbered information message and Denumber turns the targets into labels.
- **Fix (commit `52ea0271`):** `buildDecompileArgv` (`bbj-vscode/src/Commands/process-args.ts`) and `BbjLstCommand.argv` (IntelliJ) no longer emit `-l`; `-xlst` for a `.lst` input, `-d<outputDir>` and the file name last are kept; both doc comments updated. Tests that pinned `-l` were changed to assert it is absent (`decompile-io`, `command-argv-injection`, `commands-cjs-execution`, `BbjLstCommandTest`), and a new real-`bbjlst` JUnit test checks that a numbered program comes back identical with its jump targets. The two decompile command docs (`documentation/docs/vscode/commands.md`, `documentation/docs/intellij/commands.md`) and QA rows 39 and 44 now say that Decompile returns the program as written; the VS Code command doc also dropped "Command Palette only" for the new Explorer entries and QA row 39 got a step 5 for them. No source guard test pinned `-l`.
- **Files modified:** `bbj-vscode/package.json`, `bbj-vscode/src/Commands/process-args.ts`, `bbj-vscode/src/Commands/Commands.cjs` (comment only), `bbj-intellij/src/main/java/com/basis/bbj/intellij/tokenized/BbjLstCommand.java`, the four test files above plus `bbj-vscode/test/decompile-manifest.test.ts`, the two docs and the QA checklist.

Hand check step 9 changes meaning accordingly: Decompile & Replace on `tok-numbered.bbj` is now expected to give the numbered source back unchanged, followed by the line-numbered information message.

**3. [Scope change by the user] The language server now starts lazily, on the first BBj document, instead of at every activation**
- **Found during:** Task 2 follow-up. Deviation 1's `onStartupFinished` made `activate()` run in every window, and `activate()` started the language client, so the server spawned and connected to the Java interop service (`localhost:5008`) in windows with no BBj file; without BBjServices that raised the "Failed to connect to the Java interop service" popup. The user chose a lazy start.
- **Fix (commit `78254201`):** the extension still activates on `onStartupFinished`, but activation now only registers the commands, composers, the tab listener and its activation scan (`registerOpenFilePrompts`), the settings migration, the status bar items, the notification handlers and the config-association listeners. The `LanguageClient` is constructed there but not started. A new module `bbj-vscode/src/language-client-starter.ts` holds a once-only start (one cached promise, so concurrent triggers share one start and a failed start is reported once, not retried per document) and a trigger that starts it for a document with language id `bbj` or `bbx-config`, either already open at activation (`workspace.textDocuments`) or opened later (`onDidOpenTextDocument`). Commands that need the server start it first and then send: Denumber (`sendDenum`), Refresh Java Classes, and the in-code SETOPTS composer's request sender. Decompile only spawns bbjlst and needs no server; its result opens as a `bbj` document, which starts the server anyway. A tokenized file shown as binary creates no text document and so does not start it.
- **Client references made safe:** (1) `client.onNotification` in the diagnostic status bars, the formatter-settings link, the denumber diagnostics, the config-reload status and the config association: unchanged, because `vscode-languageclient` holds handlers registered before `start()` and attaches them when it starts (checked in the installed 10.1.2 source, `onNotification`); (2) `initializationOptions` is now a function, evaluated when the client starts, so a setting changed between activation and the first start reaches the server; (3) the workspace-trust settings re-push no longer sends to a client that is not running (`needsStop()`), since it reads the settings at start; the push middleware only ever runs on a running client; (4) the restart gate (`createRestartGate(client, ...)`) is only reached through a server notification, so it always sees a started client, and it still reuses the one instance; (5) `deactivate()` keeps `client.stop()`, which returns at once for a client in its initial state; (6) the old `if (!client)` guard in Refresh Java Classes is replaced by the awaited start, and a failed start shows the existing "did not start" error and sends no request; (7) the module-level `client` is always assigned during `activate()`, so no `client!` use exists. The server-side code is untouched.
- **A non-BBj window** now creates no server process, makes no interop connection and shows no popup. A `**/*.bbj` file-system watcher is still created at activation (a VS Code-side watcher, no server involved).
- **Tests:** new `bbj-vscode/test/language-client-starter.test.ts` (13 tests: once-only start, concurrent triggers, cached failure, synchronous throw, an already-open bbj and bbx-config document, a later open, other languages never starting it, a command-started client not starting twice, error callback, disposable; plain functions and controllable promises, no `vi.fn`). `extension-activation.test.ts` gained seven activation-level tests (no start without a BBj document and handlers still registered, other-language document, already-open document, later document, Refresh Java Classes starting first and sending after, no second start, failed start reported and nothing sent). - **Docs:** `documentation/docs/vscode/configuration.md` and `getting-started.md` said the interop service starts with the extension; they now say the server connects when the first BBj file opens. The QA checklist has no activation or startup wording and was not changed.
- **Files modified:** `bbj-vscode/src/extension.ts`, `bbj-vscode/src/language-client-starter.ts` (new), `bbj-vscode/test/language-client-starter.test.ts` (new), `bbj-vscode/test/extension-activation.test.ts`, `extension-config-trust.test.ts`, `activation-command-coverage.test.ts`, `config-reload-host.test.ts`, `composer-cue-single-source.test.ts`, the two docs.
