  <action>
File filing-order rows 18 through 52 as public issues, in Index order, in batches of about ten creates per
shell invocation so a failure costs at most a partial batch and never the plan.

Build the batch driver once and reuse it: read the draft's `## Index` rows 18-52 into a tab-separated
worklist of `row`, `finding_id`, `title`, `area`, `prio`, `effort`. Snapshot the tracker once at the start
with `gh issue list --state all --limit 1000 --json number,title` into a temp file — that snapshot plus the
ledger is the resume-check source, and matching locally avoids a search call per finding.

Per finding, in order:

1. **Resume check** (D-14). Skip if the finding ID already has a ledger row, or if the snapshot holds an
   issue whose title equals the drafted title. Record each skip with its reason.
2. **Slice the body.** `awk` range bounded by that finding's `BODY-BEGIN` and `BODY-END` marker lines,
   both excluded, into a temp file. Assert the slice is non-empty and contains all six section headings
   before posting; an empty or short slice is a hard stop, not a warning.
3. **Create.** `gh issue create --title "$TITLE" --body-file "$BODYFILE" --label "$AREA" --label "$PRIO"
   --label "$EFFORT"`. Never `--body` with interpolated text; never a heredoc built from record prose.
4. **Ledger row, immediately.** `finding_id`, `route: issue`, `entry:` the issue number parsed from the
   returned URL, `url:`, `created_at:` — appended before the next create is attempted. This is the one
   mechanism that makes an inline run recoverable, and it is not optional (D-14).
5. **Pace.** A short delay before the next create, to stay clear of GitHub's content-creation secondary
   rate limits. 70 creates is well inside the hourly allowance and can trip the per-minute one.

Stop on the first rejection of any kind — rate limit, permission, validation, unknown label — record the
finding ID and the error in the ledger, and do not continue. Do not retry a create whose outcome is
unknown without first re-listing the tracker and matching the title; a blind retry is how a public tracker
gets two copies of the same issue.

Six records in the 18-87 range carry a `dedup:` annotation and three fall in this batch — `P61-D1-007`,
`P61-D5-003` and `P63-D4-010`. They are filed like everything else; their annotation is already in the
approved body and nothing about the create changes for them (D-08).

**Create no label.** All twelve values already exist. An unknown-label rejection means the draft and the
repository disagree, which is a discrepancy to report, not a label to invent.

| an interrupted run → its own resume | the ledger and the deterministic title are the only things standing between a crash and a double-filed public tracker |
