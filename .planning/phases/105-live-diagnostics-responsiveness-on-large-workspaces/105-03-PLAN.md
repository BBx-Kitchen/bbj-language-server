<objective>
Give the live parse its own interop connection so it never waits behind the class lookups the
startup build sends.

The tracer: a fake peer behind the real `connect()` path. The shared connection has fifty
`getClassInfo` requests outstanding and unanswered, as during a large workspace's startup build. A
`parseProgram` call opens a second connection, sends the parse there, and gets its answer — while
the fifty lookups are still pending. That one path touches every layer: `parseProgram()`'s routing,
the lazy dedicated connection, the socket and message-connection seams, and the fake peer.

The expansion task adds the D-10 fallback, the connection lifecycle (lost, reset, cleared, older
server) and the latch/verdict interplay.

Purpose: RESP-04 and issue #692's second serialization point. vscode-jsonrpc writes each request to
the socket at once and bbj-ls reads one connection's messages in order, so a client-side priority
queue could not help (D-08); a second socket gets its own reader and its own parser worker on the
server.
Output: the dedicated connection in `java-interop.ts`, per-connection scripting in
`test/fake-interop-peer.ts`, and `test/java-interop-parse-lane.test.ts`.

<decisions_resolved_here>
1. **One class, not a new service (research Alternatives):** the dedicated connection lives in
   `JavaInteropService` next to the shared one and reuses `interopHost`/`interopPort`,
   `createSocket()` and `wrapSocket()`. No IntelliJ-side change: both IDEs configure the port
   through the same initialization option.
2. **Breaker and generation (Claude's discretion item 2, research Open Question 2):** no second
   breaker. The dedicated connection is tied to the current `connectionGeneration`: opened once per
   generation, retired when the generation moves on, not retried in a generation where opening it
   failed. Opening it does not bump the generation (the server behind it is the one the shared
   connection already probed); losing it after it was open bumps the generation once, so the parser
   service's existing reset clears verdict state — "a reset of either connection clears verdict
   state".
3. **Lazy open (research Open Question 3):** on the first parse, matching the shared connection.
   Plan 05's measurement shows whether a cold dedicated connection costs anything noticeable.
4. **Log level for the fallback:** one `logger.warn` per generation — a degraded but working state
   that should be visible without the debug setting; never `notifyJavaConnectionError`.
5. **Older servers:** a `MethodNotFound` on the dedicated connection closes it for the rest of the
   generation, so a pre-endpoint BBj never keeps an idle second socket.
</decisions_resolved_here>

<flagged_assumptions>
1. **Residual server risk (research A2).** `bbj-ls`'s shared-AST-cache guard (`ParserCacheGuard`,
   commit 9987bee on `develop`) is in the BBj install in this container but was not yet on the
   `release/26.03` branch when researched. A 26.03 build without it could, on a new connection's
   first parse of a program another connection already parsed, answer from a stale source snapshot.
   That is a server fix to backport, outside this repository; it is recorded as a transferred threat
   below and in the pull-request text in plan 05. The user authored the fix.
2. **Server concurrency (research A3).** bbj-ls dispatches every connection on a shared cached
   thread pool; a saturated pool could still delay the dedicated connection's dispatch. Not probed
   under load; the plan 05 measurement is the live evidence.
</flagged_assumptions>
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| language server → local interop socket (second connection) | A second TCP client of the same configured host and port, loopback by default; carries the document's text for parsing. |
| interop answers → published diagnostics | A parse result from either connection becomes BBj Parser diagnostics. |
