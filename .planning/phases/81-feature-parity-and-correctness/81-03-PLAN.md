<objective>
Make IntelliJ's line-comment toggle recognise BBj's `rem` in any case, so toggling an already
commented line removes the prefix instead of stacking a second one.

Purpose: `BbjCommenter` today is a plain `Commenter` that returns the literal `"REM "`, and the
platform's generic toggle compares that literal case-sensitively. So a line reading `rem foo` — the
casing BBj sources actually use — is not seen as commented, and Ctrl+/ turns it into `REM rem foo`
(#540). The fix is to take ownership of the toggle: implement `SelfManagingCommenter`, decide
"is this line commented?" ourselves, and strip the prefix ourselves.

Two platform facts shape the implementation and both were verified against the exact 2024.2 SDK jar
this build compiles against. `SelfManagingCommenter` does not extend `Commenter` at the bytecode
level, so `BbjCommenter` must implement both — `getLineCommentPrefix()` is still read by other call
sites. And a self-managing commenter bypasses `LINE_COMMENT_AT_FIRST_COLUMN`, which
`BbjLanguageCodeStyleSettingsProvider` sets to true today; to preserve that behaviour the insert
position has to be hard-coded to column 0 rather than left to a setting the platform will no longer
consult.

Output: a plain-Java `RemToggleSeam` with no platform imports, a `BbjCommenter` that delegates every
line decision to it, a behavioural JUnit 5 test class whose method names carry #540's acceptance
wording, and a source guard over the wiring. This plan is 81-03 and is independent of every other plan
in the phase — in particular it does not use 81-02's lexer COMMENT token (D-15).
</objective>

## Flagged assumptions

Surfaced, not dropped. Each needs a human read at verification time.

1. **The eleven-method interface list is pinned to IntelliJ Platform 2024.2.** RESEARCH.md disassembled
   the exact `util-8.jar` this build resolves. If the platform target in `build.gradle.kts` moves, the
   method set could change and `BbjCommenter` would stop compiling — a loud failure, not a silent one,
   which is why no runtime fallback is planned for it.
2. **Block-comment methods are implemented as "no block comments exist in BBj".** BBj has no block
   comment form, `Commenter.getBlockCommentPrefix()` already returns null today, and the five
   block-related self-managing methods have no meaningful behaviour to provide. They return null or do
   nothing. If a future BBj construct is treated as a block comment, these are the five methods to
   revisit.
3. **The column-0 insert is asserted by the seam test, not by a live editor.** C-01 keeps the platform
   test framework out of the module, so `commentLine`'s document edit is proven by the seam's string
   result plus a source guard that the commenter computes its replacement from the line start offset.
   Live confirmation that an indented line gets its prefix at column 0 is a UAT item.

<assumption_delta_decision>
The deterministic assumption-delta probe fired one `pluralization` signal on this phase's scope, on
the phrase "removes the prefix instead of adding a **second** one" in PARITY-03's roadmap wording.

- **Primary noun:** unchanged — a *line* is still the unit the toggle reasons about, and there is
  still exactly one comment form in BBj.
- **Decision:** `no-change`. The signal is a false positive: "a second one" describes a duplicated
  prefix on one line, not the introduction of a second kind of comment, a second commenter, or a
  second prefix. Nothing in this phase generalises a singular concept to a plural one; `REM ` remains
  the only prefix and `RemToggleSeam.COMMENT_PREFIX` remains the single place it is written.
- **Invariant already encoded:** Task 2's Test 3 round trip asserts that toggling on and then off
  returns the original line character for character, which is exactly the property a genuine
  "second prefix" regression would break.

Advisory only; this checkpoint does not block the phase.
</assumption_delta_decision>
