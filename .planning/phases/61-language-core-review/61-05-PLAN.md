`bbj-completion-provider.ts` build markdown from Java class, member and javadoc text that originates
with the java-interop peer, and from document content. Concrete checks: whether any such text is
inserted into markdown without escaping, so that peer- or document-controlled content can render as a
link, an image, an HTML fragment or a command URI inside the IDE; whether `bbj-code-action-provider.ts`
constructs a workspace edit or a command from untrusted text; whether `bbj-use-insert.ts` builds an
insertion from a value it does not control; and whether any provider logs document content or resolved
paths at a level that reaches a user-visible output channel. A defect in what the peer is permitted to
send is a cross-unit referral to `RU-61-06`; a defect in how this unit renders it is a finding here.

rejections, swallowed exceptions, async races, off-by-one, wrong edge-case behavior and resource leaks.
Three checks are required by name, because they are the phase's translated edge probes:
  - **Touching and coinciding ranges.** A completion request at the exact boundary between two tokens; a
    hover over a zero-width range or over a position where two node ranges coincide; a document symbol
    whose range exactly equals its parent's. Does the provider merge them, return both, or return
    neither?
  - **Empty and single-element inputs.** What each provider returns for an empty document, a
    single-token document, and a position with no AST node under it — an empty list, `undefined`, or a
    thrown error. Record the actual behavior per provider; the shipped Phase 59 decision that the `(`
    trigger returns an empty `CompletionList` rather than `undefined` is deliberate and is not a finding.
  - **Order stability.** Whether two equal-ranked completion items or two equal document symbols come
    out in a specified, stable order, and whether any provider depends on ordering it does not control.
Beyond those three: cancellation-token handling on every async provider — whether a cancelled request
still resolves or leaks; unhandled rejections when a provider awaits java-interop and the peer is
unavailable; and swallowed exceptions in `bbj-document-symbol-provider.ts`, whose resilience was a
v3.7 concern. Each claim needs a runnable reproduction — a fixture plus the exact `npx vitest run`
command — or a line-by-line trace naming the concrete input and the exact `file:line` where behavior
diverges.

caches or debounces, redundant AST traversals and unbounded memory growth. These providers run on
