<objective>
Every BBj document open in an editor gets full language support (Langium validation, the live BBj parser check, and the BBjCPL compiler check) wherever it lives on disk. The PREFIX skip applies only to PREFIX library files that are NOT open.

Purpose: BBj's default PREFIX includes the plugins dir, and customers usually add their own development directory to PREFIX. Today `BBjDocumentBuilder.shouldValidate` and `shouldCompileWithBbjcpl` skip every document for which `BBjWorkspaceManager.isExternalDocument` is true, including open ones. `shouldValidate` also pre-marks those documents `DocumentState.Validated` without validating them. As a result whole projects get no `textDocument/publishDiagnostics` at all, in both VS Code and IntelliJ.

Output: a single predicate `isClosedLibraryDocument` that replaces the path-only gate at every site that decides diagnostics or full linking for a document. A close path that clears diagnostics and turns the document back into a library document. Hermetic vitest coverage for requirements U09-R1 to U09-R4.

Requirement map (the user's four numbered requirements):
- U09-R1: open documents are exempt from the PREFIX gate (sites decided in `<site_decisions>`). Covered by Task 1.
- U09-R2: a pre-marked PREFIX document is validated on open. Langium already rebuilds it (see `<langium_findings>`), so Task 1 proves this with a test.
- U09-R3: on close, publish empty diagnostics and turn the document back into an unvalidated library document. Covered by Task 2.
- U09-R4: tests. Split across Tasks 1 and 2. Task 3 runs the full gates.
</objective>

<langium_findings>
Checked against the Langium 4.3.1 sources in bbj-vscode/node_modules/langium:

1. didOpen. `NormalizedTextDocuments.set()` and the `listen()` didOpen handler fire `onDidOpen` and then `onDidChangeContent`. `addDocumentUpdateHandler` (lsp/language-server.js:219) routes `onDidChangeContent` to `DefaultDocumentUpdateHandler.didChangeContent`, which calls `fireDocumentUpdate([uri], [])`, which calls `DocumentBuilder.update([uri], [])` under the workspace lock. `DefaultDocumentBuilder.update()` (workspace/document-builder.js:74-122) calls `resetToState(changedDocument, DocumentState.Changed)` on every changed URI, whatever the text and whatever the current state. That clears index content, local symbols, links, diagnostics and buildState, so the document is rebuilt through every phase, and `shouldValidate` is asked again with the open-time build options. Result: a PREFIX document that was pre-marked Validated IS rebuilt on open. Once `shouldValidate` stops refusing open documents it is validated. U09-R2 needs a test, not new code.
2. didClose. `DefaultDocumentUpdateHandler` has no `didCloseDocument`. `addDocumentUpdateHandler` subscribes `onDidClose` only when the handler defines that method. `addDiagnosticsHandler` (language-server.js:268) publishes empty diagnostics only for URIs reported as deleted. So closing a document publishes nothing, and its last diagnostics stay in the client. U09-R3 needs code.
3. A document skipped by `shouldValidate` is marked completed and gets no `notifyDocumentPhase(Validated)`. A rebuild of a closed library document therefore publishes nothing. The empty publish has to be explicit.
4. `DefaultLangiumDocumentFactory.update()` (workspace/documents.js:156) reads the open TextDocument when one exists and otherwise reads the file from `FileSystemProvider`. Rebuilding a closed document therefore restores the on-disk text and drops any unsaved editor edits.
5. `DefaultWorkspaceLock` rejects the write promise when an action throws with anything other than a cancellation (workspace/workspace-lock.js:58-64). `DefaultDocumentUpdateHandler.fireDocumentUpdate` never attaches a handler to that inner write promise, and this server has no process-level unhandledRejection handler. The close rebuild must therefore not use `fireDocumentUpdate`. It needs its own chain that ends in a logged catch.
</langium_findings>

<site_decisions>
Every `isExternalDocument` call site under bbj-vscode/src/language, and the decision for each. Rule: a site that decides diagnostics, compiler arming, or how completely the document's OWN AST is linked or scoped switches to `isClosedLibraryDocument` (open documents are exempt). A site that decides indexing or affected-documents relationships between library files keeps `isExternalDocument`.

| Site | What it decides | Decision |
|------|-----------------|----------|
| bbj-document-builder.ts `shouldValidate` | Langium validation; also pre-marks skipped documents Validated | EXEMPT open docs (`isClosedLibraryDocument`). The pre-mark stays for closed library documents. |
| bbj-document-builder.ts `shouldCompileWithBbjcpl` | live-parse and BBjCPL arming (rebuild path, event path, and the trigger-off clearing loop) | EXEMPT open docs. |
| bbj-document-builder.ts `revalidateUseFilePathDiagnostics` (line 1208) | after imports load, removes false "could not be resolved" USE diagnostics from validated documents | EXEMPT open docs. An open PREFIX document is now validated, so its own USE diagnostics need the same cleanup as any other validated document. |
| bbj-linker.ts `link` | for a library file, links only non-private member signatures and prunes method bodies | EXEMPT open docs. See the note below. |
| bbj-scope-local.ts `collectLocalSymbols` | for a library file, collects local symbols only for non-private member signatures and prunes bodies | EXEMPT open docs. See the note below. |
| bbj-index-manager.ts `isAffected` (c757a8d6) | whether a library document is relinked when workspace documents change | LEAVE ALONE. This is about affected documents and performance. It is path-only on purpose. |
| bbj-ws-manager.ts `isExternalDocument` itself | path membership in PREFIX (issue #579 segment semantics) | UNCHANGED. path-containment.test.ts and the index manager rely on path-only semantics. The new predicate composes it. |

Note on the linker and scope-local rows. These deviate from the example in the task brief ("the scope provider's private-member filtering for external documents: leave alone"). bbj-scope.ts has no external-document logic. The private-member and body pruning lives in exactly these two methods, and it only affects the document's OWN local symbols and links, not what other files can see. The comment in bbj-scope-local.ts justifies it with "a reference deep inside a method body can never be resolved from outside that file". That is no longer true once the file is open: validation, hover, go-to-definition and completion in that editor all resolve references inside method bodies. Leaving the pruning in place would validate an open PREFIX document against method bodies that were never linked, with local symbols missing. Task 1 records evidence first: it runs the body-resolution test after the builder-only change and before touching these two files. For documents that are not open, the pruning stays exactly as it is today.
</site_decisions>
