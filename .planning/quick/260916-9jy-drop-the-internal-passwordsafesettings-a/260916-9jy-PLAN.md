<objective>
The IntelliJ Plugin Verifier's default `failureLevel` widened when PR #669 bumped the IntelliJ Platform Gradle Plugin from 2.11.0 to 2.18.1 (plugin 2.15.0 added internal and override-only API usages to the default). The v0.15.0 Manual Release (run 35064112482) therefore failed at `./gradlew verifyPlugin` with `Verification failed with [INTERNAL_API_USAGES] problems`, even though the plugin was reported **Compatible** against all four IDEs. The single flagged usage is the platform's internal password-settings service reader plus the deprecated do-not-store provider constant, both inside `BbjEMTokenStore.resolveBackend()`.

Root cause is already diagnosed and the fix is already decided — this is implementation, not investigation. Swap the classification source to the public `PasswordSafe.isMemoryOnly()`, then invert the source guard that currently pins the internal API's *presence*.

Purpose: unblock the next Manual Release (which must ship as 0.16.0 — tag `v0.15.0` already exists) and keep the verifier's stricter default in place so it can keep catching real internal-API drift.

Output:
- `BbjEMTokenStore.java`: two imports deleted, `resolveBackend()` rewritten against the public API, javadoc corrected
- `TokenBackend.java`: javadoc corrected (its claim about an unstable internal API stops being true)
- `EmTokenBackendNoticeSourceGuardTest.java`: inverted — it now proves the internal API is gone and cannot come back

**Accepted behaviour change (decided, not open):** the public surface distinguishes only *memory-only* from *persisted*. Nothing public tells an OS keychain from a KeePass file, so the #552 notice narrows from three-way to two-way: memory-only warns, anything persisted does not. KeePass users stop being told they are off the OS keychain. Do not invent a workaround, do not use reflection, and do not re-derive the KeePass distinction by any other means.

**Decision on the now-unreachable KeePass branch — KEEP BOTH.** The `TokenBackend.KEEPASS_FILE` constant and the `case KEEPASS_FILE:` branch of `showBackendBalloon()` stay exactly as they are. Rationale, confirmed by reading the files at planning time: `BackendNoticePolicyTest` names `KEEPASS_FILE` in 15 places across 7 of its 10 tests (including `aKeepassBackendNotifiesOnce`, `aDifferentNonKeychainBackendWarnsAgainWithoutAnInterveningKeychain` and the 8-thread concurrency test), and that test stays intact by decision. Removing the constant would force a rewrite of a test the task is explicitly told to preserve. The constant remains the policy's vocabulary for "some non-keychain backend"; production simply no longer produces it. `UNKNOWN` stays reachable in production via the null-instance and `Throwable` paths, so the balloon's other two branches are both still live.
