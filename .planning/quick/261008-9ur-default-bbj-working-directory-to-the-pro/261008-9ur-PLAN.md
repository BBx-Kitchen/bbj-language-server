<objective>
Make the BBj working directory and the language server's relative-path resolution agree, in both IDEs.

Decision map. The planning context numbers the locked decisions 1-4, and they are cited here as D-01..D-04:
- D-01: every run path (VS Code GUI/BUI/DWC, IntelliJ GUI/BUI/DWC) uses the project root as its working directory. In VS Code that is the workspace folder that contains the file. In IntelliJ it is the project base path. Both fall back to the file's directory when the file is outside, and there is no override setting.
- D-02: the language server resolves relative program paths the way BBj does: the working directory first, then PREFIX. The current file's directory is no longer a candidate, except as the fallback working directory for a document under no workspace folder.
- D-03: one shared candidate-builder for every site: USE scope, the USE validator, USE revalidation, addImportedBBjDocuments (decision below), RUN/CALL validation, hover, definition, and file-path completion.
- D-04: the stale-relink bug is out of scope and gets its own quick task. Nothing in this plan touches relinking.

Requirement IDs: 9UR-R1 = D-01, 9UR-R2 = D-02, 9UR-R3 = D-03.

Purpose: today the language server accepts `use ::OtherClass.bbj::` from subdir/prog.bbj because it also searches the program's own directory. BBj searches the working directory first and then PREFIX, so the program fails at runtime. On top of that, VS Code GUI, all BUI/DWC runs and IntelliJ BUI/DWC set the working directory to the program's directory, while IntelliJ GUI uses the project root.

Planner choices (discretion, apply exactly):
- Working directory of a document = the deepest workspace root that contains it, matched on path segments. This matches `vscode.workspace.getWorkspaceFolder`, which returns the containing folder. The document's own directory is used when no root contains it, when there are no roots, or when the document URI is not a `file:` URI. In a multi-root workspace, a USE from folder A therefore no longer resolves through folder B, because at runtime the working directory is A.
- RUN/CALL PREFIX candidates now go through `containedPrefixCandidates` as well, the rule USE has followed since #526. One shared helper means one rule.
- addImportedBBjDocuments keeps loading PREFIX candidates only. Workspace-root files are already loaded by the workspace traversal, and the fallback-directory candidate was never disk-loaded before either.
- BUI/DWC runs pass the program's absolute path as the web.bbj programme argument, which is the same value the GUI run already passes. With the working directory at the project root, the old bare file name would not be found for a program in a subfolder. The EM app name and the `bbj.web.apps` lookup still use the file's base name, so they do not change.

Output: the shared helper module, all LS sites switched to it, both IDEs' run commands switched, updated and new tests, and a short note in both run-command docs.
</objective>
