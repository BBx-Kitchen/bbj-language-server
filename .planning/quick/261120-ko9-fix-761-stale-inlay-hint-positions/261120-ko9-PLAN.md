<objective>
Fix GitHub issue #761. Inlay hints can land at stale positions (for example inside a REM comment) while the user types.

Requirements for this quick task:
- KO9-R1: never answer textDocument/inlayHint from a parse whose text differs from the client's current text. Prefer waiting for the queued rebuild and answering with the new positions.
- KO9-R2: the wait is bounded and cancellable. If it gives up, the request fails with ContentModified, which VS Code and LSP4IJ both ignore silently.
- KO9-R3: no change for the common (fresh) case. Existing inlay-hint tests, lint, typecheck:test and build stay green. The change is scoped to inlay hints only. Semantic tokens and code lenses are a follow-up named in the issue and are NOT touched here.

Purpose: Langium 4.3.1's inlay handler (`addInlayHintHandler` -> `createServerRequestHandler` -> `waitUntilPhase` -> `DocumentBuilder.awaitDocumentState`) returns at once when the LangiumDocument's state is already >= IndexedReferences. A didChange only queues `DocumentBuilder.update` behind the WorkspaceLock write queue (`DocumentUpdateHandler.fireDocumentUpdate`). `update()` then awaits `findChangedUris` before `resetToState(Changed)`. In that window the request is served from the OLD CST. LSP4IJ then maps the old line/character onto its current text.

Output: an override of `getInlayHints` in `BBjInlayHintProvider` plus a nested regression describe block in the existing inlay-hint test file.
</objective>

## Verified facts (planner checked these in the installed sources; do not re-research)

### PITFALL: do NOT compare version numbers. It looks right and cannot work.
Issue #761 proposes comparing the built LangiumDocument's text-document version with the version in TextDocuments. In production the two are always equal:
- `DefaultLangiumDocumentFactory.update` (bbj-vscode/node_modules/langium/lib/workspace/documents.js:156-165) sets the document's `textDocument` property to the very instance held by TextDocuments.
- The BBj builder's `bindLiveTextDocument` (bbj-vscode/src/language/bbj-document-builder.ts:640) binds the live instance onto the LangiumDocument on every open/change event, before any re-parse.
- `TextDocument.update` (vscode-languageserver-textdocument `FullTextDocument.update`) mutates that instance IN PLACE. It is called from `NormalizedTextDocuments` (langium/lib/lsp/normalized-text-documents.js:101) through BBj's `createChangeRecordingTextDocumentsConfiguration` (bbj-vscode/src/language/bbj-kept-check.ts:285).

A test that builds two separate TextDocument objects with different versions would pass while production stays broken. The test MUST mutate the live instance in place.

### Freshness signal: CST root fullText vs live text (verified)
- `LangiumParser.parse(input)` calls `nodeBuilder.buildRootNode(input)` BEFORE lexing (langium/lib/parser/langium-parser.js:127). So `root.fullText` is the raw document text, not the lexer-rewritten text.
- BBj uses a standard `LangiumParser` (`createBBjParser` in bbj-module.ts:174, built with `prepareLangiumParser`). There is no custom LangiumDocumentFactory in src/language.
- bbj-validator.ts:289 already documents fullText as "the ORIGINAL, pre-rewrite document text".
- Precedent: bbj-diagnostic-reconciliation.ts:479 compares `validatedText === liveText` in exactly this way.
- Cost: when fresh, both strings are the same reference (`getText()` returns the content string that was handed to the parser), so the comparison is O(1). When stale, it usually exits early.

### Lock ordering and deadlock analysis (verified in langium/lib/workspace/workspace-lock.js)
- `DefaultWorkspaceLock.performNextOperation` always runs the next queued write first and runs reads only when the write queue is empty. A read therefore resolves only after every write queued before it, and every write queued while it waits.
- Writes never wait for reads. The read action is a no-op that awaits nothing. The inlay provider runs in Langium's request handler, never inside the lock. So there is no cycle and no deadlock.
- The read takes no cancellation token. The provider must race it against `cancelToken`. An abandoned read entry resolves harmlessly later.
- `fireDocumentUpdate` enqueues the write in `workspaceManager.ready.then(...)`, which is a microtask after the didChange. vscode-jsonrpc dispatches each message on its own macrotask, so the write is already queued when the inlay request reaches the provider. One `delayNextTick()` (exported by 'langium') before each lock read is defensive and cheap.

### Error transport (verified)
- `createServerRequestHandler` catches errors from the provider. `responseError()` (language-server.js:545-552) returns `RequestCancelled` for `OperationCancelled` and returns the error itself when `err instanceof ResponseError`. Anything else is rethrown as an internal error.
- langium imports ResponseError from 'vscode-languageserver-protocol'. That package resolves the NESTED vscode-jsonrpc 9.0.1 (bbj-vscode/node_modules/vscode-languageserver-protocol/node_modules/vscode-jsonrpc). The top-level vscode-jsonrpc package is 8.2.1, a DIFFERENT class. Import `ResponseError` and `LSPErrorCodes` from 'vscode-languageserver', which uses the same protocol copy as langium. Otherwise the instanceof check fails.
- ContentModified is silent in both clients:
  - vscode-languageclient `handleFailedRequest` returns the default value for inlayHint (node_modules/vscode-languageclient/lib/common/client.js:1846).
  - LSP4IJ `CancellationSupport` ignores it (lsp4ij/src/main/java/com/redhat/devtools/lsp4ij/internal/CancellationSupport.java:141).
  - The LSP spec reserves ContentModified for "result invalid due to a content change". An empty list would be a positive "no hints" answer.

### Test harness facts
- `parseHelper` builds with `LangiumDocumentFactory.fromString`, so its documents are NOT in TextDocuments. The existing tests therefore keep the fresh path automatically.
- `NormalizedTextDocuments.set(doc)` fires onDidOpen and onDidChangeContent (normalized-text-documents.js:48-58). The BBj builder's listeners return early only when the compiler trigger is 'off' (`eventArmsCheck`, bbj-document-builder.ts:111). The new tests must call `setCompilerTrigger('off')` (from src/language/bbj-document-validator.ts) so no live-parse or BBjCPL cycle is armed, and restore 'debounced' afterwards.

The test controls the rebuild itself with `services.shared.workspace.WorkspaceLock.write(token => services.shared.workspace.DocumentBuilder.update([uri], [], token))`.
